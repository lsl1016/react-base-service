# 技能与插件创建器实现方案

- 日期：2026-10-13
- 定位：为 react-base-service 增加「技能创建器」与「插件创建器（Bundle 创建器）」两个能力——让 ReAct 运行时里的 agent 能在对话中**起草、校验、交付**技能与 Bundle 插件包
- 前置决策（P0 硬约束，来自方案评审）：**agent 只产草稿，不自动生效**。技能落库一律 `status=0`，Bundle 只到"上传暂存 + 校验通过"，启用（status 0→1）与安装（`/bundle/install`）永远由人在面板操作。此边界不可被任何一期绕过
- 补充需求（2026-10-13 评审追加）：**草稿与安装产物按 app 隔离**——本 app 生成/安装的草稿与资源，其他 app 的接入方与运行时不可见；实现见 §6
- 关联文档：[ZCode插件与技能创建器学习.md](../ZCode插件与技能创建器学习.md)（本方案的机制来源）、[参考ZCode的运行时增强方案.md](../参考ZCode的运行时增强方案.md)（内置技能包机制的出处）、[plan/20261012_APP接入方工作台设计方案.md](20261012_APP接入方工作台设计方案.md)（§6 的 app 级鉴权前置依赖）、[system/skill.md](../system/skill.md)、[system/react_runtime.md](../system/react_runtime.md)

## 1. 背景与目标

ZCode 用两个"自举"的创建器（本身就是技能/插件）证明了：**创建器不是专用引擎，是两份写给模型看的工作流知识**。宿主只要已有 注册表 + 安装机制 + 工具通道，创建器就是一层知识封装（详见学习笔记 §0/§6）。

本项目对应地基已齐：Skill 注册表（双通道触发）、Bundle 插件包（快照回滚）、go:embed 内置技能包、危险工具确认、app 作用域。本方案要做的事只有三件：

1. 写两份创建器技能正文，经现有内置技能包机制分发；
2. 补一个小体量后端：bundle 校验端点 + 草稿暂存通道；
3. 把"产物治理"（防 agent 刷产物、防污染运行时索引）固化为硬边界。

**非目标**：不做公网 marketplace；不做 agent 自动安装/自动启用（即便未来放宽，也只通过 app 级开关，见 §8）；不改变既有 Bundle 安装/回滚语义。

**缺口只有两个**：① bundle 只有"安装"没有"校验不安装"；② agent 没有把多文件 bundle 草稿送到暂存区的通道（上传接口是 multipart 表单，http 业务工具构造 multipart 不一定方便，且需要一个"多文件 JSON → 暂存目录"的纯 JSON 通道）。

## 3. 总体设计

```
┌─ 内置技能包 bundled-skills/（go:embed，现有机制）
│    ├─ skill-creator/SKILL.md   技能创建器：教格式 + 创作循环 + 经 save_skill 落禁用草稿
│    └─ bundle-creator/SKILL.md  Bundle 创建器：教 manifest/目录规范 + 经 draft/validate 通道交付
│
├─ 新增后端（小体量）
│    ├─ POST /react/bundle/draft     {name, files:{path:content}} → 写入上传暂存区，返回 source 路径
│    └─ POST /react/bundle/validate  {source | 内联 files} → 复用 fetch+parse，只校验不落库，返回报告
│
└─ 人工闸门（现有机制，不改）
     ├─ 技能：面板 status 0→1 启用（草稿不进装配索引）
     └─ Bundle：面板 /bundle/install 安装、/bundle/uninstall 回滚
```

创建器技能对模型的交付要求统一为**四态汇报**（照抄 ZCode 的诚实汇报纪律）：已生成 / 已校验 / 已启用（已安装）/ 已试用——未到达的状态必须明说 pending，四态里 agent 自己只能推进到"已校验"。

## 4. 技能创建器（skill-creator）

### 4.1 内置技能「技能创建」内容设计

manifest.json 条目（沿用现有字段）：

```json
{
  "name": "技能创建",
  "file": "skill-creator/SKILL.md",
  "triggerCondition": "用户明确要求创建、改写或沉淀一个技能时",
  "executionSteps": "捕获意图 → 对照平台技能字段规范起草 → save_skill 落禁用草稿 → 指引用户面板启用试跑",
  "businessContext": "技能是 DB 注册表行，草稿 status=0 不进装配索引，启用权在用户",
  "triggers": ["创建技能", "新建技能", "做成技能", "沉淀为技能", "改写技能", "写一个技能"]
}
```

SKILL.md 正文须覆盖五块知识：

1. **字段规范**：逐字段教写法——`Name` 命名（中文短语，同一 app 内唯一）；`TriggerCondition` 给模型读，写"什么时候用 + 做什么"；`Triggers` 确定性子串，**高精度关键词，禁止过宽子串**（如"优化""看看"），并要求与同 app 存量技能的 triggers 查重；`ForbiddenCondition` 写反触发条件；`ExecutionSteps`/`BusinessContext`/`Content` 各自的职责与篇幅（Content 目标 < 300 行，超长应考虑拆分或收敛）。
2. **运行时行为**：装配期索引只注入 name/triggerCondition 摘要 → 模型 `get_skill` 两段式取全文。因此**触发字段决定"被看见"，Content 决定"被用好"**——两者要分开打磨。
3. **创作循环**（ZCode 方法论的本地化）：先从当前对话历史提取已有素材（用了哪些工具、步骤、纠错）→ 起草 → 设计 2–3 个口语化测试提示词 → 试跑验证 → 迭代。改进原则：泛化而非堆 MUST、删无效指令、解释为什么。
4. **写通道**：调用 `save_skill` 业务工具（见 4.2）落 `status=0` 草稿；**更新优先于新建**（先 `/skill/list` 查同名，改写保持 SkillID 不变）。
5. **交付话术**：告知草稿名 + 面板启用路径 + 验收提示词与预期；四态汇报模板。

### 4.2 写通道：`save_skill` 业务工具

- **P0（零后端）**：注册一个 http 型业务工具指向现有 `/skill/import`（粘贴导入天然支持 `status` 字段与 frontmatter 中的 app_key/route_values），加 `/skill/list`、`/skill/update` 两个查询/更新工具。业务工具走现有两段式协议（`get_tool` → `execute_tool`），鉴权随 app 能力池。
- **P1（增强）**：替换为专用 `save_skill` 工具（client 型或服务端内置），增加 dry-run 校验：必填完整性、同 app 重名检测、triggers 与存量技能的子串冲突检测（两个技能的 trigger 词互为子串 → 警告）、Content 行数告警。挂**危险工具二次确认**（写库前用户确认一次）。

## 5. 插件创建器（bundle-creator）

### 5.1 内置技能「Bundle 创建」内容设计

triggers：`["创建bundle", "新建bundle", "做一个插件包", "打包成bundle", "安装插件包"]`；triggerCondition 限定"用户明确要求制作/打包 Bundle 插件包时"。

SKILL.md 正文须覆盖：

1. **产物规范**：manifest 三字段（name 小写连字符 / version 语义化 / description）；目录布局 `agents/*.md`（基名即 agent 名）、`skills/<name>/SKILL.md`、`.mcp.json`（可选）；**只声明真正包含的组件**。
2. **工具来源决策树**（关键知识，防止产出"纸面技能"）：技能/子智能体引用的每个工具名，起草前必须先回答来源——① 已注册业务工具或内置工具（python_exec、delegate_agent 等，最常见）；② 已部署的 HTTP MCP 服务（服务先存在，`.mcp.json` 只做登记，bundle 不能自带可执行服务端代码——url 型约束是刻意的安全边界，对照 ZCode 本地 command 型 MCP 的差异见学习笔记）；③ 新能力是 HTTP 接口 → 产出业务工具配置草稿（JSON）交人审核注册，与技能草稿同一治理模式（P2 的 `tools/` 组件落地后可直接随包声明，见 §5.3）；④ 计算/数据处理类"新能力"优先用 python_exec 表达，不造新工具。**引用了不存在工具的技能禁止交付**。
3. **边界知识**：来源白名单语义（内部 git / 本地路径 / 上传暂存区）；安装语义（重装=先卸载再装、卸载按快照回滚）；**更新纪律：改内容必须 bump version**。
4. **工作流**：明确目标与验收示例 → 组装 files（纯文本映射）→ `bundle_draft` 暂存 → `bundle_validate` 校验 → 修复循环直到校验通过 → 交给人安装。**禁止**：不得调用 install、不得宣称未校验/未安装的包可用、不得生成空 MCP 骨架冒充集成（照抄 ZCode 的"空握手骨架不算可用"纪律）。
5. **交付话术**：暂存 source 路径 + 校验报告 + 面板安装步骤 + 验收提示词；四态汇报。

### 5.2 新增后端：draft + validate 两个端点

```
POST /react/bundle/draft
  req:  { name string, files map[string]string }   // 相对路径 → 文件内容，纯 JSON
  行为:  校验路径干净（拒绝绝对路径/..//空路径）、必须有 manifest；
        写入 cache_dir/uploads/<draft-name>/ 下，纳入现有暂存区白名单与过期清理
  resp: { source }                                   // 可直接作为 /bundle/install 的 source

POST /react/bundle/validate
  req:  { source string } | { files map[string]string }（内联，不落盘）
  行为:  复用 fetch.go 的 readBundleDir/解析逻辑 + Install 的前置校验，只校验不落库
  resp:  { ok, checks: [{item, passed, detail}] }    // manifest 合法性 / 必备目录 / skills 与 agents
                                                     // 声明的文件齐全 / .mcp.json JSON 合法 / 路径不越界
                                                     // / 工具引用闭环：包内 skills、agents 引用的工具名
                                                     //   对照 已注册业务工具 + 内置工具 + .mcp.json 登记
                                                     //   的服务，引用不存在工具 → 红灯（url 服务实际
                                                     //   工具集探测为 warning 软检查，与"连接失败不阻断
                                                     //   安装"语义一致）
```

**工具引用闭环是硬检查**：没有它，"结构合法但跑不起来"的包会静默通过校验——模型装完照技能正文调 `get_tool` 直接失败。此检查依赖读取业务工具注册表与内置工具清单，实现时注意 validate 端点无副作用（只读）。

实现要点：`validate` 直接复用 [service/bundle/fetch.go](../../service/bundle/fetch.go) 已有的解析函数，包一层"不 Install"的早退；`draft` 复用 upload.go 的暂存目录与清洗逻辑（`sanitizeBundleUploadName`、`isJunkUploadSegment`）。两个端点合计预计 < 200 行，带单测（校验矩阵：缺 manifest / 坏 JSON / 路径穿越 / 正常包）。

### 5.3 工具与 MCP：`tools/` 组件与双消费面（P2 完整设计）

§5.1 决策树里"新能力是 HTTP 接口"这条路，长期答案是**把工具做成 bundle 的一等组件**。可行性依据是项目已有的双消费面架构——工具是注册表数据，不是进程：

```
                    tblLlmTool（工具本体，唯一存储）
                   ↗          ↘
     写入方（三个）                消费面（两个）
     · playground 管理侧栏        · 对内：ReAct 两段式（get_tool / execute_tool）
     · mcp-admin 控制台           · 对外：mcpgateway 标准 MCP Server
     · bundle tools/ 安装（P2）      （Bearer 凭证 + tblLlmMcpAppTool 授权白名单）
```

三张表各司其职，网关对工具定义**无状态**（[service/mcpgateway/registry.go](../../service/mcpgateway/registry.go) `LoadTools` 实时读 `tblLlmTool` 再与授权白名单取交集，运行时视图而已）：

| 表 | 存什么 | 说明 |
|---|---|---|
| `tblLlmTool` | 工具本体：name / description / config（url/method/headers/timeout + input/output schema）/ app_key / status | 对内运行时与对外网关的共同数据源 |
| `tblLlmMcpApp` | 网关应用凭证（Bearer app_key:app_secret） | 发给外部消费方 |
| `tblLlmMcpAppTool` | 应用 ↔ 工具授权白名单 | **不存工具定义**，只存"绑定即权限"的关系 |

**`tools/*.json` 组件设计**（四条）：

1. **格式不新发明**：直接对齐 `tblLlmTool.config` 结构——已有两个现成的字段拼装参考实现（mcp-admin 的 `buildToolConfigJSON`、工具管理接口入参），保证三写一读不漂移。
2. **安装语义**：写 `tblLlmTool`（app_key 归属 + 快照回滚）；`BundleResourceType` 新增 `tool` 类型进 `tblLlmBundleResource` 资源清单，卸载才能覆盖到它。
3. **网关自动纳入、共享显式**：落库即进网关基础集合（无需也不能"往网关表同步工具"），但对外不可见——别的 app / 外部消费方要用的唯一通道是管理员写 `tblLlmMcpAppTool` 授权行。与 §6 隔离语义一致（隔离默认、共享显式）；manifest 可选的预授权 grants 段**默认不做**（避免扩大包的权限面）。
4. **来源标识**：`tblLlmTool` 建议补 source 维度（admin / bundle / agent），并在 validate 报告中提示"将覆盖非本包来源的同名工具"——否则"卸载 bundle 会不会回滚控制台手工配的工具"无法预判，管理员不敢装包。

**为什么"创建 MCP"这件事消失了**：ZCode 的包必须携带 MCP server 进程（command 型 + 包内脚本），因为它的工具没有统一注册表可落；本平台本身就是 MCP server（mcpgateway），bundle 只声明工具、server 由平台统一提供。工具逻辑依然不进 bundle——落在上游 HTTP 服务（工具是其声明式绑定）、python_exec（运行时计算）或外部 MCP 引用（`.mcp.json`）三处之一，"bundle 携带可执行代码"的安全边界保持完整。

## 6. 草稿的 app 级隔离

需求：本 app 生成/安装的草稿与产物，其他 app 的**接入方与运行时**不可见。平台管理员的全局视图不受此约束——隔离的是 app 之间，不是运营与 app 之间。

### 6.1 隔离现状：一半天然成立，一半缺维度

| 产物 | 隔离现状 | 结论 |
|---|---|---|
| 技能草稿（DB 行） | `Skill.AppKey` 非空；装配索引按 `AppCapabilityScopeKeys` 查询（app 自身 + 继承的 default 伪 app，[models/llm/skill.go:170](../../models/llm/skill.go#L170)），app A 的行进不了 app B 的索引 | **天然隔离**，只需守住 §6.3 规矩 |
| Bundle 包内资源（安装后） | skill/agent 落库带安装 appKey；`.mcp.json` 登记的 server 行带属主 app，其工具仅对属主 app + 显式绑定的 app 可见（[models/llm/mcp_server.go:163](../../models/llm/mcp_server.go#L163)） | **天然隔离**，无需改造 |
| Bundle 草稿（暂存区文件） | `cache_dir/uploads` 是全局目录，无 app 概念，拿到 source 路径即可安装 | **缺维度**，需 §6.2 改造 |
| Bundle 安装记录 | `tblLlmBundle` 无 `app_key` 列，`/bundle/list` 无 app 过滤 | **缺维度**，需 §6.2 改造 |

### 6.2 改造设计：路径分区 + 草稿元数据表 + 安装记录补列

**暂存路径按 app 分区**：`cache_dir/uploads/<appKey>/<draftName>/`；TTL 清理（`cleanupAgedBundleUploads`）改为按 app 子目录扫描，清理逻辑本身不变。草稿与安装记录是两种生命周期（TTL 临时对象 vs 持久 + 快照回滚），草稿元数据**独立建表**，清理/安装收敛走**硬删**（草稿不做软删找回）：

```sql
CREATE TABLE IF NOT EXISTS `tblLlmBundleDraft` (
    `id`            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY COMMENT '自增主键ID',
```

**`tblLlmBundle` 加归属列**（安装归属记录，`/bundle/list` 按调用方 app 过滤的依据）：

```sql
ALTER TABLE `tblLlmBundle`
    ADD COLUMN `app_key` VARCHAR(64) NOT NULL DEFAULT '' COMMENT '归属app(安装时从上下文注入;空串=存量未归属,仅管理员可见)' AFTER `name`,

```

存量行的空 `app_key` 语义定为"平台级（仅管理员可见）"，不强制回填。

### 6.3 归属校验规则（硬规则）

1. **appKey 单一来源**：`save_skill`、`/bundle/draft`、`/bundle/validate`、`/bundle/install` 的 appKey 一律由**服务端从调用上下文注入**（业务工具调用的 app 身份 / app 级鉴权中间件），请求体不接收、不自报；仅平台管理员身份可显式指定。
2. **技能禁写 default 池**：`default` 伪 app 全 app 可见，写 default 等于主动广播——save_skill 校验注入 appKey ≠ default；提池只能是人在面板的显式操作。
3. **草稿路径即归属**：draft 写入路径必须落在 `cache_dir/uploads/<ctxAppKey>/` 之下；validate / install 遇暂存区 source 时按路径反解属主，与调用方 appKey 不一致即拒绝——同时堵住"拿别的 app 的草稿来装"和"把自己的草稿装进别的 app"两个方向。
4. **安装记录归属**：install 落 `tblLlmBundle.app_key`；draft list / bundle list 按调用方 app 过滤。
5. **管理员豁免**：平台管理控制台身份保留全局视图与跨 app 安装能力。

### 6.4 前置依赖：app 级鉴权

"从调用上下文注入"成立的前提是接口能识别调用方 app，而现状管理接口不校验 app 归属（信任 `X-User-Name` 头，问题盘点见 [20261012_APP接入方工作台设计方案.md](20261012_APP接入方工作台设计方案.md)）。完整隔离链路：

```
app 级鉴权中间件（20261012 方案 P0）
  → appKey 从鉴权上下文注入（§6.3 规则 1）
  → 存储层 app 维度（skill.app_key 天然 / 暂存区分区 / 草稿表 / bundle 表新列）
  → 列表接口按 app 过滤
```

在 app 级鉴权落地前，draft / validate / install 先以"业务工具调用的 app 身份"作为注入来源（内部调用可信），面板全量视图维持现状；与 20261012 的鉴权中间件合流后即闭环。

## 7. 产物治理：四道闸门（评审结论固化）

| 闸门 | 挡什么 | 机制 |
|---|---|---|
| 触发闸 | 误触发（用户没想创建） | 创建器 triggers 只放显式意图词；`ForbiddenCondition` 写明"讨论改进流程 ≠ 要求创建"；**创建器宁可漏触发**（与普通技能相反） |
| 落点闸 | 产物散落 | 技能草稿只落 DB（status=0）；Bundle 草稿只落上传暂存区（天然白名单 + TTL 清理）；agent 无任意文件系统写权限 |
| 生效闸 | 污染运行时索引 / 自我修改闭环 | status=0 不进装配索引（[models/llm/skill.go:177](../../models/llm/skill.go#L177)）；启用与安装是纯人工动作；`save_skill` 挂危险确认——闭环断在"人按生效键"这一步 |
| 生命周期闸 | 草稿无限堆积 | 同名幂等更新（保 SkillID/包名，不造 v2）；Bundle 暂存区沿用 `cleanupAgedBundleUploads` 过期清理；P1 面板加"草稿技能"筛选（status=0 列表 + 一键清理） |

最坏情况量化：模型失控连造 10 个技能 + 5 个 bundle，后果 = 10 行禁用 DB 行 + 5 个过期自动清理的暂存目录，**运行时零感知**。

## 9. 风险与待决问题

1. **提示工程质量是主要风险**：创建器技能太啰嗦会拖慢每次触发的执行。上线后按 ZCode 的 trace 审查法迭代（模型兜圈子 = 指令过度规定，做减法）。
2. **http 业务工具回环调用自身管理 API 的鉴权形态**（P0 的 save_skill）：依赖免鉴权中间件信任 `X-User-Name`。若某部署形态收紧管理面鉴权，P0 形态需带 token 配置——P1 专用工具（服务端内置，不走 HTTP 回环）天然规避，可按部署形态决定是否直接跳到 P1。
3. **bundle draft 端点的写放大**：files 全量 JSON 提交，单包体积上限沿用 upload 的现有上限配置，超限直接拒绝。
4. **暂存区清理对"未安装草稿"的影响**：TTL 过期会删掉用户还没来得及安装的草稿——validate 报告与交付话术中必须提示暂存时效，重要包应尽快安装或转存内部 git。
5. **工具注册表多写入方的覆盖语义**（P2 `tools/` 组件生效后）：`tblLlmTool` 将有三个写入方（playground 管理侧栏、mcp-admin 控制台、bundle 安装）。bundle 覆盖安装可能回滚控制台手工注册的同名工具行——快照保证数据可恢复，但必须先落 §5.3 第 4 条的来源标识，validate 报告对"将覆盖非本包来源的同名工具"给出显式提示。
