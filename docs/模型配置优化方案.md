# 模型配置优化方案

> 背景：playground 接入智谱 GLM 时暴露出模型配置链路的一系列可用性问题（脱敏 key 回传、
> OpenAI 兼容 URL 404、连通性检测吞错等）。本文档沉淀市场调研结论与分阶段改造方案。
>
> 调研与方案日期：2026-09-28。文中「当前实现」均指本次调查时的 main 分支代码。

---

## 1. 市场调研：主流 Agent 的模型配置形态

调研对象：Cline、OpenCode、Cherry Studio、Open WebUI、LobeChat、Dify。
它们的模型配置形态高度收敛为四个模式：

### 1.1 连接与模型分离（Provider/Connection-first）

配置的主体是「**连接**」= 协议类型 + Base URL + API Key；模型是挂在连接下的条目。

- 协议枚举只有两种：**OpenAI 兼容** / **Anthropic 兼容**；
- 「厂商」不是必选概念，只是**预设模板**——选「智谱」自动填好 URL 和协议，选「自定义」就手填；
- Cline 的 `API Provider → Base URL → API Key → Model ID` 四段式即此形态。

### 1.2 模型列表自动发现

填好连接后一键从 `GET {baseURL}/models` 拉取可用模型列表：

- Cherry Studio 的「获取模型列表」按钮、Open WebUI 外部连接的刷新图标、
  Cline 对 OpenAI Compatible 端点的 /models 拉取；
- 拉不到时手动填模型 ID 兜底；
- 用户**永远不需要凭空记忆模型版本字符串**。

### 1.3 连通性测试在连接级别，错误透传

测的是「这条连接通不通」，失败时把上游真实错误（401 无效 key / 404 路径错 / 超时）
展示出来，而不是吞成一句「请求失败」。

### 1.4 Key 与 URL 的防御性处理

- 编辑时 key 留空 = 保持原值，**绝不把脱敏显示值回传**；
- Base URL 归一化：容忍 `/v1`、`/v4` 结尾、尾斜杠、甚至完整 endpoint 路径；
  LobeChat issue #7099（同一地址 Cherry Studio 可用而 LobeChat 不可用）即栽在
  URL 拼接差异上；
- OpenCode 另用 [models.dev](https://models.dev) 目录做模型能力元数据
  （上下文窗口 / vision / tools / reasoning）的自动填充。

### 2.1 本次实测记录（问题证据）

以下为 2026-09-28 在本机 playground 的实测，可作为回归用例：

1. **404（URL 拼接）**：接入地址填 `https://open.bigmodel.cn/api/coding/paas/v4`，
   claude client 拼出 `/v4/v1/messages` → 上游 404，UI 报「连通失败: 6080003 请求失败」；
2. **401（脱敏 key 回传）**：编辑已保存模型、key 输入框为空（占位符显示脱敏值）时点
   「测试连通性」/「保存」，前端把 `316c****zAtY` 当真实 key 发出 → 上游 401
   「令牌已过期或验证不正确」。curl 复现：脱敏值 6080003 失败，真实 key errNo=0 成功；
3. **可用路径**：modelKey=Anthropic + 接入地址空（回退 api.yaml `claude` 端点
   `https://open.bigmodel.cn/api/anthropic`）+ 真实 key → WS 对话 glm-4.6 / glm-5.3
   均正常返回（content/done 事件带 token 用量）。

## 3. 优化方案（分三阶段）

### 3.1 P0 — 修 bug 级（半天，立刻做）

1. **脱敏 key 兜底修复**（`SettingsDrawer.tsx`）：
   `apiKey()` 为空时先拉 `getUserModelDetail` 取真实 key；取不到则禁用按钮并提示
   「请填写 API Key」。`props.item.apiKey`（列表脱敏值）永远不得作为请求值。
2. **连通性检测修正**：
   - controller 透传 `req.ApiUrl` 到 `CheckConnectivityWithEndpoint`；
   - 错误文案带上游信息，如 `401 令牌无效（来自 open.bigmodel.cn）`
     （`components.ErrorUserModelConnectivityFailed` 的参数带上 status + host + body 摘要）；
   - 超时 15s → 30s（思考模型冷启动首 token 可能超 15s）。
3. **URL 归一化** `normalizeBaseURL(url, protocol)`（新增于 `api/llm/`）：
   - 剥尾斜杠；
   - OpenAI 协议：base 已含 `/v1`、`/v4`、`/api`… 版本段时只拼 `/chat/completions`，
     否则拼 `/v1/chat/completions`；
   - Anthropic 协议：同理只拼 `/messages` 或 `/v1/messages`；
   - `gpt.go` / `claude.go` 的三处拼接点统一走该函数。
   预期消掉当前大部分「照着厂商文档贴地址 → 404」类配置失败。

### 3.2 P1 — 连接与模型分离（核心重构，2~3 天）

**数据模型**：

- 新表 `tblLlmConnection`：
  `{id, name, protocol(openai|anthropic), base_url, api_key, caller_key, route_values, status, created_by, ...}`；
- `tblLlmUserModel` 加 `connection_id`（可空）：非空时 key/base_url 以连接为准；
- 存量数据迁移：按 `model_key + api_url` 归并生成连接，模型挂接。

**后端**：

- `/model/connection` CRUD（对齐现有 /apikey 风格，caller + route 前缀匹配）；
- **`/model/connection/:id/fetch_models`**：服务端代理调上游 `GET {base}/models`，
  key 不出后端、无 CORS 问题，返回规范化模型 ID 列表；
- 运行时 client 构建改为 connection 驱动：`protocol` 直接决定 gpt/claude client，
  `base_url` 直接是 ApiUrl——**删除 `modelKeyEndpointOverrides` / `modelKeyIsCN`
  推导链**，端点黑盒消失；
- `conf/mount/api.yaml` 降级为「内置连接的种子数据」（厂商预设模板），
  `api_keys` 的 `${ENV}` 注入语义保留给平台级连接。

**前端**（重做 SettingsDrawer「厂商与密钥」tab）：

```
┌ 连接列表 ────────────────────────────────────┐
│ [智谱 GLM (Anthropic)]  ● 已连通  3 个模型    │
│ [DeepSeek 官方]         ● 已连通  2 个模型    │
│ [自建网关]              ○ 未测试  1 个模型    │
│                                              │
│ + 添加连接                                   │
│   ① 选预设：智谱(Anthropic)/智谱(OpenAI)/    │
│      DeepSeek/OpenRouter/自定义 → 预填协议+URL│
│   ② 填 API Key → [测试连通]（透传真实错误）  │
│   ③ [拉取模型列表] → 勾选启用 → 批量创建     │
│      （手动填模型 ID 作为兜底入口）           │
└──────────────────────────────────────────────┘
```

完成后配置路径从「理解厂商枚举 → 猜端点推导 → 手填版本 → 踩 404」
变为「选预设 → 贴 key → 点两个按钮」，与 Cherry Studio / Cline 对齐。

### 3.4 Key 双轨消除（并入 P1 一起做）

对「API Key 模块是否冗余」的评估结论（2026-09-28 补充调查）：

- **api.yaml `api_keys`（`${ZHIPU_API_KEY}` 环境变量注入）是死配置**：唯一读取方
  `llm.GetClient()` 生产代码零调用（仅 `client_test.go`）。清除，连同
  `GetClient` / `GetClientWithKey` 死代码（或保留函数改读连接表）。
- **caller 级 API Key 模块职责真实但形态错位**：它是不带 ModelHash 路径
  （业务 Caller 契约路径：`modelKey+modelVersion` + caller 级凭证 + 平台端点兜底）
  的凭证面，直接删除会让 `/react/models` 目录模型全部报 `ErrorApiKeyNotFound`。
  但它被做成了与模型配置并列的独立管理页，造成「key 存两份、哪份生效不可知」。
- **ModelHash 与契约的关系**：ModelHash 是「引用自己注册的模型实例」的资源句柄
  （按 userName 归属、可被编辑删除，不适合跨团队契约）；`modelKey+modelVersion`
  是「调用平台承诺的某类模型」的逻辑名。业务接入契约是后者。

**动作**（随 P1 落地）：

1. `tblLlmApiKey`（callerKey + routeValues + key）升维成 `tblLlmConnection`
   ——补 `protocol` + `base_url` 即是「带租户作用域的平台连接」；
2. 无 ModelHash 路径解析顺序：**连接（caller+route 前缀匹配）→ 旧 tblLlmApiKey 兜底 →
   报错**，对外契约不断，存量数据无需迁移即可继续生效；
3. playground 独立的「API Key 管理」页撤掉，入口并入「厂商与密钥」的连接列表
   （后端 `/apikey` 路由保留，作为契约兼容层）；
4. 清除 api.yaml `api_keys` 死配置段。

改完后「key 存哪、哪份生效」只有一个答案：**连接**。模型要么引用连接（connection_id），
要么 caller+route 解析到连接。

### 3.5 P2 — 体验增强（1~2 天）

1. **能力目录**：内置 models.dev 风格 JSON（模型 ID → 上下文窗口 / vision / tools /
   thinking），`fetch_models` 返回时自动填充能力开关与 ContextTokens；
2. **默认 / 备用模型角色**：per bizScene 设默认模型，接到已有的模型互备
   （`service/react/model_failover.go`）上；
3. playground `web/react/index.js:220` 不再写死 `modelVersion: 'glm-4.6'`，
   模型选择器按连接分组、默认取平台默认模型。

### 5.2 能力目录与运行时接线（P2 前两项，2026-09-28 已实现）

**能力目录**（`api/llm/capability_catalog.json` 内嵌 + `capabilities.go`）：

- 匹配规则：exact 全等命中优先（大小写不敏感）→ prefixes 顺序首个前缀命中
  （具体变体前缀必须排在家族前缀前，如 `glm-4.5v` 在 `glm-` 之前）；
- `LookupModelCapabilities(modelID)` 返回 tools/thinking/vision/容量声明，
  未命中 Known=false（保守全关）；
- 种子覆盖 glm 全系（工具+思考、无视觉；4.5v/4.6v 变体含视觉）、deepseek、claude、
  gpt、qwen、minimax；目录是可编辑的本地数据，能力声明可被每模型开关覆盖。

**接线链路**：

1. `fetch_models` 响应升级为 `{id, supportTools, supportThinking, supportVision,
   contextTokens?, maxOutputTokens?}`（目录自动填充）；前端勾选列表渲染
   「工具/思考/视觉」徽标，批量启用携带能力位落库；
2. **tools 门禁**：run 快照用户模型能力声明（runtimeRequestModel.caps*），
   主模型轮声明不支持 tools 时不下发工具 schema（模型按纯对话作答，循环自然收敛）；
   互备模型不做门禁（沿用平台目录口径）；
3. **thinking 门禁**：能力声明经 `WithModelCapabilities` 挂入 llmCtx，claude client
   的 thinking 参数与 gpt client 的 reasoning_effort 在声明关闭时不下发；优先级 =
   run 声明 > 模型目录 > 旧启发式；
4. **vision 门禁**：`rejectVisionFilesForCaps` 在 claude/gpt 的
   `ChatStreamWithFilePayloads`（文件入模边界）拒绝 image/* 载荷。注意：主对话链路
   `LLMMessage` 为纯文本（附件走 read_attachment/python_exec 文本路径），当前不存在
   图片入模路径，此门禁为预留边界的先行约束。

**实测验收**：glm-4.6（挂连接）A/B 对照——supportTools=0 时 0 个工具事件、模型纯文本
作答；恢复 =1 后 4 个工具事件、python_exec 算出 12345×67=827115 正确。fetch_models
对 11 个 glm 模型正确返回 工具+思考+无视觉。

**遗留（P2 剩余）**：默认/备用模型角色、playground 写死 glm-4.6、api.yaml `api_keys`
死配置清除。
