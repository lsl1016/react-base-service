# 整合流程详解

当同模块的 active 变更文档累积过多时，把内容整合进系统文档。本文详解流程与常见误区。

## 核心等式

```
整合 = 内容融进系统文档 + 原文件 status 改 merged
整合 ≠ 删除原文件
整合 ≠ 把 N 篇拼成一篇合集
```

## 为什么原文件必须保留

系统文档和变更文档承载**不同类型**的信息：

| | 系统文档 | 变更文档 |
|---|---|---|
| 回答 | 现在是什么样 | 为什么变成这样 |
| 内容 | 最终状态、当前行为 | 根因、决策过程、被否决的方案、事故记录 |
| 整合后 | 保留并更新 | 保留，仅改 status |

整合时会被**丢弃**的信息（因为不属于"当前状态"）：

- 线上事故的 requestId、受影响的具体用户和数据记录
- 为什么放弃了方案 A 而选择方案 B
- 某个口径在三周内调整了三次的原因
- 当时的测试输出和验证过程

这些信息在未来排查同类问题、评估重构风险、理解"为什么代码写成这样"时是唯一来源。系统文档不会保留它们。所以原文件删不得。

**"git 历史里还有"不成立**：实践中没有人会去 git 历史里翻已删除的文档。删除等同于丢失。

## 五步流程

### 1. 圈定范围

按 `module` 字段，不按文件名：

```bash
grep -l "^module: acceleration" docs/changelog/*.md | xargs grep -l "^status: active"
```

⚠️ 文件名含关键词但 `module` 是别的模块的，**不属于本次范围**。例如文件名带"加速"但 front-matter 是 `module: migration` 的文档，属于 migration 的历史，不要卷进来。

### 2. 判断哪些内容已被吸收

先完整读一遍 `docs/system/<模块>.md`。

整合往往不是"把 N 篇文档拼起来"，而是"**补完尚未吸收的部分**"。真实情况常常是：20 篇 changelog 里 14 篇的内容其实已经在系统文档里了，只有 6 篇从未被吸收。识别出这 6 篇，工作量和出错率都大幅下降。

### 3. 融进对应章节

事实性内容按语义归位：

| changelog 里的内容 | 归入系统文档 |
|---|---|
| 新增接口 | §2 接口清单 |
| 行为规则、算法、流程 | §3 核心逻辑（可新增子节） |
| 新表、新字段、枚举值 | §4 数据模型 |
| 新配置项、容量限制 | §5 配置项 |
| 本次整合的说明 | §6 历史版本（加一行） |

**不要**在系统文档尾部追加"## 历史变更"节堆放 changelog 原文。那会让系统文档变成变更史，失去"描述当前状态"的语义。

同时更新系统文档 front-matter 的 `version`（递增）、`date`（改为今天）、必要时补充 `related_code` 和 `summary`。

### 4. 逐个改 status

范围内每一篇 changelog，`status: active` → `status: merged`。

**这一步在实践中最常被跳过。** 后果：下次整合时无法判断哪些已处理，索引与实际状态长期不一致。真实项目里出现过 229 篇 changelog 中只有 1 篇标了 merged，而索引却记录约 90 篇已合并的情况 —— 两边彻底失去可信度。

### 5. 回填索引

存在 `docs/changelog/README.md` 或 `docs/system/README.md` 时，同步更新其中的状态列、版本列、最近更新列。

## 合并前后对照

以下是**虚构示例**，用于展示文件状态的变化形态。
⚠️ 不要套用这里的篇数或结论 —— 每次整合都必须实际 grep 出真实范围。

假设 `billing` 模块经 grep 得到 8 篇 `status: active`，其中 3 篇内容已被系统文档吸收、4 篇未吸收、1 篇是运维手册。

### 合并前

```
docs/changelog/
├── 20260301_v1.0_账单列表增加筛选.md        status: active    未吸收
├── 20260315_v1.0_账单列表空间隔离.md        status: active    未吸收
├── 20260322_v1.1_修复账单金额精度.md        status: active    未吸收
├── 20260405_v1.0_新增批量对账接口.md        status: active    未吸收
├── 20260112_v1.0_账单生成流程调整.md        status: active    已吸收
├── 20260128_v1.0_对账周期配置化.md          status: active    已吸收
├── 20260210_v1.0_账单表新增字段.md          status: active    已吸收
└── 20260220_v1.0_账单数据修复操作手册.md    status: active    运维手册

docs/system/billing.md    version: v1.4, §1-§6
```

### 合并后

```
docs/changelog/
├── 20260301_v1.0_账单列表增加筛选.md        status: merged    ← 文件仍在
├── 20260315_v1.0_账单列表空间隔离.md        status: merged    ← 文件仍在
├── 20260322_v1.1_修复账单金额精度.md        status: merged    ← 文件仍在
├── 20260405_v1.0_新增批量对账接口.md        status: merged    ← 文件仍在
├── 20260112_v1.0_账单生成流程调整.md        status: merged    ← 文件仍在（内容早已吸收，仅改状态）
├── 20260128_v1.0_对账周期配置化.md          status: merged    ← 文件仍在（同上）
├── 20260210_v1.0_账单表新增字段.md          status: merged    ← 文件仍在（同上）
└── 20260220_v1.0_账单数据修复操作手册.md    status: active    ← 运维手册，不整合，状态不变

docs/system/billing.md    version: v2.0
├── §1 模块概述              原有
├── §2 接口清单              ← 新增"批量对账"一行
├── §3 核心逻辑              原有
│   └── §3.4 账单列表        ← 新增子节：筛选条件、空间隔离、金额精度规则
├── §4 数据模型              原有
├── §5 配置项                ← 补充链接指向账单数据修复操作手册
└── §6 历史版本              ← 新增一行记录本次整合
```

**关键点：**

- 文件数量**不变**（8 篇仍是 8 篇），只有 `status` 变了
- 已吸收的 3 篇同样要改 `status`，只是不需要再动系统文档
- 运维手册保持 `active`，系统文档加链接指向它
- 新内容**融进 §2/§3/§5 对应章节**，没有新开一节"历史变更"

§6 新增的那一行：

```markdown
| v2.0 | 2026-04-10 | <维护人> | 整合 billing 模块 7 篇变更文档；补充列表筛选与空间隔离、金额精度规则、批量对账接口 |
```

## 特殊情况

**跨模块的变更。** front-matter 只能填单一 `module`。一次改动波及多模块时，选主模块填 `module`，在 §3 影响范围里列出其他受影响模块。整合时按主模块归属。

**规范外的 status 值。** 实践中常出现 `draft`、`pending`、`dev` 等规范未定义的值。默认不纳入整合范围，但要列出来问用户，不要静默跳过。

**系统文档不存在。** 该模块从未有过系统文档时，整合的第一步是按 `bootstrap-project-docs` 的 6 节模板新建一篇，再把 changelog 内容填入。

## 检查清单

整合完成后逐项确认：

- [ ] 范围按 `module` 字段圈定，未误纳其他模块
- [ ] 事实性内容已融进系统文档**对应章节**，未追加"历史变更"节
- [ ] 系统文档 `version` 已递增、`date` 已更新
- [ ] 系统文档"历史版本"表已加整合记录
- [ ] 范围内**每一篇** changelog 的 `status` 已改为 `merged`
- [ ] **原 changelog 文件全部仍在**，一个都没删
- [ ] 索引文档的状态/版本/日期列已回填
- [ ] 运行 `bash scripts/check-docs.sh`（若存在）并贴出真实输出
