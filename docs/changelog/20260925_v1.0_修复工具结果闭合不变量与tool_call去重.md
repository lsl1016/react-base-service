# 修复工具结果闭合不变量与 tool_call id 去重（Tool Runtime 闭合治理 Phase 1-2）

## 1. 背景与目标

按《docs/plan/20260925_ToolRuntime流水线借鉴与优化方案.md》实施其 P0 两个阶段：Phase 1 闭合不变量修复（含中断文案区分）、Phase 2 tool_call id 去重。参照系为 ZCode Tool Runtime 的对应设计（`turn-tools.ts` 无条件结果提交循环、三层 id 去重、hydrator 孤儿回填）。

### 问题描述

- `engine.go` 模型轮循环中，`executeToolCalls` 返回任何错误即提前 `return`，本轮全部 tool_result 不落库——而 assistant `tool_use` 已在之前落库，历史中出现孤儿 tool_use；同 session 下次 run 重建上下文后，provider 请求携带未配对 tool_use，严格 Provider（Anthropic 系）直接拒绝请求。
- 串行执行路径出错即返回，出错调用之后的 results 为零值（连 ToolUseID 都没有）。
- 子代理 token 预算超限路径（`checkTokenBudget`）同样在不落结果的情况下终止。
- tool_call id 全链路无去重：模型/adapter 异常重复投递同 id 调用会重复执行，写类工具产生重复副作用。

### 根因分析

闭合依赖各错误路径"自觉回填"而非结构保证：中断回填存在四种并存的约定（`closeInterruptedToolUse` 返回结果、confirm/client-tool/ask_question 各自单独落一条单结果消息并返回零值），一旦执行入口在错误时提前 return，没有任何一层兜底。ZCode 的做法是把"结果提交循环对每个 result 无条件执行 + 恢复期 hydrator 回填"作为结构不变量。

### 影响范围

- 开发库实测存量数据：全库 1099 个 tool_use 中 19 个孤儿（所属 run 状态：error 7、expired 12），与上述两条错误路径完全吻合，证明 bug 真实发生过。

## 2. 代码改动

- `service/react/tool_closure.go`（新增）：闭合治理核心——
  - `roundInterruptedResults` 登记表（`recordInterruptedToolResult` / `interruptedToolResult`）：中断路径只登记不落库，登记表生命周期与一轮调度一致；
  - `synthesizeUnexecutedToolResult`：统一合成器（无 resultRef、status=cancelled）；
  - `duplicateToolCallIndexes` / `duplicateToolCallResult`：同轮重复 id 识别与拒绝结果；
  - `completeToolRoundResults`：收口补全（零值槽位先取登记，再合成"状态未知"）；
  - `fillUnexecutedSerialSuffix`：串行停止点之后的未开始调用合成"未执行"；
  - `backfillOrphanToolResults`：历史重建孤儿回填（纯函数，插入位置在该 assistant 的结果块末尾）；
  - 文案常量按 ZCode 语义区分：`toolUnexecutedContent`（未执行，可按失败处理）/ `toolUnknownStateContent`（状态未知，先核实再决定是否重试）/ `toolOrphanBackfillContent`（历史缺口）。
- `service/react/tool_dispatch.go`：`executeToolCalls` 入口清空登记表、按 id 去重跳过重复调用（重复 id 回灌拒绝结果不执行）；串行/并行两条路径收口处统一走 `completeToolRoundResults`，返回 results 永远与 calls 等长且槽位配对；`executeServerTool` 确认等待中断时取回登记结果填入槽位。
- `service/react/engine.go`：
  - 模型轮循环改为"无论执行是否出错，先落库本轮 tool_result 再返回"（执行错误与落库错误分别处理，落库失败打 `[React.Closure]` 错误日志、由重建回填兜底）；
  - `checkTokenBudget` 超限终止前调用 `persistBudgetExhaustedToolResults` 回填本轮未执行调用（该函数改用统一合成器）；
  - `collectLLMStreamWithEmitter` 收集 Done chunk 的 ToolCalls 时按非空 id 去重（第一层去重，防 adapter/协议重复投递）；
  - `reactMessagesToChatMessagesWithRefs` 接入 `backfillOrphanToolResults`（第三道防线：存量数据与极端故障兜底）；新增 `reactToolUseIDs` 日志辅助。
- `service/react/runtime_support.go`：`classifyToolInterruption` 文案升级为 unknown_execution_state 语义（"结果未提交，副作用状态未知，先核实当前状态再决定是否重试"）；`closeInterruptedToolUse` 从"单独落库"改为"登记 + 保留 resultRef 落库与事件发射"。
- `service/react/tool_confirm.go` / `client_tool.go` / `ask_question.go`：三个中断回填函数由"各自单独落库"改为登记制（`persistToolConfirmInterrupted`→`recordToolConfirmInterrupted`、`persistClientToolInterruptedResults`→`recordClientToolInterruptedResults`、`persistAskQuestionCancelledResult`→`recordAskQuestionCancelledResult`），事件发射（卡片收敛）与文案保持不变。
- `service/react/runtime_state.go`：`reactEngineState` 新增 `roundInterruptedResults` 字段。
- `service/react/tool_closure_test.go`（新增）：8 个单元测试覆盖去重索引、流收集去重、收口补全（登记优先/状态未知合成）、未执行后缀补全、合成器无 resultRef、孤儿回填三场景（结果块后插入/已配对不动/run 中断于末尾）。

## 3. 影响范围

- 接口：无新增或变更的 HTTP/WS 接口、事件类型与事件协议。
- 模块：仅 `service/react` 运行时的闭合与去重行为；`service/tool` 执行器、模型适配层、前端协议不变。
- 消息形态：中断轮的工具结果从"中断路径单独落的单条消息"统一为"引擎收口的一条合并 tool_result 消息"（与正常轮一致）；每个 tool_use 恰好一条配对结果。
- 配置与数据：不新增数据表、配置项或缓存；不涉及 SQL 变更与数据迁移。

## 4. 测试验证

- `go build ./...` — 通过。
- `go test ./service/react/ ./service/tool/ -count=1` — ok（react 包含新增 8 个用例，全量回归无失败）。
- `go test -tags orphancheck -run TestOrphanBackfillOnRealSession -v`（临时集成测试，直连本地开发库，验证后已删除）— 通过：session `session_b1e5b1a6…` 重建前含 SQL 定位的 2 个已知孤儿 id，经 `reactMessagesToChatMessagesWithRefs` 重建后孤儿数归 0，回填 3 条合成结果。
- 全库 SQL 不变量核查（JSON_TABLE 关联统计）：`total_tool_uses=1099`、`orphan_tool_uses=19`（error 7 / expired 12），确认修复针对的缺口真实存在且重建回填可覆盖。
- 启动验证：`go run main.go` 后 `:8180` 正常监听、`/react-base-service/react/playground` 返回 200、`POST /tool/list` 返回结构化参数校验错误（启动日志中 mcpgw 连接失败为外部依赖 127.0.0.1:18080 未运行的既有环境状况，与本次改动无关）。

## 5. 风险与兼容性

- 用户可感知的正向变化：取消/失败的 run，其历史中原本永远悬空的工具卡片现在有 cancelled/error 终态结果；后续 run 重建的模型上下文不再携带未配对 tool_use（存量孤儿由重建回填兜底，无需迁移）。
- 中断轮 tool_result 的落库时序与消息分组变化（见 §3）：对 provider 消息语法无影响；历史回放中中断轮会出现配对的错误结果。
- 模型行为：中断文案从"结果可能不确定"升级为"副作用状态未知，请先核实再决定是否重试"，预期模型在写类工具被打断后更倾向先核实而非盲目重试（对齐 ZCode 语义的预期效果）。
- 理论风险：引擎错误路径现在会先执行一次结果落库再返回错误，若 DB 长时间不可用，错误返回会多一次失败尝试（落库失败被捕获并记日志，不吞掉原始错误）。
