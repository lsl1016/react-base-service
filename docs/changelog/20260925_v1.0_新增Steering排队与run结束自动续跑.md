# 新增 Steering 排队与 run 结束自动续跑（S2）

## 1. 背景与目标

按《docs/plan/20260925_Session与Steering机制借鉴方案.md》实施其 S2 阶段（P0），复用 S1 建立的账本 `tblLlmReactPendingInput` 与结算机制。S1 之后仍有一段空缺：不可引导（HITL 等待/软着陆/带附件）时只能明确拒绝，用户输入直接丢失。S2 补齐排队语义：

1. busy 且不可引导 → 账本落 `queued` 行，回执 `{kind:"queued", queueLength}`；
2. run 正常结束（含 finishExhausted）后自动续跑队首，其余顺延；未开启自动续跑则留待显式发送（S3）；
3. 失败语义对齐 ZCode：run 出错/取消/超时不自动续跑（暂停，留给用户决定）；取消时未消费 guide 降级 queue 而非作废。

## 2. 代码改动

### 文件：`models/llm/react_pending_input.go`

1. **`ReactPendingInput` 新增 `payload_json` 列**：准入时保存原始 run 请求快照（ReactRunPayload 序列化），queue 晋升/自动续跑据此重建 run 请求。
2. **`GetNextQueuedBySessionWithDB`**：按会话准入序号取队首 queued 行（`Limit(1).Find` 避免 gorm record not found 噪音日志，guide 边界检查查询同改）。
3. **`MarkPendingInputPromotedWithDB`**：条件更新 `WHERE id=? AND status='queued'` 实现 claim-once 晋升，并归属到新 run。
4. **`FallbackPendingInputsToQueueWithDB`**：run 内未消费 admitted guide 降级 queue（status→queued、delivery→queue，对齐 ZCode fallbackPendingGuidesToQueue）。
5. **`SettleStaleQueuedBySessionWithDB`**：会话内 `created_at` 早于本进程启动时刻的 queued 行结算 `discarded(session_resumed)`——重启不复活队列，本进程新产生的排队行不受影响。

### 文件：`service/react/steering.go`

1. **准入保存 payload 快照**：`admitSteeringInputTx` 改收完整 payload 并序列化入账；steer 消息通常不带模型选择，缺省时回填被引导 run 的实际模型（modelKey/modelVersion），保证晋升重建 run 请求时模型选择有合理默认。
2. **`shouldAutoDrainQueue`（纯函数）**：排队开关 + 自动续跑开关 + run 成功收敛三者同时成立才续跑。
3. **`dequeueQueuedHeadForAutoDrain`**：读队首并构造续跑 payload（`PromotePendingInputID` 随 payload 传递）；claim 在新 run 的创建事务内完成。
4. **`settleRunPendingGuides` 队列化**：queue 开启时 run 终态的未消费 guide 改为降级排队并广播 `steer_delivery_changed`（reason=turn_ended）；queue 关闭时保持 S1 的 discarded 结算。
5. 新增进程启动时刻包级变量 `steeringProcessStart` 供陈旧队列结算判定。

### 文件：`service/react/runtime.go`

1. **`run()` 循环化 + `runSingle` 抽取**：原 run() 主体抽为 `runSingle`（单 run 生命周期与终态收敛不变），外层循环在 run 成功收敛后检查队列——有队首则构造续跑 payload 再次进入 `runSingle`，直至队列排空；同一 WS 连接内完成整个续跑链（readClient/hub 随每个 run 重建，defer 清理按 run 粒度保持原语义）。
2. **`createReactRunContext` 晋升原子化**：事务内 `persistUserInput` 之后按 `req.promotePendingInputID` 执行 `MarkPendingInputPromotedWithDB`（账本置 guided + run 创建 + 用户消息落库同一事务，对齐 ZCode promoteSessionInput 原子性）；claim 失败（已被消费/作废）整体回滚，杜绝双 run 消费同一条排队输入。
3. 陈旧 queued 结算并入既有 `session_resumed` 清理位置。

### 文件：`service/react/runtime_state.go`、`components/params/react.go`、`conf/config.go`、`sql/init.sql`

1. `runtimeRequestExecution` 新增 `promotePendingInputID`；`ReactRunPayload` 新增 `PromotePendingInputID uint json:"-"`（仅服务端 run 循环内部传递，不进 WS/API 序列化、不写入账本快照）。
2. 新配置 `llm.react.steering.queue_auto_drain`（未配置默认 true，仅 queue 开启时生效）。
3. init.sql 补 `payload_json` 列与存量环境增量迁移语句。

### 文件：`service/react/steering_test.go`

新增纯函数测试：`shouldAutoDrainQueue`（成功收敛才续跑、关闭任一开关不续跑）、`pickPendingQueued`（只取 queued 行、FIFO、admitted guide/已消费/已结算行不参与）。

## 3. 影响范围

- 接口：`/react-base-service/react/ws`——queue 开启后 run 活跃期间的不可引导输入返回 `steer_queued` 回执（S1 为 `steer_rejected`）；新增下行事件 `steer_delivery_changed`（guide 降级排队）。
- 模块：`react_runtime`；S1 的 guide 注入、结算路径、HITL 保护语义不变（仅结算目标从 discarded 变为 queued）。
- 配置：新增 `steering.queue_auto_drain`；`steering.queue` 仍默认 false——不开配置时行为与 S1 完全一致。
- 数据库：`tblLlmReactPendingInput` 新增 `payload_json` 列（存量环境需执行 init.sql 中的 ALTER 语句）。
- run 生命周期：run() 从单次执行变为"执行 + 自动续跑循环"；单个 run 的取消/超时/错误边界、事件协议、token 口径均不变。

## 4. 测试验证

- `go build ./...`：通过。
- `go test ./service/react/ ./service/tool/`：通过（新增 shouldAutoDrainQueue、pickPendingQueued 测试）。
- `bash scripts/check-docs.sh`：通过（26 篇受管文档 0 处问题）。
- 实测所用 WS 客户端保留于 `cmd/livetest/steering-*`（queue 场景用 `go run ./cmd/livetest/steering-queue`，取消降级用 `steering-fallback`，需服务已启动且对应配置开启）。
- 启动实测（`steering.enabled/queue/queue_auto_drain` 全开；deepseek-flash 模型）：
  1. **排队回执**：run 调用 ask_question 进入 `waiting_client_message` 后发送两条 run 消息 → 依次回执 `steer_queued {"kind":"queued","pendingInputId":"pend_8","queueLength":1}`、`...pend_9..."queueLength":2}`（HITL 等待不被打断，输入不丢）。
  2. **自动续跑 FIFO 链**：作答回来 run1 收敛后 → `steer_drained(pend_8)` → 自动开启 run2（新 runId）→ run2 收敛 → `steer_drained(pend_9)` → 自动开启 run3 → run3 收敛 done；全程同一 WS 连接。账本两行均 `status=guided`、`run_id` 分别归属 run2/run3；run2 最终回答以【队列A】开头、run3 以【队列B】开头——模型确实消费了各自的排队输入且顺序为 FIFO。
  3. **取消降级**：模型流进行中发送引导（回执 guided）后立即 cancel → `steer_delivery_changed {"count":1,"reason":"turn_ended"}`，账本行 `delivery=queue`、`status=queued`（非 discarded），且取消后无自动续跑（客户端等待 2s 无新 run 事件）——留给用户决定是否继续。
  4. **回归**：S1 的引导注入全链路（steer_guided → steer_drained → 下一模型轮消费）在 queue 关闭/开启两种配置下均复测通过；S1 验证过的 session_resumed 结算路径不受影响。
- 实测中发现并修复两个问题：① 队列项 payload 快照缺模型选择导致晋升后 run 校验失败（"modelKey 不能为空"）——准入时从被引导 run 回填默认模型；② gorm `First` 在空表时打 record not found 错误级日志（边界检查高频触发）——改用 `Limit(1).Find`。

## 5. 风险与兼容性

- **默认关闭**：`steering.queue` 未开启时排队/自动续跑/降级路径全部不生效，行为与 S1 一致；S1 未开启时与历史一致。
- **自动续跑烧钱面**：queue 开启且 auto_drain 开启时，用户排队 N 条即连续执行 N 个 run（每条一个模型任务）；run 出错/取消/超时会自然中断链条（暂停语义），但正常排队链条的消费没有二次确认——这是产品语义（对齐 ZCode queueAutoDrain 默认 true），需要保守些可设 `queue_auto_drain: false`。
- **续跑模型默认**：steer 消息不带模型选择时，晋升 run 使用被引导 run 的模型快照（随后仍按当前 caller/模型目录重新解析 API key）；若希望排队项用会话默认模型而非当前 run 模型，需在 S3 队列管理中补充编辑能力。
- **跨进程语义**：进程重启后上一进程遗留的 queued 行在下一次 createReactRunContext 时作废（session_resumed）；本进程内排队行跨 run 保留，直到被晋升或会话重启清理。
- **回滚**：`steering.queue: false` 即回到 S1 行为；payload_json 列对旧代码无影响（多余列可读）。
