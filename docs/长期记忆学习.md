# 长期记忆学习笔记

> 调研对象：本仓库（react-base-service）的长期记忆实现——`service/memory`、`service/react/memory*.go`、`service/graphmemory`、`models/llm/memory.go`、`controllers/http/react/memory.go`。
> 定位一句话：**双层跨会话记忆——Layer1 用 MySQL 存"偏好与约定"条目（常驻全文 + 目录按需读取 + 统一写核心审计），Layer2 用外部 Graphiti 存"实体关系与时序事实"（异步抽取、语义检索）；run 初始化时按作用域合并注入 system prompt，模型通过内置 Meta Tool 读写。**
> 与其他文档的关系：`docs/memory.md` 是设计文档（背景、原则、DDL、分期规划），`docs/system/memory.md` 与 `docs/system/graph_memory.md` 是系统功能基线，`docs/graphiti学习.md` 是 Graphiti 本体的调研。本文是**实现学习笔记**，关注"代码到底怎么存、怎么检索、怎么注入"，图均按当前代码绘制。
> 设计蓝本（摘自设计文档）：ChatGPT 的双层记忆思想 + Mem0 的事实化写入/检索 + Letta 的常驻核心记忆。

## 1. 心智模型：两层记忆

| | Layer1 Memory | Layer2 GraphMemory |
|---|---|---|
| 定位 | 偏好与约定层（用户称呼、业务口径、长期约定） | 时序事实图谱层（实体关系、历史事件、状态变化） |
| 存储 | MySQL 两张表 | 外部 Graphiti REST（基座零落库） |
| 生效 | 同步（写入即可见） | 异步（episode 受理后数秒~数十秒可检索） |
| 检索 | 目录索引 + memory_read 按需读取（无向量） | Graphiti 混合检索（向量 + BM25 + 图游走 + 时间窗） |
| 审计 | 不可变修订流水 + 回滚 | 无（受理即成功） |
| 冲突仲裁 | **以 `<memory>` 为准** | 注入块声明让位于 `<memory>` |

两条硬约定写进了工具描述与注入块文案：**两层冲突时以 `<memory>` 为准；偏好类写入用 `memory_write`，事件类才写图谱**。

## 2. 存储

### 2.1 Layer1 表结构（models/llm/memory.go）

`tblLlmMemoryItem`——记忆条目，一条 = 一条原子事实：

| 字段 | 说明 |
|---|---|
| `owner_type + owner_key` | 作用域：`caller` 或 `caller_user`（key 为 `callerKey\|userName` 拼接） |
| `layer` | `resident`（常驻）/ `detached`（按需），默认 detached |
| `title / content / description` | 标题 ≤32 字；正文 ≤500 字（一到三句原子事实）；description 是**检索提示** ≤512 字 |
| `tags` | 逗号分隔标签，`locked` 标签 = 人工钉死只读 |
| `item_key` | 内容语义指纹（见 2.2），与 owner 组成逻辑唯一键 `uk_owner_item` |
| `version / state` | 乐观锁版本号；`active/deleted` 软删 |
| `source / last_reason / created_by` | 来源 model/reflection/admin；最近修订原因；触发方（runID 或操作人） |

`tblLlmMemoryRevision`——修订流水：**不可变、只插不改**。每次 create/update/delete/rollback 追加一行 `before/after` JSON 快照 + 必填 `reason`；回滚 = 读目标修订的 `before` 快照反向提交新版本（`RollbackRevision`，service/memory/memory.go:446）。

### 2.2 内容指纹幂等（ItemKey）

```text
content ──规范化（去首尾空白/折叠连续空白/ASCII 小写）──► SHA-256 前 16 位 ──► item_key
```

同一事实排版略有差异（多空格、大小写）会得到相同 `item_key`。create 时先按 `(owner, item_key)` 查存量（**含软删**）：

- 命中 → **收敛为 update**（软删条目同时复活），reason 自动标注"create 命中同指纹条目，收敛为更新"，返回 `converged=true`；
- 未命中 → 正常新增（`mutateCreate`，service/memory/memory.go:217）。

效果：重复记忆在存储层天然去重，模型重复调用 `memory_write` 无副作用。

### 2.3 作用域模型

```text
allow_user_scope=false:  owners=[caller]                          写入→caller
allow_user_scope=true :  owners=[caller, caller_user]              写入→caller_user（默认目标）
```

- `caller` 空间是共享底座：该调用方全部会话可见；
- `caller_user` 空间是覆盖层：仅该用户会话可见，启用后作为默认写入目标；
- **读取合并时同 itemKey 恒取 caller_user**（`MergeRuntimeItems`，service/memory/runtime.go:51）——个人表述覆盖公共底座；
- 写入/读取前用 `AllowedKeys`（scope key 集合）逐条校验，越权整单拒绝。

### 2.4 统一写核心 ApplyMutation（唯一写入口）

三个写入来源（模型工具 / Reflection / 管理面）全部收敛到 `ApplyMutation`（service/memory/memory.go:148），保证审计链完整、无旁门写入：

```text
ApplyMutation
  │
  ├─ 1. 归一化：trim 各字段、NormalizeTags（切分/去空/去重）、layer 合法性
  ├─ 2. reason 必填且 ≤512 字（审计根，缺 reason 直接拒绝）
  ├─ 3. ScanSensitiveContent：7 类敏感形态正则扫描，命中即拒（见 2.5）
  ├─ 4. 开事务 GetLLMDB().Transaction
  │     ├─ create → mutateCreate
  │     │     ├─ 字段校验 + AllowedOwnerKeys 作用域校验
  │     │     ├─ ItemKey 查同指纹 → 命中则收敛为 applyUpdate(converged=true)
  │     │     ├─ checkLayerCap 容量守门（resident≤16 条 / detached≤500 条）
  │     │     └─ 插入 version=1 + createRevision("create", before=nil)
  │     ├─ update → mutateUpdate → applyUpdate
  │     │     ├─ loadItemForMutation（作用域校验 + RespectLocked 时 locked 只读）
  │     │     ├─ 乐观锁：expectedVersion>0 必须与当前 version 一致
  │     │     └─ version+1 + createRevision("update", before/after)
  │     └─ delete → 软删 state=deleted + createRevision("delete")
  └─ 5. 打点 MemoryWritesTotal{action,source,status} + RefreshMetrics（条数/字符量指标）
```

### 2.5 敏感信息拦截（内置 7 类形态）

| 规则 | 形态 |
|---|---|
| OpenAI 风格 API Key | `sk-` 前缀 ≥16 位 |
| AWS AccessKey | `AKIA` + 16 位 |
| GitHub Token | `gh[pousr]_` + ≥20 位 |
| JWT | `eyJ` 三段式 |
| 私钥文件 | `-----BEGIN ... PRIVATE KEY-----` |
| 身份证号 | 18 位（含校验位形态） |
| 手机号 | `1[3-9]` + 9 位 |

拦截口径是"整段形态匹配"不做语义判断，误伤由调用方改写表述后重试。工具描述里提前告知模型"含敏感形态的内容会被直接拒绝"，宁拒勿存。

### 2.6 Layer2 存储：外部 Graphiti，按 group_id 分区

基座侧只有一个瘦 HTTP 客户端（`service/graphmemory/client.go`：`Search`=POST /search、`AddEpisode`=POST /messages、`Healthcheck`），**不镜像图数据、不直连图数据库**。

- 分区：caller 级组做公共底座（`SanitizeGroupID(callerKey)`），`group_scope=caller_user`（默认）时追加 `caller__user` 组并把写入目标切到 user 组——与 Layer1 的 owner 两级作用域**同构**；
- `SanitizeGroupID`（scope.go:26）只保留 `[a-zA-Z0-9_]`（FalkorDB 全文检索解析器不接受连字符），清洗有信息损失时追加 8 位 sha256 后缀防碰撞，总长截断 64，空串回落 `default`；
- `group_ids` 由服务端按 run 作用域强制注入，**模型入参不暴露组概念**（防跨组越权检索）；
- 写入是 episode：`graph_memory_write` 只提供 name/content，组、来源描述（`react-base run <runID>`）、参考时间由服务端补齐；Graphiti 受理即成功（202），异步抽取实体/关系/带 `valid/invalid` 时间窗的事实。

## 3. 检索

### 3.1 Layer1：没有向量检索，是"目录 + 按需读取"

设计上把向量检索排在 P4（`docs/memory.md` 待实施项）。当前方案完全靠**结构化索引**控制 token：

| 工具 | 行为 | 限制 |
|---|---|---|
| `memory_list` | 列当前作用域索引（itemId/title/description/tags/layer），**不含正文**；可按 layer/tag/keyword 过滤 | 默认 20 条、上限 50；默认查 detached 层 |
| `memory_read` | 按 `itemId` 读全文（正文/版本/来源/最近修订原因） | 一次最多 10 条；**逐条校验作用域，任一条越权整单拒绝**（防跨用户探测） |

keyword 匹配是 title+description+tags 的**包含匹配**（`RuntimeItemMatchesKeyword`，转小写后 Contains），不上索引不上向量——条目量级受 detached≤500 守门，全量拉回内存过滤即可。

**关键巧思：`description` 在工具定义里就叫 `retrievalHint`（"检索提示：什么场景需要想起这条记忆"）**——写的时候就强制模型给出"何时该想起我"，读的时候它就是目录里展示的那一行。检索质量在写入时就被决定了。

### 3.2 Layer2：语义与时序检索

`graph_memory_search` 用自然语言查询（`query` 必填，limit 默认 10、上限 30），返回 `facts[]{fact, name, validAt, invalidAt}`，时间裁到日期。Graphiti 内部是向量 + BM25 + 图游走 + 时间过滤的混合检索（详见 `docs/graphiti学习.md`），适合"A 和 B 什么关系""过去发生过什么""状态什么时候变的"这类问题。返回可能包含**已失效的历史事实**，靠时间窗区分。

## 4. 注入上下文

### 4.1 注入总流程（run 初始化，一次性完成）

```text
POST /react/run
  ▼
prepareRuntimeRequest（runtime.go:470-483）
  │  （前面已装配 systemPrompt / skills / tools / agents）
  │
  ├─ Layer1：memory.enabled？
  │    └─ 是 → BuildRuntimeContext（service/memory/runtime.go:142）
  │         ├─ ResolveRuntimeScope：owners=[caller(, caller_user)]
  │         ├─ FindActiveMemoryItemsByOwners：两个空间一次查全 active
  │         ├─ MergeRuntimeItems：同 itemKey caller_user 覆盖 caller；
  │         │                    结果按 updated_at 倒序
  │         └─ RenderRuntimeContext：分层渲染（见 4.2）
  │         ★ 查询出错 → 返回 err，run 启动失败（Layer1 是依赖）
  │
  ├─ Layer2：graph_memory.enabled && inject.enabled？
  │    └─ 是 → buildGraphMemoryContextForRun（graph_memory.go:199）
  │         ├─ query = 本次 UserPrompt（拿用户输入当检索词）
  │         ├─ 独立超时预算 inject.timeout_ms=1500ms（不占用主链路）
  │         ├─ client.Search(scope.Groups, query, max_facts=8)
  │         └─ renderGraphMemoryContext：每事实一行 + 双预算截断
  │         ★ 失败/超时/空结果 → 返回 ""（token 零增量，绝不阻塞 run）
  ▼
buildInitialMessages → buildReactSystemContent（runtime.go:663）
  system = systemPrompt + 工具索引摘要 + 技能索引摘要
           + <memory> + <graph_memory>    （非空块以 \n\n 拼接）
  ▼
进入 LLM 工具循环；子 Agent 委派（delegate.go:255）携带同一份注入
```

**两层的失败语义刻意不同**：Layer1 是记忆本体，查不到就别启动（fail fast）；Layer2 是增强，"注入是增强不是依赖"，图谱挂了最多少点背景事实。

### 4.2 `<memory>` 块长什么样（按 RenderRuntimeContext 逻辑还原）

```text
<memory>
## 长期记忆（自动维护）

### 常驻
- [用户称呼] 希望被称为"老王"，沟通风格偏简洁
- [输出格式] 评审结论用中文，按 P0/P1/P2 分级
（另有 1 条常驻记忆超出字符预算未注入，可用 memory_list 查看）

### 记忆目录（需要时用 memory_read 按 itemId 读取全文）
- #42 [主体信息] 涉及合同条款时注意用户使用香港主体
- #57 [技术栈] 团队主力语言 Go + React，不推荐 Python 方案
（另有 3 条记忆未列出，可用 memory_list 检索）

记忆使用纪律：以上内容自动维护、可能过时；与用户当前表述冲突时以用户为准，并用 memory_write 修正。
</memory>
```

预算机制：常驻层 `resident_budget_chars=2000` 字符预算（超出条目计数提示）；目录最多 `index_max_items=64` 行。**尾部的"使用纪律"是固定文案**——明确告诉模型记忆可能过时、冲突以用户为准、发现错误要主动修正。

### 4.3 `<graph_memory>` 块（按 renderGraphMemoryContext 逻辑还原）

```text
<graph_memory>
## 相关历史事实（自动检索，可能过时或已被新事实取代，注意时间窗；深挖用 graph_memory_search；与 <memory> 冲突时以 <memory> 为准）
- [供应商] 甲公司是老王的供应商（2025-11-01 ~ 2026-06-30）
- [签约主体] 老王使用香港主体签约（2026-03-12 ~ 未知时间）
</graph_memory>
```

每条事实一行：关系名 + 事实 + 有效时间窗（空端点显示"未知时间"），`max_facts=8` 条 + `max_chars=1200` 字符双预算，超出提示改用 `graph_memory_search`。

### 4.4 注入的运行时门控

- 是否暴露记忆工具由 `ExecutionProfile.AllowMemory / AllowGraphMemory` 二次校验；
- reflection 子 run 的 profile 只有 `AllowMemory=true`——工具面被裁到只剩 memory 三件套；
- 记忆为空时渲染空串，system 拼接跳过空块（token 零增量）。

## 5. 写入的三条路径

```text
写入来源                          统一写核心                    存储
────────────────                ────────────────            ──────────────
① 主对话模型调              ┌──►                          MySQL 事务
   memory_write             │    ApplyMutation     ┌──►  tblLlmMemoryItem
   source=model             │    （归一化/校验/     └──►  tblLlmMemoryRevision
                            │     敏感拦截/乐观锁/
② Reflection 整理写 ────────┤     容量守门/审计流水）
   source=reflection        │
   + 写入限额 + locked 只读   │
                            │
③ 管理面 /react/memory/* ───┘
   source=admin（可回滚，不受 locked 约束，保留人工最终干预权）

   另：graph_memory_write ──────► AddEpisode ──► Graphiti 异步抽取（不走 ApplyMutation）
```

### 5.1 模型主动写（在线）

`memory_write`（service/react/memory.go:86）的参数即纪律：`action` 必填、`reason` 必填、update 可带 `version` 乐观锁、`retrievalHint` 必填。工具描述本身写得很克制："只记稳定事实与明确偏好，不记一次性任务上下文，宁可少写不写错"。

### 5.2 Reflection 自动整理（离线，service/react/memory_reflection.go）

```text
主会话 run（上下文超水位 → 压缩）
  ▼
compact_end 事件 ──► maybeTriggerMemoryReflection
  │ 判定（任一不满足即静默退出，绝不阻塞主会话）：
  │   memory.enabled && reflection.enabled（默认关，灰度开）
  │   会话类型 ≠ reflection        ← 防自触发
  │   压缩摘要非空
  │   会话级冷却 cooldown_minutes=60（进程内表，重启丢失可接受）
  ▼ 通过
异步 goroutine（context.Background：生命周期独立于触发它的 WS 连接；
                headless gin ctx 显式注入 userName）
  ▼
reflection 子 run（type=reflection，maxSteps=12）
  │ 用户提示词 = <memory_reflection_task> 五阶段指令
  │  + 压缩摘要 + 被压缩对话原文转录（单条 800 字截断、总量 16000 字）
  ▼
五阶段整理：
  1 Investigate  memory_list(layer=all) + memory_read 看现有记忆全貌
  2 Extract      列候选动作：create / update / 重复合并 / 过期淘汰（宁可不动）
  3 Update       逐条 memory_write，必填 reason；时间敏感事实加「截至 YYYY-MM-DD」
  4 Review       memory_list 复查矛盾、重复与常驻层预算
  5 Commit       一段话总结（做了什么/为什么/放弃了什么）后结束
  │
  ├─ 安全阀：max_writes_per_run=20 限额（引擎侧计数，超限直接报错终止写入）
  ├─ locked 标签条目只读（RespectLocked=true，写核心二次拦截）
  └─ source=reflection，CreatedBy=runID → 同一 ApplyMutation 落库
  ▼
失败 → 静默重试 1 次 → 终态打点 react_memory_reflection_total{status}
（事件流照常持久化，回放页可查；实时事件被 headless writer 丢弃）
```

设计上最值得注意的一点：**Reflection 的触发原材料是"被压缩掉的对话"**——压缩摘要 + 被压缩原文在内存里直接持有，无需回库取，等于把"上下文淘汰"变成了"记忆沉淀"的信号源。

### 5.3 管理面（controllers/http/react/memory.go）

6 个接口：`list / create / update / delete / revisions / rollback`，走同一写核心（source=admin）。与模型路径的差异：不受 locked 约束（保留人工最终干预权）、支持查修订流水与按修订回滚。

## 6. 安全与权限设计汇总

| 机制 | 落点 |
|---|---|
| 作用域校验 | 读：逐条 AllowedKeys 校验，越权整单拒绝；写：create/update/delete 前校验目标空间 |
| 跨用户覆盖 | 同 itemKey 合并时 caller_user 恒覆盖 caller（个人 > 公共） |
| 敏感拦截 | 7 类形态正则，唯一写入口统一拦截，命中即拒 |
| 乐观锁 | version 不匹配报冲突，防并发覆盖 |
| locked 标签 | 人工钉死条目对 Reflection 只读；管理面不受限 |
| 容量守门 | resident 16 条 / detached 500 条，防记忆爆炸稀释注入 |
| 防滥用 | memory_read ≤10 条/次、memory_list ≤50 条/次、reflection 写入限额 + 冷却 + 防自触发 |
| 图谱越权 | group_ids 服务端强制注入，模型不感知组概念 |

## 10. 设计取舍与值得借鉴的点

1. **"目录 + 按需读取"替代向量检索**：detached 条目只注入一行索引，正文由模型自主 `memory_read`。在条目量 ≤500 的守门下，检索简单可解释、零外部依赖；代价是依赖模型主动想起来（retrievalHint 质量决定一切），规模化要等 P4 向量检索。
2. **写入侧收敛一切**：三个来源一个写入口，敏感拦截、幂等指纹、乐观锁、审计流水只实现一次。任何新入口（如未来的定时整理）免费继承全部安全性质。
3. **检索线索前置到写入时**：`retrievalHint`（description）必填，把"什么时候需要想起这条记忆"作为一等公民存下来，而不是检索时再猜。
4. **两层失败语义分离**：本体（MySQL）fail fast，增强（Graphiti）fail silent——外部依赖的可用性等级直接映射到注入策略。
5. **把上下文压缩当作记忆信号**：compact_end 的"被淘汰内容"恰好是值得沉淀的近期对话，Reflection 顺流而下；配合冷却/限额/locked/防自触发四重安全阀，后台自治任务不会失控。
6. **记忆自我声明不可信**：注入块固定文案"可能过时、冲突以用户为准、发现错误用 memory_write 修正"——把纠错责任和纠错工具一起交给模型。
7. **软删 + 不可变流水**：当前态可变、历史态只增，回滚是"用旧快照提交新修订"而非破坏性恢复，审计链永不断裂。
