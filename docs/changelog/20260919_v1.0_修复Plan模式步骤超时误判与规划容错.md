# 修复 Plan 模式步骤超时误判与规划容错

## 1. 背景与目标

Plan Runtime 上线当日以真实模型 + 真实工具做了六场景 E2E（[测试报告](../plan模式E2E测试报告.md)），
控制流场景全部通过，但重型步骤任务暴露出一组执行鲁棒性缺陷。本次修复其中可归因的五项
（报告 §6 P1/P2/P3/P6/P7/P8），并顺带修复一个测试中发现的存量缺陷。

### 问题描述

1. **步骤超时被误判为用户取消（P1，高危）**：默认 600s 步骤超时若落在**工具执行阶段**，
   中断错误被包装为 `context.Canceled`，`IsCancellation()` 将其判为取消——当前步骤置
   CANCELLED（"步骤已取消"）、整个 Plan 级联 CANCELLED（"用户取消了 Plan"）。实测证据
   `plan_exec_b373129c…`：步骤 3 attempt 19:23:49→19:33:49 恰 600s 整被级联取消，
   后续 2 个 PENDING 步骤一并陪葬。
2. **Planner 偶发非法 stepKey 判死 Run（P2）**：模型漏填 stepKey（约 10 次规划出现 1 次），
   `validateDraft` 直接报 `invalid stepKey ""` → `planner_failed`，用户只能整体重发任务。
3. **步骤超时不可配（P3）**：`timeoutSeconds` 不在 `submit_plan` Schema 中，重型步骤
   （深度检索/大规模计算）必撞 600s 默认上限，叠加 P1 后必然失败或被误取消。
4. **Plan FAILED 后续步骤停留 PENDING（P8）**：与取消级联（D3）不对称，公开视图出现
   "已失败但还有待执行步骤"的矛盾状态。
5. **跨步骤数据消费与工具预算缺指引（P6/P7）**：模型把 result_ref 引用本身塞进
   python_exec 入参反复试错（实测两轮 600s 全耗在传参诊断）；无预算约束时单轮并发
   111 个工具调用、全程 391 次 `repo_list_files` 穷举直至超时。
6. **存量缺陷（测试新发现）**：失败路径把外层 run 置 `error`，而 `restoreForCommand`
   的状态守卫拒绝 error 态外层 run——`Retry`/`Skip`（作用于 FAILED Plan）永远进不了执行。

### 根因分析

- P1：`executor.runAgentStep` 的取消判定只看 `runErr` 的错误链
  （`reactService.IsCancellation(runErr) || errors.Is(runErr, context.Canceled)`）。
  截止落在工具执行阶段时，HTTP/引擎层把中断包装为 `context.Canceled`，与真实用户取消
  无法区分；而 `executor.go` D4 注释（"DeadlineExceeded 不属于取消语义"）与文档描述的
  正是未生效的设计意图。模型流读取阶段的超时错误保留 `DeadlineExceeded`，因此走对了
  Attempt 失败路径——同一缺陷两种表现，取决于截止时刻所处阶段。
- 存量缺陷：`failExecution` 调 `MarkExternalRunState(error)`，`retryStepAndContinue`/
  `skipStepAndContinue` 只复位 Plan 与步骤，不复位外层 run，随后 `restoreForCommand`
  在 `run.State == error` 分支直接拒绝。
- P2/P3/P8：分别为校验策略（一错即弃）、Schema 缺字段、终态级联不完整。

### 影响范围

所有 `executionMode=plan` 的 Run：超长步骤任务（单步 >600s）此前几乎必然失败或被误取消；
失败后的 Retry/Skip 命令此前不可用；失败计划的历史视图存在矛盾状态。

## 2. 代码改动

- 文件：`service/plan/executor.go`
  - **超时与取消分类**：`RunScopedStep` 返回后、进入取消判定前，先读
    `stepCtx.Err()`——`DeadlineExceeded` 即步骤超时（context 包"先发生者为准"，
    是区分"步骤超时"与"父级/用户取消"的权威信号），超时强制走 Attempt 失败路径，
    且错误摘要统一标注「步骤超时（上限 N 秒）」。
  - **Step Prompt 增强**：result_ref 消费范式（读到数据写字面量、不传引用本身）与
    工具调用预算约束（禁止无边界穷举）。
- 文件：`service/plan/state.go`
  - **stepKey 自动修复**：非法/重复 key 按 name（其次按序号）确定性推导合法 key 并去重
    （`repairStepKey`/`deriveStepKey`），线性依赖自动补链引用修复后的 key。
  - **TimeoutSeconds 草稿字段**：`PlanDraftStep` 新增字段，AGENT 步骤钳制到
    [60, 3600]、USER_* 步骤固定 0（`clampStepTimeoutSeconds`）。
- 文件：`service/plan/planner.go`
  - **Schema**：`submit_plan` 步骤属性新增 `timeoutSeconds`（integer, 60–3600）。
  - **提示词**：新增规则——预计单步明显超过 10 分钟的重型步骤应显式设置 timeoutSeconds。
  - **规划重试**：`generateDraft` 失败自动重试（单 Run 最多 3 次规划尝试，逐次记日志）。
- 文件：`service/plan/runtime.go`
  - `failExecution` 级联：置 FAILED 前调用 `cancelPendingSteps`，后续 PENDING 步骤
    批量置 CANCELLED（"Plan 失败，后续步骤未执行"），与 D3 同理不留孤儿行。
- 文件：`service/plan/repository.go`
  - **持久化**：`persistInitialDraft` 写入 `TimeoutSeconds`（列已存在，此前从未写入）。
  - **Retry 复活**：`retryStepAndContinue` 事务内把该步骤之后被失败级联置 CANCELLED 的
    步骤一并复位 PENDING（FAILED Plan 内 CANCELLED 步骤仅可能来自失败级联，无需标记区分）。
  - **reviveOuterRun（新增）**：Retry/Skip 事务内把外层 run 复位 `running`、清空
    error_message，与计划状态变更保持原子，解锁被状态守卫拒绝的命令。
- 文件：`service/plan/state_test.go`：新增 6 个用例（stepKey 修复/去重、超时钳制、
  Schema 暴露 timeoutSeconds 等，连同既有 5 个用例覆盖校验全分支）。
- 文件：`docs/system/plan.md`：升 v1.1——接口清单标注 WS 控制命令适用窗口（报告 P4）、
  规划容错与 timeoutSeconds 说明、超时分类与失败级联行为、历史版本表。

## 3. 影响范围

- 接口：WS/HTTP 控制命令行为不变；`submit_plan` 虚拟工具 Schema 新增可选属性
  `timeoutSeconds`（对模型可见，客户端无感知）。
- 数据库：**无 DDL 变更**。`tblLlmPlanStep.timeout_seconds` 列自 `plan_runtime_v1.sql`
  起已存在，本次开始真正写入；失败级联会为 FAILED Plan 写入 CANCELLED 步骤行
  （读取方按终态处理，无兼容问题）。
- 配置：不新增 YAML 配置项。
- 模型调用：规划失败自动重试至多 2 次额外调用（仅在失败时发生）。
- 未修复（留二期）：客户端断连期间 RUNNING 步骤按失败烧尽重试（报告 P5，Durable
  Runtime 范畴）。

## 4. 测试验证

- `go build ./...`、`go vet ./service/plan`：通过。
- `go test ./service/plan`：11 个用例全部通过（含新增 6 个）。
- `go test ./...`：全量通过。
- 超时链路 E2E（`tests/plan-e2e`，场景 t7）：任务要求步骤 `timeoutSeconds=60` 执行
  `time.sleep(90)`——DB 落库 `timeout_seconds=60`；两次 Attempt 错误摘要均为
  「步骤超时（上限 60 秒）」且第 2 次为自动重试；Plan 终态 **FAILED**（修复前为
  CANCELLED）；后续步骤级联 CANCELLED；HTTP Retry 后该步骤新建 Attempt 续跑、
  后续步骤复位 PENDING、外层 run 复位 running（修复前 Retry 直接被拒）。结论 PASS（166s）。
- 回归：S2 USER_INPUT 等待/WS 恢复 PASS（438s）；S4 运行中取消 PASS（71s）。
- `bash scripts/check-docs.sh`：20 篇受管文档 0 问题。

## 5. 风险与兼容性

- 行为变化：单步超时的 Plan 终态由 CANCELLED（误判）变为 FAILED+可 Retry——依赖旧
  （错误）终态的下游逻辑需知晓；公开视图上失败计划不再显示 PENDING 步骤。
- `errors.Is(stepCtx.Err(), DeadlineExceeded)` 依赖 context "先发生者为准"语义；
  步骤超时与用户取消几乎同时到达时二者取先到者，均可自洽。
- 规划重试最多 3 次模型采样：极端情况下单次 Run 规划阶段 token 消耗增至 3 倍
  （仅前两次失败时发生，且避免了整体重发任务的更大浪费）。
- stepKey 自动修复为确定性推导（name 规范化/序号兜底），不改变已合法 key；
  若计划消费方对 key 有额外语义约定，推导值可能与模型本意不同（可从 PlanVersion
  的 InputJSON 还原原始输出）。
- 回滚：改动集中在 service/plan 五个文件，revert 即可，无数据迁移。
