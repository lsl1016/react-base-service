# 代码工作区共享化改造方案（已实施）

- 日期：2026-10-04（方案设计）；2026-10-05 实施完成，全量测试通过（`go build ./...` + `go test ./...` 39 包零失败，workspace 包含 -race 通过）
- 状态：**已实施**；共享粒度 run → (service, commit)，修复 1 个并发竞态（P0）+ 1 个存量 bug（P1）。与方案的差异见 §七「实施偏差记录」
- 相关代码：`service/workspace/workspace.go`、`service/mcpclient/manager.go`（未改，仅复用语义）、`service/react/load_runtime_code.go`、`service/agent/builtin.go`、`controllers/http/react/workspace_view.go`、`sql/init.sql`（tool_id 列加宽）、`service/react/internal/e2e/workspace_e2e_test.go`

## 一、背景与问题

当前工作区是"每 run 专属"模型：`load_runtime_code` → `workspace.Manager.Load(runID, callerKey, service, env)`
（`workspace.go:102`），每个 run × 每个 service 分配独立 git worktree（`<root>/<runID>/<service>`，
`workspace.go:138`），幂等仅在**同一 run 内**成立（`workspace.go:117`）。repo-mcp 子进程无预索引、
`Repo` 结构不可变（`repotools/repo.go:16`），工具整体只读（`manager.go:69-80`），但分配粒度没有利用
这些共享条件。

### 1.1 并发竞态（P0）：MCP server 名不带 runID

`serverName = "ws_" + service`（`workspace.go:149`），而 `mcpclient.EnsureServer` 对同名 server 是
**替换语义**——新起子进程后 `Stop()` 旧的（`manager.go:298-314`）。用户 A、B 并发加载同一 service 时：

1. **B 的 Load 杀掉 A 正在用的子进程**，换成指向 B worktree 的实例；
2. **A 的后续检索静默错位**：工具调用按名字取当前 client（`manager.go:362`），A 再调 `ws_X_*`
   实际打到 B 的 worktree。两次 Load 之间 mirror fetch 推进了 HEAD、或两人 env/ref 不同时，
   A 读到的是 B 的 commit 快照——不报错，数据是错的；
3. **A 先结束误杀 B**：A 的 `ReleaseRun` → `RemoveServer("ws_X")`（`workspace.go:232`）杀掉 B
   在用的子进程，B 后续检索全部报 "mcp server is not configured/running"。工具注册表按 caller
   清理所以 B 的工具条目还在，但 server 已不存在。

### 1.2 存量 bug（P1）：同 caller 并发 run 误删工具副本

`release` 里 `RemoveRegistryToolsForCaller(server, callerKey)`（`workspace.go:229`）按 caller 而非
按 run 清理：同一 caller 开两个并发会话、都加载了同一 service 时，**第一个 run 终态就会把该 caller
名下全部 `ws_*` 工具副本删掉**，第二个 run 的模型立刻丢工具。

### 1.3 性能问题（P2）

- `Load` 全程持有 Manager 全局互斥锁（`workspace.go:115`），锁内含 git fetch 网络耗时——所有用户
  所有加载完全串行；
- `ensureMirror` 每次 Load 都 `git fetch --prune`（`workspace.go:279`），并发加载同仓库重复走网络，
  且裸并发 fetch 同一 mirror 会抢 git `.lock` 报错（现状被全局锁掩盖）；
- 每 run 每 service 一份 worktree + 一个 MCP 子进程，尽管 mirror 对象库本身已是全局共享。

## 二、目标与原则

把共享粒度从 **run** 提升到 **(service, commit)**：同一 commit 的检索工作区（worktree + repo-mcp
子进程）全局只加载一份，多 run / 多 caller 引用计数共享；run 结束只减计数。

- 模型侧协议不变：`load_runtime_code` → `get_tool` → `execute_tool` 两段式；入参出参结构不变；
- 只读语义不变：无写工具，共享 worktree 无并发写风险（这是共享安全的前提，已具备）；
- `mcpclient` 包零改动：`EnsureServer` 的同名替换语义保留给管理面连接场景（显式更新配置的合理
  语义），工作区侧因名字带 commit 不再触达它。

## 三、改动方案

### 3.1 核心重构：`service/workspace/workspace.go`

数据结构：引入共享条目，Manager 索引改两层：

```go
// wsEntry 是一个 (service, commit) 粒度的共享工作区实例。
type wsEntry struct {
    key        string          // service + "@" + commit
    service    string
    commit     string
    ref        string          // 解析来源 ref（展示用）
    worktree   string          // <root>/<service>/<commit12>
    serverName string          // ws_<service>_<commit8>，名字带 commit 天然唯一
    mu         sync.Mutex      // 序列化本条目冷启动（worktree add + EnsureServer + 首次工具同步）
    holders    map[string]int  // callerKey → 该 caller 名下活跃 run 数
}

type Manager struct {
    mu      sync.Mutex
    entries map[string]*wsEntry    // 活跃共享实例
    runRefs map[string][]*wsEntry  // runID → 持有的 entries（ReleaseRun 索引）
    fetchMu map[string]*sync.Mutex // mirrorPath → fetch 互斥
}
```

**Load 流程**（`workspace.go:102` 改造）：

1. 参数校验、`Resolve` 不变；`ensureMirror` + `resolveCommit` 得到 commit。**每次仍 fetch**，
   保持"每次加载解析最新 commit"的现有语义（成本与现状持平；共享省的是 worktree / MCP spawn /
   重复 fetch）。fetch 用 `fetchMu[mirrorPath]` 串行化同一仓库，不同仓库并行；
2. 全局锁下按 `key` 查 `entries`：
   - **热路径（命中）**：`holders[caller]++`、登记 `runRefs`，锁外做一次
     `SyncServerRegistryScoped(callerKey, serverName, false)`（每个 caller 仍需自己的工具副本）。
     零 git 操作、零 MCP spawn——并发用户秒级复用的来源；
   - **冷路径（未命中）**：新建 entry，在 **entry 自己的锁**内做双重检查后：
     `worktree add --detach`（残留时 remove --force 重试，与现状一致——冷路径意味着 holders 为空，
     强删安全）→ `EnsureServer`（名字带 commit，不存在顶替别人）→ 工具同步；
3. git / MCP / 网络 IO 全部在**全局锁外**：不同 service 的加载完全并行。

必须做对的两个细节：

- **per-mirror fetch 锁**：`git fetch --mirror` 并发抢 `.lock` 会直接报错；
- **Release 拆两级**（`workspace.go:227` 改造）：`ReleaseRun(runID)` 对每个 entry——先
  `holders[caller]--`，**caller 归零才** `RemoveRegistryToolsForCaller(server, caller)`（修 §1.2）；
  **总归零才** `RemoveServer` + `worktree remove` + 删目录 + 从 `entries` 摘除。幂等保持
  （`runRefs` 已删则空操作）。

### 3.2 工具名带 commit 后必须同步的点

1. **`load_runtime_code.go:55`（必改，不改就出错）**：返回给模型的工具名串目前硬拼
   `"ws_" + alloc.Service + "_..."`，server 名带 commit 后必须改用 `alloc.MCPServerName` 拼接；
2. **提示词文案**：`load_runtime_code.go:27`、`agent/builtin.go:106,110` 里的 `ws_<service>_*`
   表述改为 `ws_<服务>_<commit短哈希>_*`，并注明"以 load_runtime_code 返回的 tools 字段为准"
   ——模型实际按返回 JSON 取名字，描述不能误导它手拼；
3. **`ActiveSnapshot`（`workspace.go:205`）与 `workspace_view.go`**：展示结构增加 holders
   （callers、引用 run 数），swagger 注释同步，管理面能看到共享实例被谁引用。

### 3.3 明确不动的东西

- `mcpclient` 包零改动；
- `cleanupOrphans`（`workspace.go:355`）语义不变：进程重启 = 所有 run 已终态 = 无活跃引用，
  整目录清空依然正确；
- repo-mcp / repotools 零改动：`Repo` 不可变无状态，单进程可安全服务多 run 并发调用；
- `ensureMirror` 的 fetch 语义不变（可选后续加 TTL，见 §六）。

## 四、测试计划

新增 `service/workspace` 单测（本地小仓库 fixture，不起网络）：

1. 两个 run 并发 Load 同 service 同 ref → 只有一个 worktree、一个 server、两份 caller 工具副本；
2. 同 service 不同 env（不同 ref/commit）→ 两个 entry 并存，互不干扰；
3. 其一 ReleaseRun → server / worktree / 另一 caller 工具全部还在；双方 Release → 全清；
4. 同 caller 两个 run 先 Release 一个 → 该 caller 工具副本仍在（§1.2 修复回归）；
5. 并发 Load 不同 service 不互相阻塞（锁粒度回归）。

e2e（`workspace_e2e_test.go`）基本兼容：单 run 场景 run 结束 refs 归零仍全清，"根目录为空 /
ws_ 工具清理"断言不变；工具名前缀断言 `strings.HasPrefix(name, "ws_react-base-service")` 仍命中。

## 五、风险

- **工具名 / toolID 变长**：`mcp_ws_<service>_<commit8>_<tool>__<callerKey>`，实施前确认
  `tblLlmTool.tool_id` / `name` 列宽；commit 取 8 位足够且长度可控；
- **entry 泄漏**：ReleaseRun 调用点已全部挂上（`runtime.go:242`、`external_runtime.go:292`、
  `delegate.go:209,324`），run 终态收尾必经；进程重启由 `cleanupOrphans` 兜底；
- **per-mirror 锁不可省**：否则并发 fetch 直接报 lock 错误（全局锁拆掉后暴露）。

## 六、实施顺序

1. `workspace.go` 重构（entry / refcount / 锁粒度）+ `executeLoadRuntimeCode` 工具名修正 +
   `ActiveSnapshot` 扩展（一个提交，功能完整）；
2. 提示词与描述文案更新（`load_runtime_code.go`、`agent/builtin.go`）；
3. 单测 + e2e 验证；
4. 可选后续：fetch TTL（share-hit 免 fetch，进一步省网络）；共享命中率 / 冷启动耗时 metrics。

## 七、实施偏差记录（2026-10-05 回填）

按 §六 顺序一次实施完成，与方案的差异：

1. **tool_id 列宽确认为实际约束并已加宽**：`mcp_ws_react-base-service_<commit8>_list_repositories__<callerKey>`
   最长约 86 字符，超出 `VARCHAR(64)`。`sql/init.sql` 已把 `tblLlmTool` / `tblLlmToolUserPolicy` /
   `tblLlmMcpAppTool` 三处 `tool_id` 加宽到 `VARCHAR(128)`，并按文件惯例追加存量环境 ALTER 语句
   （部署存量库时需执行）；`name VARCHAR(128)` 实测最长 48 字符，无需加宽。
2. **mcpclient 触点抽成包内变量**（`ensureRepoServer` 等 4 个，默认直连 `mcpclient` 包函数）：
   单测用替身注入，与 `pyexec.pythonExecArtifactUploader` 同一模式；`mcpclient` 包本身零改动（符合方案）。
3. **热/冷路径统一走 `ensureStarted()`**：方案里热路径与冷路径分支描述不同，实现统一为
   "登记 → ensureStarted（started 双检，entry.mu 序列化冷启动）→ 同步 caller 工具副本"，
   冷启动期间的并发加载方在 entry.mu 上等待而非各触 EnsureServer，天然不会触发同名替换。
4. **同 run 同 service 幂等在解析前后各查一次**：第二次查防"解析期间同 run 已加载"导致的
   双计数（run 内工具串行，属防御性双检）。
5. **§四.5 锁粒度回归以并发正确性断言替代时序断言**：时序断言（"不同 service 不互相阻塞"）
   易 flaky，改为 `TestConcurrentLoadSingleColdStart`（8 并发混合 caller/run：全部成功、冷启动
   恰一次、计数精确、全部释放后目录清空），fetch 锁路径已被覆盖。
6. **`ActiveAllocation` 重命名为 `ActiveEntry`**：视图模型从"run 分配"变为"共享实例"，
   语义变了保留旧名反而误导；仅 `workspace_view.go` 一处外部引用，已同步 swagger 注释。
7. **新增回归闸**：`TestLoadSameRunIdempotent` 末尾断言"单次 ReleaseRun 后立即回收"，
   防止幂等路径未来被改成双计数后静默泄漏 entry。
8. **终审时补掉一个实施中引入的回收竞态**：ReleaseRun 在锁内决定 teardown 并摘除 entry，
   物理回收在锁外执行——该窗口内新 Load 会新建同 key entry 并重建**同一路径**的 worktree，
   与旧实例的 `worktree remove` 交叉执行。修复：`Manager.keyMu`（entry key → 生命周期锁，
   跨 entry 对象）让 `ensureStarted` 与 `teardown` 串行；锁条目不随 entry 回收删除（删锁与
   持锁等待方有竞态），数量以不同 (service, commit) 组合为界。
9. **文档同步范围**：`docs/architecture.md` 3 处（工具表与四件套描述）、e2e code-agent
   提示词（原文写死旧工具名，模型会 get_tool 失败）、todo 本文档状态头。
   §六.4（fetch TTL、metrics）未做，留作后续。
10. **server 名 32 字符上限显式化**：`mcpclient.validateServerName` 限 1-32 字符，
    `ws_<service>_<commit8>` 隐含 service ≤ 20 字符（react-base-service=18 贴上限）。
    `Load` 在解析后前置校验并给出可读错误，替代挂载阶段的晦涩失败。
11. **共享实例并发调用安全性确认**：改造后多 run 并发调用同一个 stdio repo-mcp 进程，
    `mcpclient.Client` 按设计支持——请求在 `c.mu` 下串行化（与 stdio 单线程模型一致），
    pump goroutine 按 JSON-RPC id 分发响应（client.go:98-100），共享只是排队而非竞争。
12. **新增真实链路集成测试**：`service/workspace/workspace_integration_test.go`
    （`WORKSPACE_IT=1` 门控，与 e2e 同一惯例）。真实 clone 两个开源仓库
    （sirupsen/logrus、google/uuid，uuid 另用 v1.0.0 tag 模拟不同 env），
    真实拉起 `bin/repo-mcp` 子进程走 stdio JSON-RPC，仅桩掉 DB 注册表同步。
    覆盖：双会话共享单实例、双 commit 并存隔离、8 路并发 Load + 8 路并发 search_code
    打同一共享 server、逐个释放至最后持有者才回收、回收后重建。
    运行：`go build -o bin/repo-mcp ./cmd/repo-mcp && WORKSPACE_IT=1 go test ./service/workspace/ -run TestWorkspaceSharingIntegration -v -count=1 -timeout 600s`。

验证：`go build ./...` 通过；`go test ./... -count=1` 39 包全部通过；`go test ./service/workspace/ -race`
通过（含新增 5 类场景单测）；集成测试（12 条）单跑与 `-race` 均通过——10 次加载共享 3 个实例
（3 次冷启动 + 回收后重建 1 次），全部实例回收，commit 隔离正确。e2e（`REACT_DELEGATE_E2E=1`）
未在本次跑（需真实模型与白名单配置），其断言（根目录清空、`ws_react-base-service` 前缀命中）
