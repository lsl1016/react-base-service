# 非对称信息多智能体场景分析：适配评估与通信模型选型

> 起因：讨论"当前运行时适合完成某一个具体功能/任务，但类似狼人杀、多人辩论这种各参与者视野和世界观不同的多智能体场景是否合适"，延伸出"这类场景是否需要做子 Agent 间通信"的设计选型问题。
> 结论先行：现运行时是**主-从编排（orchestration）**模型，不是**对等多方（peer）博弈场**模型——前者适合"单任务执行 + 委派编排"，后者需要补一层"房间中介"；而**子 Agent 间直接通信管道是明确不需要的**（§4）。
> 定位：思路分析与设计选型固化。是否投入属于产品定位问题（从"任务执行器"扩展成"多方博弈场"），应由具体业务场景驱动。
> 后续：2026-10-01 已开独立孵化目录 `../agent-arena` 承接本方向的落地（设计期，代码零落地），本文为其上游分析。

## 1. 一页结论

| 问题 | 结论 |
|---|---|
| 现运行时能否直接跑狼人杀/多人辩论？ | **不能**。会话模型、消息模型、路由机制都假设"单一对话方"（§3 四个缺口） |
| 差距是推倒重来级别吗？ | **不是**。子 Agent 声明、上下文强隔离、父子窄通道、按 run 重建上下文这些原语都是可复用的地基（§2） |
| 需要子 Agent 间通信吗？ | **不需要直接通信管道**。需要的是"共享世界状态（房间）+ 可见性过滤 + 回合调度"这个中介层（§4） |
| 落地要补什么？ | 三件套：**频道/可见性模型、按参与者渲染的上下文装配、回合调度器**（§5）；其中主持人的"房间工具"是工具层的活，不是引擎层的 |

一个有用的区分：**世界观差异 ≠ 信息差异**。多人辩论里参与者主要是立场/视角不同（信息大体公开），靠"分角色 system prompt + 共享公共记录"就能成立，用现有 delegate 原语即可近似；狼人杀的核心是**信息不对称本身**（谁知道什么就是规则），才需要完整的可见性模型。本文以狼人杀为最严苛场景分析，辩论是其退化情形。

## 2. 现状盘点：主-从编排原语已具备什么

这些能力对"主持人 + 隔离参与者"拓扑是直接可复用的地基：

| 原语 | 位置 | 对多方场景的价值 |
|---|---|---|
| Agent 注册资源 | `models/llm/agent.go`（`tblLlmAgent`：独立 SystemPrompt/ModelKey/工具白名单/Skills/MaxSteps/递归 token 预算/ReadOnly） | 每个参与者可声明为独立 agent，身份与能力天然分角色 |
| 上下文强隔离 | `models/llm/react_message.go:115-126`（`GetOuterReactMessagesBySessionIDWithDB`，注释明确"子 run 的消息绝不进入父历史"） | 参与者私有视野的隔离已有先例——隔离粒度虽粗（run 级），但方向一致 |
| 父→子定向注入 | `service/react/send_message.go`（send_message，复用 S1 Steering 落 guide） | 主持人私下告知某个参与者（私聊频道） |
| 子→父完成通知 | `service/react/internal/hub/command_box.go`（Q1 命令箱，模型步边界吸收、claim-once、账本镜像落库） | 参与者回合结束 → 主持人被唤醒推进状态机 |
| 并行委派 + join | `service/react/delegate.go:292`（后台委派）、`service/react/wait_agent.go:151`（wait_agent） | 多参与者同时行动（狼人夜间阶段）的 fan-out + 汇合 |
| 上下文按 run 从 DB 重建 | `service/react/runtime.go:334`（`createReactRunContext`，:381 读历史装配） | "每回合按视野渲染上下文"在架构上是顺的——渲染点已经存在 |
| 工具结果只回流调用者 | `service/react/engine.go`（executeToolCalls → tool_result 只 append 进当前 run 的 `state.messages`） | 参与者的私有动作（夜里动手）天然不泄漏给别人 |

## 3. 四个缺口（按重要性排序）

1. **消息级可见性模型**。`tblLlmReactMessage`（`models/llm/react_message.go:34-50`）没有 visibility/recipient/audience 任何字段，role 只有 system/user/assistant；唯一的隔离粒度是 run 级父子二分。狼人杀的"夜晚行动只对特定玩家可见"需要每条消息带接收方语义，或按参与者渲染视图。
2. **对等路由**。`send_message` 被安全边界限定为只能发给本 run 直接委派的子 run（`service/react/send_message.go:8`，防跨会话窥探）；全库无 broadcast（grep 仅命中面向前端的 WS 事件扇出 `client_hub.go`）。多个 agent 互相寻址的机制不存在。
3. **会话模型**。一个会话 = 一个 main 身份 = 至多一个活跃外层 run（`service/react/runtime.go:348` 起的事务 + 行锁保证）。"多参与者轮流发言、回合调度"在数据模型里不可表达。
4. **共享世界态**。没有"房间/世界状态 + 按参与者视角取数"的概念。投票、角色、存活状态这些游戏真值没有归属地。

## 4. 核心设计决策：不做子 Agent 间直接通信

这类场景的正确解法是把通信对象从"彼此"换成一个中介：**共享世界状态（房间）**。Agent 间交互全部退化为对房间的读写：

- **发言** = 往某个带成员资格的频道写一条记录（公开演讲频道、狼人夜间频道、主持人私聊）；
- **感知** = 该参与者被"唤醒"的回合开始时，按它的视野把世界状态投影渲染成上下文。

"狼人杀里狼队夜里商量"看起来像 agent 直连，其实只是一个**成员资格受限的频道**，不是点对点管道。辩论同理：反驳对方是往公共频道发言，内容上引用对方，传输上走共享 transcript。

不做直连管道的三个理由：

1. **生命周期不匹配**。回合制场景里参与者大部分时间处于休眠。管道要求收发双方同时在线，最终不得不给每个 agent 配收件箱——而"收件箱 + 成员资格 + 投递规则"这个东西就叫房间。既然终点是房间，就不该先修管道。
2. **信息流管控必须中心化**。狼人杀的规则本质就是信息不对称本身。如果 agent 能直连，"狼能不能私聊村民"就从结构性不可能退化成 agent 的自觉问题；走中介 + 可见性过滤，作弊在结构上不可能。现有 `send_message` 故意限定父子链、`wait_agent` 校验 `parent_run_id`（`service/react/wait_agent.go:19`），延续的正是"通道要窄、由父方仲裁"的哲学。
3. **与现有架构最顺**。上下文本来就是每次 run 启动时从 DB 重建（§2），"每回合按视野渲染"只是历史装配那条 JOIN 加一个可见性维度，不动消息总线；工具结果本来就只回流调用者的 run，"夜里动手"自然就是一个写世界态的工具调用。

什么情况才真的需要 agent 直连：异步、长驻、事件驱动互相应答的 agent（互相监听对方产出并即时响应）。即便是那种形态，工程上通常也建模为总线/队列而非点对点管道。本文目标场景（回合制博弈/辩论）完全不沾。

这与既有非目标一致：[todo/20260926_多智能体编排补齐点与场景.md](./todo/20260926_多智能体编排补齐点与场景.md) §四已明确"兄弟智能体点对点消息总线——兄弟间经父模型中转，每条跨代理信息可审计、可归因；点对点一旦放开调试难度指数上升，收益场景罕见"。

## 5. 落地形态草图（狼人杀在现有原语上的映射）

仅作可行性论证，不是实施方案：

| 场景元素 | 映射到现有原语 | 备注 |
|---|---|---|
| 主持人 | 外层 run，驱动回合状态机（天黑→各角色依次行动→天亮→投票） | `ResolveSystemPrompt` 按 caller/route 出主持人提示词 |
| 玩家回合 | 一次 `delegate_agent` 子 run：system prompt = 角色与私有信息，历史 = 该玩家可见的投影 | 跑完即终态，玩家"无状态休眠"到下回合——每回合 re-delegate，上下文渲染发生在装配时，天然幂等 |
| 玩家动作 | 工具调用（`speak(channel)` / `vote(target)` / `night_action(...)`）写世界态 | 新增房间工具，工具结果只回流调用者 |
| 回合推进 | 子 run 完成通知经命令箱回灌，主持人吸收后委派下一个玩家 | 现有 Q1 机制原样复用 |
| 狼队夜间频道 | 成员资格受限的频道（世界态的一部分） | 不是管道，是带读写权限的数据 |
| 长局上下文膨胀 | 每回合重装配时可做投影裁剪/摘要 | 引擎已有 compact_summary 机制可衔接 |

要补的三件套（引擎/数据层）：

1. **频道/可见性模型**：世界态的数据模型（房间、参与者、频道、成员资格、消息的接收方语义）与渲染规则；
2. **按参与者渲染的上下文装配**：`GetOuterReactMessagesBySessionIDWithDB` 这条装配路径增加可见性维度，或改为"从世界态按参与者投影生成历史"；
3. **回合调度器**：房间协调器（谁该发言、超时/掉线怎么处理、状态机推进）。

工具层（非引擎层）的活：给主持人加"房间工具"——建频道、查当前该谁发言、读公共记录。走房间中介后，连"跨 run 定向寻址"（现有 send_message 只支持父→子）这个引擎侧扩展都不需要。

## 6. 非目标

- **不做子 Agent 间点对点通信/广播总线**（§4，与既有非目标一致）；
- 图引擎、平级 transfer 全共享、gob checkpoint 等仍按 [multi-agent-orchestration.md](./multi-agent-orchestration.md) §六"明确不建议引入"执行；
- 本文不构成排期承诺：多方会话层是否值得建，等真实业务场景出现再说。
