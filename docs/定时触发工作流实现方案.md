# 定时触发工作流实现方案（react-base-service）

> 依据：[openhands-automation学习.md](./openhands-automation学习.md)（OpenHands Automation/无人值守执行调研）、[定时触发工作流的能力.md](./定时触发工作流的能力.md)（需求对话记录）。
> 目标：为基座新增「**定时触发工作流**」能力——按 cron 计划在服务端无人值守地发起一次完整 ReAct run（智能巡检是首个场景），运行历史可追溯、可回放、可通知。
> 定位约束：基座只做**通用触发与执行框架**（定义/调度/执行/历史/通知），巡检领域模型（finding/report 判定逻辑）由 caller 侧配置承载。
> 撰写日期：2026-09-12。
> 修订：2026-09-30 —— 调度器由「DB 轮询 + next_fire_at 原子推进」改为引入 **robfig/cron v3** 进程内调度（当前单实例部署）；防重语义迁移至 run 表唯一索引，详见 §5.1。

---

## 1. 背景与首个场景

需求对话已给出目标形态：每天 02:00 自动巡检 bd-cron——OPS MCP 查错误日志、数据平台 MCP 查失败任务、Metrics MCP 查资源、（P2 后）Code Agent 检索线上代码、DBA Agent 分析慢 SQL，最终产出巡检报告，风险 ≥ P2 时 IM 告警。且明确要求**调度层与 Agent Runtime 分层**，未来从 cron 扩展到事件/指标/告警/发布触发。

OpenHands 的答案是独立 Automation Service + Agent Server 分层协作。对基座的对应判断：**基座本身就是 Agent Runtime（已有），缺的只是"何时跑"这一层**——而且基座已具备无人值守执行的全部底层条件（见 §2），所以不需要独立服务，**进程内调度模块（robfig/cron v3）**即可闭环；当前单实例部署，多实例演进时靠 run 表唯一索引防重（§5.1）。

## 2. 现状盘点：已经具备什么

| 无人值守执行的必要条件 | 基座现状 | 复用方式 |
|---|---|---|
| 无前端连接的程序化 run 入口 | ✅ **memory reflection 已是完整先例**（`service/react/memory_reflection.go`）：`RunWithClientReaderContext(ginCtx, context.Background(), payload, "", headlessEventWriter, nil)` 后台 goroutine 直接跑完一个 run | 定时触发完全复制这条链路 |
| 无 WS 客户端时事件的去向 | ✅ 事件本来就持久化（`tblLlmReactMessage`），回放页 `/react/replay` 与 `/react/session/events` 无需实时连接 | 定时 run 结束后天然可回放 |
| headless 运行的身份与上下文 | ✅ `newHeadlessGinContext(userName)` 注入用户名；`ReactRunPayload`（CallerKey/RouteValues/Type/UserPrompt/Model*/MaxSteps/ControlContext）齐全 | workflow 配置固定 `caller_key + user_name` |
| 会话类型区分（执行裁剪） | ✅ `Type` 字段 + `ExecutionProfile` 机制（reflection 已示范"只放行部分工具"） | 新增 `scheduled` 会话类型：**禁用 client 工具与 ask_question**（无前端可答） |
| 后台任务挂载点 | ✅ `router.Tasks/StopTasks`（asynctask、mcpclient 同款模式：可插拔、未配置空转） | cron manager 挂这里，随优雅停机收敛 |
| run 生命周期与超时 | ✅ run 状态机 + cancel 传播 + 进程退出 expire | 触发侧再包一层 `context.WithTimeout` |
| 报告产物 | ✅ python_exec → COS artifact（`tblLlmReactArtifact`） | 巡检报告落产物，通知带下载链接 |
| 骨架级参考 | service/asynctask 的 Provider 框架（可插拔+空转降级+状态同步） | 调度器的工程范式照此写 |

**结论：基座不需要"补运行时"，只需要补一层薄调度。** 这与 OpenHands "运行时不知道 cron 的存在"的分层结论一致。

## 3. 架构

```text
┌────────────────────────────────────────────────────────────────┐
│ react-base-service（单进程内新增模块，虚线框）                    │
│                                                                │
│  管理接口（HTTP）          调度器（goroutine，router.Tasks 挂载）  │
│  ┌──────────────┐   ┌──────────────────────────────────────┐   │
│  │ workflow CRUD │   │ robfig/cron v3 进程内调度（manager）：│   │
│  │ 启停/手动触发  │   │  启动加载注册 / CRUD 动态增删 entry   │   │
│  │ 运行历史查询  │   │  着火→插 run（唯一索引防重）→闸门     │   │
│  └──────┬───────┘   │  停机 misfire 不补跑 / 优雅停机收敛   │   │
│         │           └───────────────┬──────────────────────┘   │
│         ▼                           ▼ 每次触发一个 goroutine    │
│  tblLlmWorkflow（定义+计划）   ┌──────────────────────────────┐ │
│  tblLlmWorkflowRun（历史）     │ runner：headless run           │ │
│                               │ RunWithClientReaderContext    │ │
│                               │ （type=scheduled，超时 ctx）    │ │
│                               │ → 终态映射/摘要/风险判级        │ │
│                               │ → webhook 通知                 │ │
│                               └───────────────┬──────────────┘ │
│                                               ▼                │
│                    现有 ReAct 引擎（caller 的提示词/工具/Skill/MCP）│
└────────────────────────────────────────────────────────────────┘
```

分层原则（对齐 OpenHands + 需求文档）：**触发定义（何时跑）→ 调度器（防重/闸门/历史）→ headless run（怎么跑）** 三段解耦；调度器对 run 内部完全无感知。

## 4. 数据模型

两张表（沿用 `tblLlm` 前缀与资源管理模式；领域级 finding/report 表按定位约束留给业务层，基座只存摘要与风险级别）：

```sql
CREATE TABLE tblLlmWorkflow (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  workflow_key   VARCHAR(64)  NOT NULL,            -- 如 daily-bd-cron-inspection
  name           VARCHAR(128) NOT NULL,
  description    TEXT,
  caller_key     VARCHAR(64)  NOT NULL,            -- 触发的 run 用哪个 caller（解析其提示词/工具/Skill/ApiKey）
  route_values   VARCHAR(256) NOT NULL DEFAULT '[]',
  user_name      VARCHAR(64)  NOT NULL DEFAULT '',  -- 以谁的身份跑（工具白名单/积分归属/审计）；空则匿名
  prompt         MEDIUMTEXT   NOT NULL,             -- 任务提示词，支持 {{date}}/{{datetime}}/{{workflow}} 占位符
  trigger_type   VARCHAR(16)  NOT NULL DEFAULT 'cron',  -- cron | manual（一期）；webhook/event 三期预留
  cron_expr      VARCHAR(64)  NULL,                 -- 标准 5 段
  timezone       VARCHAR(64)  NOT NULL DEFAULT 'Asia/Shanghai',
  model_key      VARCHAR(32)  NULL,                 -- 空 = caller 默认模型
  model_version  VARCHAR(64)  NULL,
  max_steps      INT          NOT NULL DEFAULT 20,
  timeout_sec    INT          NOT NULL DEFAULT 1800,
  notify_webhook_url VARCHAR(512) NOT NULL DEFAULT '',   -- 完成通知（企业微信/飞书通用 webhook 兼容格式）
  risk_patterns  TEXT         NULL,                 -- 判级规则：每行一个正则，命中即 risk=high（一期）
  enabled        TINYINT      NOT NULL DEFAULT 1,
  next_fire_at   DATETIME     NULL,                 -- 展示缓存：cron entry 下次着火点快照（manager 注册/着火时回写，非调度依据）
  last_fire_at   DATETIME     NULL,
  created_at/updated_at ...,
  UNIQUE KEY uk_workflow_key (workflow_key)
);

CREATE TABLE tblLlmWorkflowRun (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  workflow_id    BIGINT       NOT NULL,
  trigger_type   VARCHAR(16)  NOT NULL,             -- cron | manual
  trigger_note   VARCHAR(512) NOT NULL DEFAULT '',  -- 手动触发备注/未来的事件摘要
  planned_fire_at DATETIME    NULL,                 -- cron 计划着火时刻（多实例防重键）；手动触发为 NULL
  status         VARCHAR(16)  NOT NULL,             -- pending/running/completed/failed/cancelled/timeout/skipped
  session_id     VARCHAR(64)  NOT NULL,             -- 关联 react 会话 → 回放页直接可看
  run_id         VARCHAR(64)  NOT NULL,
  summary        MEDIUMTEXT   NULL,                 -- run 最终 assistant 消息（巡检结论）
  risk_level     VARCHAR(8)   NOT NULL DEFAULT 'none', -- none/low/high（一期两级+none）
  error_msg      VARCHAR(1024) NULL,
  started_at     DATETIME NULL, finished_at DATETIME NULL, created_at ...,
  KEY idx_workflow_run (workflow_id, id DESC),
  UNIQUE KEY uk_workflow_fire (workflow_id, planned_fire_at)
);
```

设计取舍说明：

- **防重落在 run 行**：`uk_workflow_fire(workflow_id, planned_fire_at)` 使「插入 run」本身就是抢锁——单实例下不会触发冲突，多实例部署时同刻着火只允许一条 run 落库，无需分布式锁组件；手动触发 `planned_fire_at=NULL`，MySQL 唯一索引对多个 NULL 放行，与手动可重复触发天然兼容；
- **定义与计划合一张表**（OpenHands 也如此）：`trigger_type` 判别 + `cron_expr`；三期加 webhook 触发时增列即可，不提前分表；
- **状态机对齐 OpenHands** 并按基座细化：`pending → running → completed | failed | cancelled | timeout | skipped`（skipped = 并发超限瞬时跳过，不算失败，防告警误报；timeout 从 failed 中拆出，因为对巡检"超时未完成"是最需要单独观察的失败模式）；
- **summary 取 run 最后一条 assistant 消息**（OpenHands `agent_final_response` 同义）；全文在会话消息表里，这里只存结论快照供列表页与通知渲染。

## 5. 关键设计决策

### 5.1 调度器：robfig/cron v3 进程内调度（当前单实例，多实例已预留）

> 修订说明（2026-09-30）：初稿采用自研「DB 轮询 + 原子推进」以避免第三方依赖；本次修订改为引入 **robfig/cron v3**（Go 事实标准 cron 库）。收益：删掉自研轮询循环与 `next_fire_at` 重算规则，着火精度从 ≤30s 轮询误差提升到秒级；代价：一条直接依赖 + 内存 entry 与 DB 定义的一致性维护（由 manager 承担）。

选型依据：`cron.ParseStandard` 即标准 5 段表达式（与 `cron_expr` 字段口径一致）；行级时区以 `CRON_TZ=<timezone>` 前缀注入表达式原生支持；纯内存调度、无持久化副作用（定义本来就在 DB，启动重注册即恢复）。

```text
启动（router.Tasks，manager 单例）：
  1. 加载 enabled=1 且 trigger_type='cron' 的 workflow 行
  2. 逐行 register：spec = "CRON_TZ=<timezone> <cron_expr>"，AddJob 持有
     EntryID（维护 workflow_key → EntryID 映射）
  3. cron.New(cron.WithChain(cron.Recover(...))) + Start

着火回调（每次触发一个 goroutine）：
  1. planned_fire_at = 本次计划着火时刻（按 cron 粒度取整）
  2. 插入 run 行（trigger_type=cron, planned_fire_at）
     —— uk_workflow_fire 冲突 = 同次触发已存在，静默跳过
        （单实例正常运行不会触发冲突；这是多实例部署时的防重路径，届时零改造）
  3. 并发闸门：该 caller 当前 running 的 workflow run 数 ≥ 上限 → 改记 skipped，不执行
  4. go executeWorkflowRun(run)

CRUD 同步（所有定义变更经 manager 单点维护，防内存 entry 与 DB 漂移）：
  创建/修改 cron_expr|timezone → Remove 旧 entry + 重新注册
  PATCH enabled：false → Remove；true → 注册
  软删 → Remove
```

关键语义：

- **run 行即锁**：初稿的锁在 workflow 行（UPDATE 推进着火点），存在"推进成功但 run 插入失败"的缝隙；本方案锁就是 run 行本身，多实例演进时同刻着火只允许一条落库，无需分布式锁组件；
- **当前单实例**：调度器是唯一触发源，运行期无跨实例竞争，防重索引仅作演进保险（成本一列一索引）；
- **重启恢复**：内存 entry 随进程消失，定义在 DB——启动重注册即恢复。停机窗口错过的周期不补跑（misfire 跳过，与初稿策略一致）；如需可观测，启动时可对比 `last_fire_at` 补记 skipped 行（可选，一期不做）；
- **启用无补跑风暴**：cron 注册 entry 只从未来最近着火点起算，初稿"长期禁用后启用需从未来起算"的专项规则不再需要；
- **重叠保护**：caller 级并发上限仍走 DB 计数闸门（跨 workflow 共享 caller 时生效，且能落 skipped 行供观测）；如需进程内同 workflow 硬互斥可加 `cron.SkipIfStillRunning`，一期不启用以保留闸门的可观测记录；
- **优雅停机**：`cron.Stop()` 停止后续着火，再等在跑 run 收敛（挂 `StopTasks`，复用现有 shutdown 模式）。

### 5.2 执行：完全复用 headless run 链路

```go
// service/workflow/runner.go 骨架（与 memory_reflection.go 同构）
func executeWorkflowRun(wf *model.LlmWorkflow, run *model.LlmWorkflowRun) {
    ginCtx := newHeadlessGinContext(wf.UserName)              // 复用 react 包的构造（导出或提公共）
    ctx, cancel := context.WithTimeout(context.Background(), time.Duration(wf.TimeoutSec)*time.Second)
    payload := params.ReactRunPayload{
        CallerKey: wf.CallerKey, RouteValues: wf.RouteValues,
        Type:       model.ReactSessionTypeScheduled,          // 新会话类型
        UserPrompt: renderPrompt(wf),                          // {{date}} 等占位符 + 附带"无人值守运行纪律"前缀
        ModelKey: wf.ModelKey, ModelVersion: wf.ModelVersion, MaxSteps: wf.MaxSteps,
        ControlContext: {"source": "workflow", "workflowRunId": run.ID},
    }
    result, err := RunWithClientReaderContext(ginCtx, ctx, payload, "", workflowEventWriter(ginCtx), nil)
    // 终态映射：nil→completed；IsReactRunCancelled→cancelled（区分停机）；
    // DeadlineExceeded→timeout；其他→failed
    // summary = 该 run 最后一条 assistant 消息；risk_level = risk_patterns 正则判定
    // 更新 run 行（含 finished_at）→ notifyWebhook(...)
}
```

四个必须显式处理的点：

1. **会话模型 = 无状态模式**（LangGraph 的 stateless cron 对照）：每次触发新建 session，标题 = `{workflow.name} {触发时间}`，回放页天然可查。巡检不需要跨次累积上下文；三期若出现"持续跟进同一问题"需求再加 `continue_session` 模式（OpenHands EventTrigger 的 `destination: continue_conversation` 对照）；
2. **无人值守纪律**：`scheduled` 会话类型的 ExecutionProfile **禁用 client 工具与 ask_question**（无前端可回填，等待即挂死）；工具可见性沿用 caller + user 白名单——**巡检 caller 建议只配只读 MCP 工具**（这是比 OpenHands NeverConfirm 更符合运维直觉的默认：不是"自动确认危险操作"，而是"危险工具根本看不见"）；
3. **若 run 意外进入 waiting_client_message**（配置错误）：调度侧视为异常终态 failed 并记录原因（Agno 的教训：等待人工输入的状态要被调度器识别，而不是傻等超时）；
4. **优雅停机**：run 注册机制已覆盖进程退出 expire；调度器自身在 StopTasks 中先停调度（cron.Stop()）、再等待在跑 run 收敛（复用现有 shutdown 模式）。

### 5.3 通知与判级（一期规则制，二期裁判制）

```text
run 终态 → 通知决策：
  completed + risk=none  → webhook（轻量：标题+结论首行+回放链接）   可配只告警不报平安
  completed + risk=high  → webhook（完整：结论 + 巡检会话回放链接 + 产物链接）
  failed/timeout         → webhook（错误摘要 + 回放链接）

webhook payload 兼容企业微信/飞书通用 markdown 消息格式（一行配置两种 IM 都能用）；
risk_patterns 每行一个正则，对 summary 命中即 high —— 应对"发现异常/风险/P0/P1/失败率"等巡检结论用语。
```

二期引入**裁判外环**（OpenHands goal loop 思想，可选开关）：run 结束后用独立轻量 LLM 调用审阅 transcript，判定「目标是否达成 / 异常等级」，未达成自动追问一轮（上限 N 轮）。这比盲目调大 maxSteps 更能保障巡检质量，且判级从关键词升级为语义。

### 5.4 管理接口

| 端点 | 功能 |
|---|---|
| `POST /react/workflow` / `PATCH /react/workflow/{key}` | 创建/更新（改 cron 或时区即重注册 entry；enabled 走 PATCH 启停） |
| `GET /react/workflow/list` | 定义列表（含 next_fire_at/last_fire_at/最近一次状态） |
| `DELETE /react/workflow/{key}` | **软删**（置 deleted + 禁用 + 跳过 pending run——OpenHands 同款；不物理删） |
| `POST /react/workflow/{key}/dispatch` | **手动触发**（trigger_type=manual；新建 workflow 的验证入口，OpenHands 最佳实践） |
| `GET /react/workflow/{key}/runs` | 运行历史分页（status 过滤 + 统计计数，对齐 OpenHands status_counts） |

### 5.5 配置

```yaml
llm:
  workflow:
    enabled: false            # 总开关：关闭时不启动调度器、不注册管理接口（默认行为与历史版本一致）
    max_parallel_per_caller: 2   # caller 级并发闸门（超限 skipped）；无轮询间隔配置——cron 按表达式到点着火
    default_timeout_sec: 1800
    default_max_steps: 20
    notify_only_on_risk: true    # completed 且无风险时是否免打扰
```

### 5.6 可观测

`/metrics` 增加：`react_workflow_trigger_total{workflow,status}`（含 skipped/timeout 口径）、`react_workflow_run_duration_seconds`、`react_workflow_running`（gauge）；运行历史页数据源即 `tblLlmWorkflowRun`。**连环失败熔断**（OpenHands `maybe_disable_unhealthy` 对照）：连续 N 次 failed/timeout 自动置 enabled=0（经 manager 摘除 entry）并发一条通知，防故障风暴。

## 7. 分期

**一期（核心闭环，本方案 §3–§6 全部）**：cron 触发 + headless run + 手动触发 + 运行历史 + 启停/软删 + 超时/并发闸门/misfire + 规则判级 + webhook 通知 + metrics。**验收**：配置"每天 02:00 巡检 bd-cron"（caller=ops-inspection，挂 OPS/数据平台 MCP 只读工具），到点自动执行，企业微信群收到结论卡片，点开链接回放页完整还原巡检过程；手动 dispatch 立即验证新配置。

**二期（质量与体验）**：裁判外环（语义判级 + 未达成追问）；报告产物化（提示词要求产出 markdown 报告 → python_exec → COS artifact，通知带产物链接）；管理面板（workflow 列表/编辑/历史页）；连环失败熔断。

**三期（触发源扩展）**：`trigger_type=webhook`（事件入口端点 + 验签 + 简单过滤，对齐 OpenHands EventTrigger）；`continue_session` 模式（同一 workflow 延续上次会话，"持续跟进"类任务）；指标触发（对接告警系统回调）。演进终点即需求文档所述：**事件驱动 + 定时驱动的自主运维 Agent 平台**。

## 8. 与其他方案的关系

- **与 [服务端AI工作台改造方案.md](./服务端AI工作台改造方案.md)（P1 子 Agent）正交互补**：本方案不依赖子 Agent——一期巡检 run 就是普通单 Agent run（caller 的系统提示词写巡检方法论 + MCP 工具）；P1 落地后，同一 workflow 的 prompt 无需改动即可受益于 delegate_agent 委派（main-ops-agent 调度 ops/dba/code 子代理），因为调度器只管"发起 run"，run 内部用什么形态执行与它无关。
- **P2 代码 Workspace 同样直接受益**：巡检提示词中调用 `load_runtime_code("bd-cron","prod")` 即可让 code 工具挂上线上代码 worktree——需求文档里"定时任务绑定代码仓库"的诉求由 P2 链路承接，workflow 层零改造。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 无人值守 run 失控（步数/token 爆炸） | max_steps + timeout_sec 双闸门；caller 级并发上限；后续可挂积分预算 |
| 调度器多实例重复触发 | 当前单实例无此问题；多实例演进时 run 表唯一索引插入防重（表结构已含，届时零改造） |
| 内存 entry 与 DB 定义漂移 | 所有 CRUD 经 manager 单点同步 + 启动全量 resync 兜底 |
| 时区/DST 配错导致错时触发 | timezone 行级显式配置（默认 Asia/Shanghai，注册时以 `CRON_TZ=` 前缀注入表达式）；cron 非法在保存时用 `cron.ParseStandard` 校验并拒绝（不静默禁用——比 OpenHands 更早拦截） |
| 等待类工具挂死 headless run | ExecutionProfile 禁 client 工具/ask_question + waiting 状态视为 failed 的兜底 |
| 通知风暴 | notify_only_on_risk + 连环失败熔断 + webhook 失败退避不重试风暴 |
| 长期运行的 run 历史膨胀 | run 行只存摘要；明细在会话消息表（已有体系）；历史保留策略后续按 caller 配置 |
