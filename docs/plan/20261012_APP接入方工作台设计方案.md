# APP 接入方工作台设计方案

- 日期：2026-10-12
- 定位：为**某一个具体 APP 的接入方**提供自助式工作台前端；现有前端（playground 管理侧栏 + MCP 网关管理台）继续作为**平台管理控制台**使用，两者并存不互相替代
- 前置决策：新页面**面向不受信接入方**（可能给外部/非可信方使用），因此 **app 级鉴权与资源隔离进 P0**，不是 P2
- 关联文档：[服务端AI工作台改造方案.md](../服务端AI工作台改造方案.md)（后端运行时改造，本文是其**前端与接入面**的补齐）、[多端服务形态接入方案.md](../多端服务形态接入方案.md)（端形态与鉴权缺口 §3.1）、[本地工作台与服务端基座的执行边界.md](../本地工作台与服务端基座的执行边界.md)（能力收窄依据）、[integration-guide.md](../integration-guide.md)（接入契约）、[system/agent.md](../system/agent.md)、[system/react_runtime.md](../system/react_runtime.md)

## 1. 背景与定位

### 1.1 现状：前端资产盘点

| 资产 | 形态 | 当前角色 |
|---|---|---|
| [web/sdk/](../../web/sdk/) | TypeScript SDK + SolidJS UI（37 个组件） | **运行面内核**，可嵌入任意宿主 |
| [web/react/index.html](../../web/react/index.html) + [index.js](../../web/react/index.js) | 手写原生 JS 宿主页（`index.js` 约 123KB） | playground 联调页 **+ 全球资源管理控制台** |
| [web/mcp-admin/](../../web/mcp-admin/) | Vue3 + Element Plus + Tailwind4 SPA（4 个视图） | MCP 网关管理台 |
| [web/react/workflow-admin.html](../../web/react/workflow-admin.html) | 自包含静态页 | 定时工作流管理（`appKey` 是表单字段，非作用域） |

### 1.2 问题：现有前端是"资源中心视角"

playground 右栏（`rp-management-*`）与全部管理接口都是**全局**的：

- 资源列表带一个 **app 筛选下拉**（"全部 / 默认 / 各 app"，见 [web/react/index.html:134](../../web/react/index.html#L134)），默认展示全平台资源；
- 管理接口不校验 app 归属，例如 `ListAppsReq` 是空结构体（[components/params/skill.go:152](../../components/params/skill.go#L152)），`/app/list` 返回**全部已注册 app**；
- 会话列表按 `appKey + routeValues + 当前登录用户` 过滤（[service/react/history.go:46](../../service/react/history.go#L46)），是**终端用户看自己**的视角，不是接入方看自己用户的视角。

接入方要回答的是完全不同的问题：「**我的 app 现在是什么状态、我该怎么调它**」。用全局资源列表回答这个问题，既看不全也看不准。

### 1.3 定位：APP 中心视角

| | 平台管理控制台 | **接入方工作台（本文）** | 接入方自己的产品 |
|---|---|---|---|
| 受众 | 平台运营（内部） | **某个 APP 的接入方** | 终端用户 |
| 视角 | 资源中心：先选资源类型，再筛 app | **APP 中心：先确定我是谁** | 无 app 概念 |
| 关注 | 全平台 CRUD、模型、全局开关、配额 | **我的 app 状态 + 我的能力装配 + 调通与观测** | 业务体验 |
| 载体 | playground 右栏 + mcp-admin | 新增 SPA | 嵌 SDK |

一句话原则：**接入方工作台是"视角反转"，不是管理台的功能子集。** 所有页面的数据范围由"我是哪个 app"唯一确定。

### 2.3 SDK UI 的真实缺口（宿主必须补齐）

盘点确认：**工作台级交互大部分内建，但有 6 处必须在宿主侧补齐。** 这些直接转化为新页面的工作量。

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| 1 | **危险确认未浮层化** | `FeedbackArea` 的 `onToolConfirmSubmit` 声明后**从未被使用**（[FeedbackArea.tsx:22](../../web/sdk/ui/components/FeedbackArea.tsx#L22)）；`AgentPanel` 的 activeInteraction 只认 `ask_question` 与 `interactionUI`（[AgentPanel.tsx:405](../../web/sdk/ui/components/AgentPanel.tsx#L405)） | 确认只能点内联工具卡，而 `WorkBlock` 非 live 时**默认折叠**（[WorkBlock.tsx:82](../../web/sdk/ui/components/WorkBlock.tsx#L82)）→ **确认请求可能被用户漏看，run 一直卡在 waiting** |
| 2 | **Plan attempt 内工具卡的确认回调缺失** | `PlanRuntimeCard` 的 attempt 视图只传 `resolveTool`，未接 `onToolConfirmSubmit`（[PlanRuntimeCard.tsx:172](../../web/sdk/ui/components/PlanRuntimeCard.tsx#L172)）；reducer 靠 `toolCallIndex` 定位（[event-reducer.ts:1013](../../web/sdk/runtime/event-reducer.ts#L1013)），attempt 内工具卡不在索引中 | Plan 模式下的危险操作**无法确认** |
| 3 | **统一待办收件箱不存在** | 等待项分散 5 处：`FeedbackArea`（只取最后一个 waiting）、工具卡内联、`PlanRuntimeCard` 卡内、`QueueStrip`、`AsyncTaskResults` 铃铛 | 接入方无"待我处理"总览；**可纯前端派生**（见 §4.5），无需新协议 |
| 4 | 工具结果截断/分片无 UI | `ToolCallState` 不含 `resultRef`/`truncated`（[runtime/types.ts:62](../../web/sdk/runtime/types.ts#L62)） | Inspector 想展示"结果被截断、可拉取完整分片"需自建 |
| 5 | 上下文用量只有环形图 | `UsageRing` 单会话环；`UsageStats` 是写死占位（[UsageStats.tsx:28](../../web/sdk/ui/components/UsageStats.tsx#L28)），[AgentPanel.tsx:1003](../../web/sdk/ui/components/AgentPanel.tsx#L1003) 已注释 | "数值面板"需自建（可复用 `/react/usage/context`） |
| 6 | 产物与 Markdown 渲染有边界 | 产物仅 `window.open`；`ContentBlock` 用 marked + gfm（**无 mermaid**）；`CodeBlock` highlight.js（**无行号**）；**无通用 diff 组件**（diff 仅存在于自定义工具 primitive） | 若接入方需要内嵌预览/diff，需自建或走自定义工具 renderer |

> 泳道形态补充：`AgentLaneView` 是**顶部 tab 切换、一次一条**，`lanes.ts` 只取 `agentPath` 末段做 label，**不做层级嵌套渲染**（[lanes.ts:43](../../web/sdk/ui/components/lanes.ts#L43)）。若工作台要"嵌套时间线 + 并行泳道并排"，需自建视图（数据是现成的：`step.agentPath`）。

### 2.4 边界结论

```text
SDK（现成，直接用）              新页面（本方案要建）
─────────────────────────       ─────────────────────────────
对话 / 事件流 / 工具卡            app 概览与指标
Plan / HITL / 队列 / 异步         能力装配（工具/Skill/Agent/提示词/MCP）
会话列表 / 分叉 / 重命名           装配快照与预览
模型与连接个人配置（用户级）        接入体检
附件 / 产物 / 反馈                app 级运行时配置（/setting/*，app 维度）
⚠️ 6 处缺口见 §2.3              待办收件箱 / 嵌套泳道 / 工具结果分片
                                鉴权、角色、资源归属
```

**一句话**：SDK 给了你一个**功能完整的对话工作台**；新页面要建的是**它外面的 app 外壳**——观测、配置、装配透明化、以及安全边界。

> **反例警示**：[web/react/index.js](../../web/react/index.js) 用手写原生 JS 重做了一套对话宿主，已长到约 123KB 单文件。新页面**不得**重复这条路。

## 3. 信息架构

按**接入方心智**组织导航（接进来 → 装配 → 调通 → 上线 → 观测），而不是按后端资源表。

| # | 一级导航 | 回答的问题 | 主要数据来源 |
|---|---|---|---|
| 1 | **概览** | 我的 app 健康吗？ | 新增 `POST /app/overview`、`/app/doctor`（§6） |
| 2 | **接入向导** | 我该怎么接？ | 现有 `/app/*`、`/apikey/*`、`/system-prompt/*`、`/tool/*` + 接入清单 |
| 3 | **能力装配** | 我的 Agent 会做什么？ | `/tool/list`、`/skill/list`、`/agent/list`、`/system-prompt/list`、`/setting/*` |
| 4 | **调试工作台** | 为什么它这么答？ | SDK `mount()` + 新增装配快照接口 |
| 5 | **会话与观测** | 我的用户在问什么？ | 现有 `/react/session/*` + 新增 app 维度列表接口 |

### 3.1 路由设计

```text
/react-base-service/app-workbench/#/                概览
/react-base-service/app-workbench/#/onboarding      接入向导
/react-base-service/app-workbench/#/capabilities    能力装配
/react-base-service/app-workbench/#/playground      调试工作台
/react-base-service/app-workbench/#/sessions        会话与观测
/react-base-service/app-workbench/#/settings        app 设置（运行时配置/凭证）
```

- 采用 **hash 路由**，与 [web/mcp-admin](../../web/mcp-admin/src/router/index.ts) 一致，避免后端 SPA fallback 改造；
- **appKey 不放在 URL 路径**，而由登录态/凭证解析（见 §5）。理由：放入路径会诱导前端"信 URL 里的 appKey"，与 §5 的"服务端以凭证为准、请求体 appKey 仅作校验"原则冲突，容易写出越权代码。

## 4. 关键设计点

### 4.1 装配快照（最高价值项）

**问题**：接入方最大的痛点是"我配了工具，模型却说没这个能力"。答案散落在 5 个页面，且**生效优先级（app 覆盖 > 全局覆盖 > custom.yaml > 内置默认）只有后端知道**。

**关键发现：装配快照的大部分数据已经落库。**

| 快照组成 | 是否已持久化 | 位置 |
|---|---|---|
| 工具索引快照 | ✅ | `ReactRun.ToolIndexSnapshotJSON`（[models/llm/react_run.go:45](../../models/llm/react_run.go#L45)） |
| Skill 索引快照 | ✅ | `ReactRun.SkillsIndexSnapshotJSON`（[:48](../../models/llm/react_run.go#L48)） |
| 已激活工具定义 | ✅ | `ReactRun.ActiveToolDefsJSON`（[:47](../../models/llm/react_run.go#L47)） |
| 上下文分类构成 | ✅ | `ReactRun.ContextBreakdownJSON`（[:65](../../models/llm/react_run.go#L65)） |
| 生效运行时配置 | ✅ | `tblLlmRuntimeSetting`（app 行 + 全局行） |
| **系统提示词拼接结果** | ❌ **未持久化** | 每次 run 由装配函数现算 |

写入路径见 [service/react/runtime.go:596](../../service/react/runtime.go#L596)（构建）与 [:413](../../service/react/runtime.go#L413)（落库）；回读复用见 [service/react/external_runtime.go:154](../../service/react/external_runtime.go#L154)；历史回放已在消费它（[service/react/history.go:135](../../service/react/history.go#L135)）。

**因此分两种形态：**

1. **历史态快照**（某次 run 当时装配了什么）：直接读 `tblLlmReactRun` 即可，**后端几乎零改造**，只需加一个只读接口。
2. **预览态装配**（当前配置下会装配成什么）：新增 `POST /app/assembly_preview`，复用引擎装配函数，返回 system prompt + 工具摘要 + Skill 摘要 + 生效配置（**逐项标注来源：app / 全局 / yaml / 默认**）。

> 建议补一列 `system_prompt_snapshot`（mediumtext）把 system prompt 也落库，让历史态快照完整。此项可选，但成本极低、排障价值高。

### 4.2 接入体检（Doctor）

一页列出"还差什么、哪里配错了"，每条带深链跳修复。检查项建议：

## 5. 鉴权与隔离（P0）

### 5.1 现状证据

| 事实 | 证据 |
|---|---|
| 全部业务接口免鉴权，身份仅取 `X-User-Name` 头，缺省 `anonymous`，**无任何校验** | [middleware/auth.go:14](../../middleware/auth.go#L14) |
| `/app/list` 无过滤条件，返回全平台 app | [components/params/skill.go:152](../../components/params/skill.go#L152)、[controllers/http/app/app.go:108](../../controllers/http/app/app.go#L108) |
| 会话列表按"当前登录用户"过滤，接入方看不到自己 app 的用户会话 | [service/react/history.go:46](../../service/react/history.go#L46) |
| 跨用户看会话靠**管理员白名单**闸门（`playground_whitelist`），不是 app 角色 | [router/http.go:383](../../router/http.go#L383)、[conf/config.go:94](../../conf/config.go#L94) |
| 现有"特权"机制只有全局静态令牌白名单（`admin_tokens`） | [controllers/http/mcpadmin/mcpadmin.go:48](../../controllers/http/mcpadmin/mcpadmin.go#L48)、[conf/config.go:795](../../conf/config.go#L795) |

> 结论：**今天任何人可枚举并改写任意 app 的资源。** 面向不受信接入方时，这是必须先解决的前提（[服务端AI工作台思路和讨论.md:1705](../服务端AI工作台思路和讨论.md#L1705) 也把"权限隔离和插件调用鉴权"列为第一优先级）。

### 5.2 方案：复用仓库内已验证的凭证模式

仓库已有一套正确的 app 凭证实现，直接沿用其模式：

- **凭证形态**：`Bearer <app_key>:<app_secret>`
- **校验**：查表 → 停用校验 → `subtle.ConstantTimeCompare` 常量时间比较 secret → 写入上下文身份
- 参考实现：[service/mcpgateway/auth.go:30](../../service/mcpgateway/auth.go#L30)
- 模型先例：[models/llm/mcp_app.go:20](../../models/llm/mcp_app.go#L20)（`tblLlmMcpApp.app_key` + `app_secret`）

> ⚠️ 注意命名冲突：`tblLlmApp`（运行时 appKey，本方案主体）与 `tblLlmMcpApp`（MCP 网关消费方凭证）是**两个不同的 app 概念**。本方案的 app 是前者，secret 需在 `tblLlmApp` 上新增（或新建独立凭证表）。

**推荐落地**：

1. `tblLlmApp` 增 `app_secret`（或新建 `tblLlmAppCredential` 表支持轮换多密钥）；
2. 新增中间件 `middleware.AppAuth()`：解析凭证 → 校验 → `helpers.SetAppKey(ctx, appKey)`；
3. **所有 app 作用域接口从上下文取 appKey，忽略请求体中的 appKey，或在两者不一致时直接拒绝**——这是防止越权的关键；
4. `helpers/` 目前只有 `SetUserName`/`GetUserName`（[helpers/user_name.go:8](../../helpers/user_name.go#L8)），需补 app 维度；
5. 平台管理接口（`/app/register|update|batch_delete`、全局开关）继续走**管理员令牌**，与接入方凭证分链，接入方不可访问。

### 5.3 ⚠️ 高危发现：SDK 内嵌的模型配置抽屉会写全局运行时设置

盘点中发现的**跨租户写入风险**，必须在 P0 处理：

`SettingsDrawer` 的「上下文与压缩」tab 调用链完全不传 app 维度：

```text
SettingsDrawer.save()            → client.updateContextSetting({enabled, tokenTrigger, ...})   // 无 appKey
session-manager.updateContextSetting → POST /setting/context/update
components/params/setting.go:51  → AppKey 为空 ⇒ 写【全局行】
```

证据：[SettingsDrawer.tsx:1157](../../web/sdk/ui/components/SettingsDrawer.tsx#L1157)（保存不带 `appKey`）、[session-manager.ts:200](../../web/sdk/session/session-manager.ts#L200)（`get` 传 `{}`）、[components/params/setting.go:51](../../components/params/setting.go#L51)（注释明确"空=写全局行"）。

**更硬的证据**：SDK 侧的类型定义 `UpdateContextCompactSettingReq` **根本没有 `appKey` 字段**（[protocol/types.ts:431](../../web/sdk/protocol/types.ts#L431) 共 10 个字段、无 appKey）。也就是说 **SDK 连"写 app 行"的能力都不具备**——它只能读合并视图、写全局行。因此这不是"调用方漏传参数"，而是 SDK 能力缺失。

**后果**：任何接入方（乃至终端用户）在嵌入的 SDK 面板里点一下「保存」，就会**覆盖全平台的上下文压缩策略**；点「清除覆盖」则会**抹掉全部 app 共用的全局覆盖行**。同理适用于 `/setting/subagent`、`/setting/memory`、`/setting/web`（三者同样支持 app 维度，[components/params/setting.go:7](../../components/params/setting.go#L7)）。

**处理方案（建议 1+2 都做）**：

1. **SDK 补 `appKey`**：给 `UpdateContextCompactSettingReq` 等类型加 `appKey`，`SettingsDrawer` 从 `client.getSessionScope()` 取值传入；同时 `mount()` 应提供"隐藏模型配置抽屉"的开关（当前无此选项）。
2. **服务端兜底（必须做）**：`/setting/*/update` 对**非管理员令牌**的请求，强制以 `ctx` 的 appKey 覆盖请求体 appKey；**即使请求体为空也不得写全局行**。这样即使旧版 SDK 在线，也不会造成跨租户污染。
3. 明确区分"用户级个人模型配置"（`/model/*`，SDK 现有职责，可保留）与"app 级运行时配置"（`/setting/*`，工作台自建面板）。

> 这条也说明：**§5.2 的中间件加固不是"为了能对外开放"的额外工作，它同时修掉了一个现在就存在的越权写路径。**

## 7. 技术选型与工程结构

### 7.1 选型

**新建 `web/app-workbench/`，栈沿用 mcp-admin：Vue3 + Element Plus + Tailwind4 + hash 路由 + axios。**

理由：

1. 管理台已是 Vue3 + Element Plus，团队有组件与习惯积累，复用 API 封装/构建/embed 全流程成本最低；
2. 避免仓库出现 Vue / Solid / 原生 JS / React 四种栈；
3. 对话内核通过 `window.AgentWebSDK.mount()` 复用，**不重写**——SolidJS 已被打包进 SDK 产物（`solid-js` 在 devDependencies，构建期内联），对 Vue 宿主是隔离的"孤岛"，无版本冲突。

### 7.2 工程结构（照抄 [web/mcp-admin](../../web/mcp-admin/)）

├── src/
│   ├── main.ts
│   ├── router/index.ts   # createWebHashHistory

│   ├── api/auth.ts       # app 凭证（替换 X-Admin-Token）
│   ├── api/{app,capability,session,observability}.ts

## 9. 风险与待验证项

| 6 | SDK 尺寸 | `0.0.1.js` 706KB + CSS 159KB | 首屏延迟加载 SDK，仅调试工作台路由按需引入 |
