# <变更主题>

## 1. 背景与目标

说清为什么要改。原有行为是什么、有什么问题、本次要达到什么效果。

修复类变更在此展开三个子节：

### 问题描述

现象、触发条件、可复现的具体案例。

### 根因分析

定位到具体函数和代码行为。有线上日志时给出 requestId、涉及的数据记录。

### 影响范围

哪些用户/接口/数据受此问题影响。

## 2. 代码改动

按文件组织。不贴大段 diff，写清改动的行为语义。

- 文件：`path/to/file.go`
  - 改动说明：
- 文件：`path/to/file_test.go`
  - 改动说明：

改动较复杂时可用二级标题分文件：

### 文件：`path/to/file.go`

1. **新增 `xxx` 函数**：职责与边界处理
2. **修改 `yyy` 函数**：改动点

## 3. 影响范围

逐项写明，**没有影响也要显式声明**。

- 接口：`/api/xxx`、`/api/yyy`
- 模块：
- 配置：无新增配置项
- 数据库：不新增数据表

## 4. 测试验证

写**真实执行过的**命令和结论。不写"已测试通过"。

- `go test ./service/xxx`：通过。
- `go vet ./service/xxx`：通过。
- `go build ./...`：通过。

## 5. 风险与兼容性

用户可感知的后果、需要注意的边界、回滚方式。真的无风险才写无风险。
