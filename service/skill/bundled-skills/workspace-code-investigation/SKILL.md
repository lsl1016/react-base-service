# 代码工作区调查规范

需要定位报错代码、核对线上逻辑、解释实现或梳理调用链时，先建立只读代码工作区，再用符号级检索工具调查。工作区与全部检索工具均为只读——任何写操作都会被拒绝，修改建议以"文字描述 + 文件位置"给出。

## 工作区生命周期

1. `load_runtime_code(service=<目标服务>, env=<环境可选>)`：代码落到本 run 专属 worktree，**锁定到该环境当前 commit**，工具以前缀 `ws_<service>_` 动态挂载；run 结束自动释放。
2. service 名必须在 workspace 白名单（resolvers）内，来自任务描述或用户输入；不确定时先确认再加载，不要猜服务名。
3. 加载返回里有 commit——报告结论时必须带上它（"核对自 <commit>"）。

## 检索工具族与选用顺序

| 工具 | 用途 | 何时用 |
|---|---|---|
| `get_repo_map` | 仓库结构地图（模块/目录/符号分布） | **第一步**，建立全局认知再下钻 |
| `find_symbol` | 按符号名查声明（go/ast 声明级） | 已知函数/类型/方法名时，**优先于文本搜索** |
| `get_file_symbols` | 单文件符号表 | 已锁定文件、想快速掌握其结构 |
| `find_references` | 符号引用候选 | 追调用链、评估改动影响面 |
| `search_code` / `search_pattern` | 文本/正则检索 | 报错文案、配置键、注释、字符串常量 |
| `list_files` | 目录列表 | 确认目录结构与文件命名习惯 |
| `read_file` | 读文件内容 | 最后精读关键路径，配合行号引用 |

原则：**声明级工具（find_symbol 系）比文本搜索准**——先符号后文本；read_file 放最后，避免把大文件整读进上下文。

## 调用方式

ws_ 工具同样走两段式协议：先 `get_tool` 加载 `ws_<service>_<tool>`（返回 parameters），再 `execute_tool` 执行。`load_runtime_code` 之后工作区才挂载，get_tool 早于加载会报 tool not found。

## 报告格式

- 结论先行，每条结论一行；
- 证据必须可核对：`文件路径:行号` + 关键代码摘录（1~3 行）+ 符号名；
- 末尾标注核对的 commit 与 service/env；
- 未找到/不确定的假设单独列出，并给出下一步检索建议，不要臆测补全。
