- 日期：2026-09-30（方案设计 + 主体实施完成，同日）

- 迁移后规模：门面 46 个非测试文件（原 56）；子包 6 个 / 23 个非测试文件；外部导入面零改动（controllers 与 service/plan 仍只导入 `react-base-service/service/react`）。

- 关联文档：`docs/runtime-modularization.md`、`docs/todo/20260926_多智能体编排补齐点与场景.md`

## 一、现状诊断：为什么这个包难拆

真正的障碍不是文件多，是三条耦合轴：

1. **`reactEngineState` 是万能 receiver**——约 120 个方法散布在 31 个文件里（engine.go 16 个、boundaries.go 12 个、delegate.go 11 个、tool_dispatch.go / business_tool.go 各 8 个……）。Go 规定方法必须定义在类型所在包，所以这 31 个文件不能直接移进子目录，一动就是拆包级别的手术。
2. **`executeReactLoop` 被递归复用**——delegate 子 Agent（delegate.go:214）、Plan Step（external_runtime.go:296）、client_tool 都调它，引擎主循环必须留在顶层。
3. **对外 API 面宽但入口窄**——只有 13 个外部文件导入（controllers/http/react 7 个 + service/plan 6 个），但引用符号极多（`WS`、`Run`、`ListSessions`、queue 管理全套）。门面必须原样保留。

有利条件：

- `doc.go` 有清晰的架构自述与修改约束（分层哲学、runtimeServices 注入、ExecutionProfile 收敛）；
- `runtime_services.go` 已是服务注入雏形；
- 方法数分布不均匀——web_fetch（1 个方法）、web_search（1）、graph_memory（2）、inspect_data（2）、display_files（2）这类文件是"叶子"，拆起来便宜。

## 二、硬约束（Go 语言层）

- 同一包的文件必须在同一目录 → "目录重构"必然意味着拆子包；
- 方法定义必须在类型所在包 → 方法群文件迁移前必须先函数化或接口化；
- 拆包必须保证依赖方向无环：core ← 能力域 ← 引擎门面，能力域之间不互相依赖。

## 三、候选方案对比

### 方案一：零拆包，包内分组（保守）

文件名前缀规范化（`mem_`、`tool_`、`agent_`、`hist_`）+ `doc.go` 维护分组索引。

- 代价：1 天，零风险，测试不动。
- 收益上限低：IDE 里还是 100+ 文件平铺，`reactEngineState` 继续膨胀。只适合暂时缓解，不建议作为终点。

### 方案二：分阶段拆子包，从叶子开始（推荐 ✅）

核心思路：**不拆引擎，拆能力域**。`reactEngineState` / `executeReactLoop` / 对外门面留在 `service/react`，把低耦合叶子和自成体系的能力域逐批迁到 `internal/` 子包，防止外部绕过门面。

- 代价：批次 1~4 每次半天到一天，批次 5 两天左右，合计一周量级；风险被批次切小。
- 收益：引擎包缩到 ~30 个文件，方法群停止膨胀；新能力有明确落点；delegate 子系统（约 3.7k 行）独立演进。

### 方案三：端口适配器彻底重分层（激进）

引擎只剩状态机，所有能力（工具/记忆/委派/交互）通过 `runtimeServices` 接口注入，彻底消灭 `reactEngineState` 方法群。

- 代价：重写约 120 个方法签名和一半测试，数周工作量，e2e 回归成本高。
- 适用前提：runtime 要支持多种执行形态（如 Durable Runtime）。当前 `doc.go` 演进路线未到此步，**暂不启动**。

## 四、方案二目标结构

```

  doc.go  engine.go  runtime*.go  ws.go  steering.go  meta_tools.go  ...
  external_runtime.go           # Plan Runtime 窄接口
```

### 破解方法群的两个手法（按需选用）

1. **receiver 降级为参数**：`func (s *reactEngineState) executeWebFetch(...)` → `netcap.Fetch(ctx, netcap.Request{...})`，子包只拿它需要的字段。web_fetch 只有 1 个方法，函数化成本极低。
2. **接口提取**：delegate 等需要回调 `executeReactLoop` 的域，子包声明 `type LoopRunner func(...)` 或 `SubRunner` 接口，由引擎注入——与 `doc.go` 约束 3"新领域能力优先通过 runtimeServices 注入"同方向。

## 七、实施结果与验收核对（2026-09-30）

| 项 | 结果 |
|---|---|
| 全量测试 | ✅ react 7 个包 + plan + controllers 全绿；repotools 两失败为存量问题（HEAD 复现，symlink 环境） |
| 外部导入面 | ✅ 零改动（controllers/plan 仍只导入 service/react） |
| 子包依赖方向 | ✅ 全部只依赖 core + 外部领域包，无相互导入、无反向依赖 |

| gofmt | ✅ 0 未格式化文件 |
| 根目录非测试文件 | 46（原 56）——未达 ≤30 目标，原因见下 |

**实施偏差记录（为何部分域留门面）**：

实施中发现原方案低估了方法群对引擎状态的共享深度。`s.req`×16、`s.emitter`×9 这类耦合若强行函数化，RunContext 会膨胀成半个引擎状态，违背「不拆引擎」原则。据此调整：

1. **model_failover 留门面**：模型轮转状态机操作 `s.currentModel/s.failoverModels/s.client/token 计数`，是 executeReactLoop 的延伸；其纯函数部分（失败分类/退避曲线/预算）已下沉 `core/modelretry.go`，错误哨兵（取消/断连/超时/交互超时/可重试标记）下沉 `core/errors.go`。
2. **queue_manager 留门面**：与 steering 常量群（steerReceiptGuided/Rejected、准入原因词表）深度交织，二者本质是同一「排队与引导」域，强拆会造成常量两处定义。
3. **history / microcompact / context_breakdown 留门面**：historyEventBuilder 依赖 ToolMeta 注册表与 executeToolInput（工具域类型）；后两者直接操作 s.messages/s.activeTools 对话状态。
4. **memory_extractor / memory_reflection / graph_memory / async_task 留门面**：引擎生命周期钩子与 session 级状态；mem 包只收纯函数 adapter 部分。
5. **delegate / wait_agent / send_message 留门面**：需要回调 executeReactLoop（子 run 复用），是引擎编排本体。

**最终落地结构**：

```
service/react/                  # 引擎门面：engine/runtime/history/delegate/steering/meta_tools/...
  core_bridge.go                # 别名桥：子包导出符号 → 包内既有私有名（门面与方法群文件零改动）
  internal/core/                # 常量(事件/工具名)+ExecutionProfile+JSON Schema+token估算+skill触发
                                # +错误哨兵+模型重试分类+reasoning 解析+大结果/附件/cookie 原语(11 文件)
  internal/netcap/              # web_fetch / web_search（含缓存、SSRF 防护、SearXNG 适配）
  internal/pyexec/              # python_exec 沙箱执行 / inspect_data 结构探查 / 产物管理下载
  internal/mem/                 # 记忆 adapter 纯函数：作用域/渲染/工具声明
  internal/asynctask/           # 异步任务会话级查询 API
  internal/hub/                 # clientMessageHub（WS 上行唯一读者）+ RuntimeCommandBox（通知回灌）
```

**后续新增能力的落点约定**：新的无状态工具/纯函数优先落 core 或对应能力域子包；新的长等待交互复用 hub.ClientMessageHub；新错误哨兵进 core/errors.go；新事件常量进 core/events.go（勿在门面散落定义）。

## 八、e2e 测试独立成包（2026-09-30 追加实施）

8 个 e2e 测试文件（1,813 行，真实 MySQL + 真实模型调用、环境变量门控）已迁至 `service/react/internal/e2e/`（package e2e）。它们本就以导出入口 `RunWithClientReaderContext` 按黑盒姿势编写，迁移代价极小：

- **随迁导出**：`SubAgentFinalResponse`（原 subAgentFinalResponse，Plan Runtime 本在用）、`ReactToolIndexItem`（工具索引快照结构）；工具执行状态词汇六常量下沉 core（ToolExecutionStatus*）。
- **e2e 包自带**：newHeadlessGinContext 副本（3 行 headless gin 构造器，门面生产版不动）。
- **路径修正**：`env.SetRootPath` 由 `../..` 改 `../../../..`（包目录深两层）；注释中的运行命令同步改为 `go test ./service/react/internal/e2e/ -run ...`。
- **验证**：编译 vet 通过、全部单测绿；`REACT_DELEGATE_E2E=1` 真实跑通 TestSkillTriggerE2E（真实 MySQL + glm-4.6，11s）。
- **效果**：门面测试文件 39→31；e2e 获得独立目录与生命周期。约束：迁出后的 e2e 不得断言包内新增私有符号（需要时先导出或回迁）。
