# 新增 Steering 引导注入——运行中消息准入账本与模型步边界 guide 消费（S1）

## 1. 背景与目标

按《docs/plan/20260925_Session与Steering机制借鉴方案.md》实施其 S1 阶段（P0）。参照系为 ZCode 的 Steering 机制：`prompt-admission.ts` 准入决策树、`turn-tools.ts:469` / `turn-stop.ts:195` 的注入点纪律、`steering.ts` 的 drainPendingInput 消费原子性与 discardPendingInput 结算词汇。

### 问题描述

本项目对运行中 session 的新用户消息是硬拒绝：`createReactRunContext` 事务内 `HasActiveReactRunWithDB` 命中即返回 `ErrorReactRunActive`（错误码 6000100），WS 层 `handleWSMessage` 对活跃 run 的 run 消息也直接回错误事件。用户必须等 run 结束或另开会话——这是与 ZCode 体验差距最大的一处。

### 目标

1. run 运行中收到新用户消息时走准入：可引导（running、非软着陆、无附件、配置开启）则回执 `{kind:"guided"}` 并在当前 run 的下一个模型轮注入；不可引导时明确拒绝（原因随回执下发），不打断 HITL 等待。
2. guide 注入点唯一：整批 tool_result 落库之后、下一次模型请求之前（或纯文本 finish 判定之前），注入的 user 消息成为请求尾部，绝不插入 assistant tool_use 与 tool_result 之间。
3. 准入持久化：新增账本表，"引导意图存在过"这一事实崩溃不丢；消费原子（账本置 guided + 用户消息落库同一事务）；重启不复活队列。

## 2. 代码改动

### 文件：`models/llm/react_pending_input.go`（新增）

1. **`ReactPendingInput` 模型**：session_id、run_id、kind（user_input/notification，后者为 Q1 预留）、delivery（guide/queue）、status（admitted/guided/queued/cancelled/discarded）、content、seq（会话内准入序号）、settle_reason、时间戳。
2. **`GetNextAdmittedGuideForUpdateWithDB`**：按 seq FIFO 取最早一条待消费 guide 并加行锁（引擎消费事务的 claim-once 基础）。
3. **`MarkPendingInputGuidedWithDB`**：条件更新 `WHERE id=? AND status='admitted'` 实现 claim-once。
4. **`SettlePendingInputsByRunIDWithDB` / `SettlePendingInputsBySessionWithDB`**：批量结算 admitted → discarded(reason)。
5. **`GetReactPendingInputMaxSeqBySessionIDWithDB`**：会话内准入序号分配（调用方须持 session 行锁）。

### 文件：`service/react/steering.go`（新增）

1. **纯函数层**（单测覆盖，不依赖 DB）：`steerAdmissionDecision`（对齐 ZCode 决策树：running+无附件+非软着陆 → guide；waiting_*/cancelling/软着陆/带附件 → QueueEnabled 时落队列否则明确拒绝）、`steerDiscardReasonForRunState`（cancelled→turn_cancelled、error/timeout/expired→turn_failed、finished→run_finished）、`validPendingInputTransition`（guided/cancelled/discarded 为终态）、`pickPendingGuide`（只取 delivery=guide 且 admitted 的最早一条）。
2. **准入入口 `SteerSession`**：会话行锁事务内完成归属校验（复用从 `validateReactSessionOwnership` 抽出的 `validateReactSessionContext` 五元组校验）、活跃外层 run 定位（`GetActiveOuterReactRunBySessionIDWithDB`）、决策与账本落账；Steering 未开启时返回与历史一致的 `ErrorReactRunActive`。
3. **回执穿透**：`steerReceiptError` 把准入回执从 `createReactRunContext` 穿透到 WS 层（准入提交账本后返回 nil 让事务落盘，再以 sentinel error 替代 RunResult；`SteerReceiptFromError` 按 unwrap 语义还原）。
4. **引擎消费 `drainPendingGuideBoundary(step)`**：单事务内"行锁取 guide → 用户消息落库（与 user_input 同构，历史回放走同一路径）→ 账本置 guided"，随后追加进引擎上下文并广播 `steer_drained`；事务失败账本行不动，下一边界自动重试。
5. **结算 `settleRunPendingGuides`**：run 维度结算未消费 admitted 并广播 `steer_discarded`。
6. **软着陆标记注册表**：`sync.Map` + atomic.Bool，`enterSoftLanding` 置位、run 结束注销，供跨 goroutine 的准入决策读取。
7. **WS 回执下发**：`HandleWSSteer`（run 活跃期间的准入入口）与 `EmitSteerReceipt`（steer_guided/steer_queued/steer_rejected 事件映射）。

### 文件：`service/react/runtime.go`

1. **`createReactRunContext`**：命中活跃 run 时若 Steering 开启则尝试准入（admitted 落账并回执穿透，绝不启动新 run）；否则保持原 `ErrorReactRunActive` 硬拒绝。新建 run 前将会话内残留 admitted 结算为 `discarded(session_resumed)`（重启不复活队列）。
2. **`run()`**：注册/注销软着陆标记；取消/断连分支结算 `turn_cancelled`、出错/超时分支结算 `turn_failed`，结算先于终态事件发送（前端先看到 steer_discarded 再看到 cancelled/error/timeout）。

### 文件：`service/react/engine.go`

1. **工具批边界**：整批 tool_result 落库且闭合校验通过后、下一次 `callModelRound` 前，消费一条 guide（对齐 `turn-tools.ts:469`）。
2. **纯文本边界**：`finish` 判定前先查 pending guide，有则不结束 run、注入后 `continue`（对齐 `turn-stop.ts:195`）；输出截断续写优先级高于 guide。
3. **`finish()`**：run 正常结束仍未消费的 guide 结算 `discarded(run_finished)`（S2 将改为降级排队）。

### 文件：`service/react/boundaries.go`

`enterSoftLanding` 置位软着陆标记（仅外层 run）：软着陆收尾窗口内不再接收/消费 guide（硬约束）。

### 文件：`controllers/http/react/ws.go`

1. `handleWSMessage` 的 run 分支：活跃期间收到新 run 消息改为调用 `HandleWSSteer` 准入并回执（双重拦截的 WS 侧放开）；Steering 未开启时保持历史错误事件行为。
2. `startWSRun`：run 启动错误中先识别 `steerReceiptError`（跨连接 run 冲突场景），准入回执按 steering 事件下发而非错误事件。

### 文件：`models/llm/react_run.go`、`models/llm/react_message.go`

抽出活跃 run 状态集合 `reactActiveRunStates`（并发检查与准入共用同一口径）；新增 `GetActiveOuterReactRunBySessionIDWithDB`（排除子 run）、`GetReactMessageMaxSeqByRunIDWithDB`（guide 消费事务内分配消息 seq）。

### 文件：`conf/config.go`、`sql/init.sql`、`components/params/react.go`

1. 新增 `llm.react.steering` 配置：`enabled`（guide 总开关，默认 false 保持历史行为）、`queue`（排队开关，默认 false，S2 灰度）。
2. init.sql 新增 `tblLlmReactPendingInput`（索引 idx_session_status / idx_run_status）。
3. 新增回执与事件 payload：`ReactSteerReceiptPayload`、`ReactSteerDrainedPayload`、`ReactSteerDiscardedPayload`。

### 文件：`service/react/steering_test.go`（新增）

纯函数测试：准入决策矩阵（guide/reject/queue 三分支 × waiting/软着陆/附件/终态组合）、结算原因映射、账本状态机合法性、FIFO 挑选（queue 行与已消费/已结算行不参与）、guide 消息落库→历史回放 round-trip、追加后 guide 必为上下文尾部 user 消息（注入顺序不变量）。

## 3. 影响范围

- 接口：`/react-base-service/react/ws` 上行 run 消息在 run 活跃期间的行为变化（Steering 开启时回执事件；关闭时与历史一致）；新增下行事件 `steer_guided`/`steer_queued`/`steer_rejected`/`steer_drained`/`steer_discarded`。HTTP run 入口（`react.Run`）未挂路由，不受影响。
- 模块：`react_runtime`；plan 命令在 run 活跃期间仍维持拒绝（HITL 命令不打断）。
- 配置：新增 `llm.react.steering.enabled` / `llm.react.steering.queue`，均默认 false——不开配置时线上行为与历史完全一致。
- 数据库：新增表 `tblLlmReactPendingInput`（存量环境需执行建表语句，见 init.sql）。
- 子 run（delegate）：不接受引导（准入只定位外层活跃 run），engine 消费按 run_id 过滤，子 run 天然无账本行。

## 4. 测试验证

- `go build ./...`：通过。
- `go test ./service/react/ ./service/tool/`：通过（新增 steering_test.go 6 组纯函数测试）。
- `bash scripts/check-docs.sh`：通过（25 篇受管文档 0 处问题）。
- 实测所用 WS 客户端已保留为 `cmd/livetest/steering-*` 四个子命令（guide/waiting/queue/fallback），服务启动后可一键复跑本文全部场景，如 `go run ./cmd/livetest/steering-guide`。
- 启动实测（docker compose 已就绪：mysql/redis/sandbox；`go run main.go` 监听 :8180；`steering.enabled: true`）：
  1. **guide 全链路**：WS 发起长输出 run（数数到 100），首条 content_delta 到达（模型流进行中）时发送第二条 run 消息 → 收到 `steer_guided {"kind":"guided","pendingInputId":"pend_1"}`；模型轮边界收到 `steer_drained`；run 正常 done。账本行 status=guided；消息表顺序为 原始 user(seq1) → assistant(seq2) → **guide user(seq3)** → 新 assistant(seq4)，证明注入发生在 assistant 之后、下一轮请求之前，未插入 tool_use/tool_result 之间；新 assistant 最终文本完整执行引导内容（"【引导收到】我刚才一共从 1 数到了 100"）。
  2. **session_resumed 结算**：向同会话手工插入一条 admitted 残留行（run_id 指向不存在进程的 run）→ 再次发起 run → 该行变为 `discarded(session_resumed)`；本次新引导正常 guided（pend_3）。
  3. **turn_cancelled 结算**：run 中引导（回执 guided）后立即 cancel → run 收敛 cancelled，账本行结算 `discarded(turn_cancelled)`，服务端日志 `未消费 guide 已结算: count=1, reason=turn_cancelled`。
  4. **HITL 保护**：run 调用 ask_question 进入 `waiting_client_message` 后发送引导 → 回执 `steer_rejected {"kind":"rejected","reason":"run_not_steerable"}`；回答后 run 正常收敛。
- 附注：第一条 content_delta 到达瞬间（run 行尚未落 waiting 状态）的引导按 running 准入并稍后消费——这是状态快照语义而非缺陷，与 ZCode admission 时序一致。

## 5. 风险与兼容性

- **默认关闭**：`steering.enabled` 未配置时所有路径与历史行为一致（硬拒绝 + 原错误事件），升级无感。
- **回执即事实、消费有时序**：guide 回执（guided）不代表已注入；若 run 在下一边界前结束，该输入会结算 discarded 并广播 steer_discarded——前端需按事件将"引导中"卡片收敛为"已作废"。与 ZCode 终态边界语义一致。
- **跨连接 run 冲突**：另一连接对活跃会话发 run 消息时，同样走准入（回执事件），不再返回 6000100 错误；依赖旧错误码的调用方在开启配置后需适配。
- **软着陆窗口不收 guide**：临近预算耗尽时发送的输入会被明确拒绝（reason=soft_landing），属有意行为（避免引导延长收尾窗口）；S2 排队开启后将改为落队列。
- **回滚**：关闭 `steering.enabled` 即恢复历史行为；账本表残留数据无副作用（均带状态与结算原因，可审计）。
