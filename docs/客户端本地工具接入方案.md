# 客户端本地工具接入方案（文件读写与 Shell 执行）

> 定位：本文回答「agent 需要读写文件、执行 shell 命令，但绝不允许碰服务端文件系统」这一需求的落地方案——把这组工具**挂载到客户端机器上执行**，服务端只做编排与闸门。属于 [多端服务形态接入方案](./多端服务形态接入方案.md) 中「端侧能力执行」边界的具体化，与 [VSCode插件接入方案](./VSCode插件接入方案.md) §7（Client Tool 的 VSCode 实现）衔接。
> 信任模型的决策依据：[本地工作台与服务端基座的执行边界](./本地工作台与服务端基座的执行边界.md)。
> 状态：设计稿（未实施）。撰写日期：2026-10-05。

---

## 1. 结论与范围

**路线**：不新建通道，**复用现有 Client Tool 机制**（服务端 `client_tool_use_start` → 客户端执行 → `client_tool_use_end` 回填），在其上新增一组「本地执行工具集」（Local Execution Toolset）：`fs_read` / `fs_list` / `fs_write` / `fs_edit` / `shell_exec`。执行端首选 **VSCode 插件**（Node 环境，具备真实 fs / child_process 能力），浏览器端 P0 不做。

**为什么是扩展而不是新建**：客户端执行通道在基座里已经端到端存在——

- 服务端状态机：`service/react/client_tool.go:34`（`executeClientToolCalls`：发 start → run 置 `waiting_client_message` 落库 → 经 `ClientMessageHub`（`service/react/internal/hub/client_hub.go:43`，按 toolUseId 认领）等回包 → 归一化回灌模型），超时（`conf/config.go:173` `interaction_timeout_sec`）、取消、断连均有确定回填语义（`client_tool.go:256` 断连时给模型写明「副作用操作不得盲目重试」）；
- 客户端 SDK：`web/sdk/tools/registry.ts` + `executor.ts` + `defineClientTool`（`web/sdk/tools/types.ts:238`），宿主声明 inputSchema / requiresConfirmation / execute；
- 渠道隔离：QQ Adapter 与定时任务 profile 已显式禁用 client 工具（`service/react/execution_profile.go:22、:77`），只读执行域硬拦截同样覆盖 client 工具（`client_tool.go:97`）。

需要补的是三件事：**能力协商**（客户端声明「我挂了本地执行能力」）、**client 工具确认门**（现在 `tool_confirm.go:120` 的确认门只拦 http/mcp，不拦 client 工具）、**执行进度保活**（本地 shell 可能长跑，固定超时不够用）。

**P0 范围**：工具集五个工具的 DB 注册、协议三处增量、VSCode 侧 LocalExecutor（含沙箱）、确认交互。
**明确不做（本期）**：浏览器端实现（File System Access API 只读降级放 P2）、服务端任何形式的 shell/文件写（[执行边界](./本地工作台与服务端基座的执行边界.md) 已否决）、跨客户端路由（工具只发给发起该 run 的连接）。

## 2. 信任模型：为什么客户端执行是正解

[执行边界文档](./本地工作台与服务端基座的执行边界.md) 的核心论断：本地工作台的隔离是「一台机器一个主人」这个物理事实免费提供的；服务端则必须自建被多租户打破的边界，全部成本都在「重建」上。

把文件/shell 工具挂到客户端，等于**把执行放回物理信任边界内**，基座侧零新增执行面：

| 维度 | 服务端执行 | 客户端执行（本方案） |
|---|---|---|
| 操作对象 | 服务端文件系统（生产密钥/其他租户） | 用户自己的文件、自己的 shell |
| 授权者与承担者 | 三方分离（触发的人 ≠ 承担后果的人） | 同一个人（用户在场确认 = 操作系统级授权代理） |
| 基座需要做的 | 重建沙箱（每会话容器，OpenHands 成本） | 只做路由、确认门与审计，**不碰执行** |

一个必须写明的边界：**文件内容与命令输出仍会流经基座**（WS 中继 + 进入模型上下文）。所以敏感文件的防线在客户端（见 §7 敏感文件模式），不在传输层。

## 3. 备选方案对比

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 服务端沙箱/容器执行 | OpenHands 模式，每 run 一个容器 | 否决。[执行边界](./本地工作台与服务端基座的执行边界.md) §3：多租户下成本只在特定场景值得付；与需求「不许碰服务端」直接冲突 |
| B. SSH 反向隧道 | 基座 SSH 到客户端机器执行 | 否决。NAT/防火墙穿不透、密钥管理重、Windows 不友好，且绕过了基座的确认门与审计 |
| C. 客户端本地 MCP server | 客户端本地跑 MCP server，基座反向拨号连接 | **P2 演进方向**，不作为 P0。连接方向反了（基座在云端无法主动连客户端），本质上仍要一条客户端发起的长连接——那就是现有 WS。协议设计保持 MCP 兼容（工具 schema 用标准 JSON Schema），P2 可把 LocalExecutor 换成「本地 MCP 桥」而通道不变 |
| **D. 扩展 Client Tool 通道（推荐）** | 工具经 DB 注册为 `toolType=client`，真实执行落在客户端宿主 | 状态机/回填/渠道隔离/回放全部白拿，增量最小 |

## 4. 总体架构与执行时序

```text
  模型 tool_use(fs_write)                     
  ┌────────────────────────────────────────────────────────────────┐
  │ 基座 reactEngineState（编排，不执行）                              │
  │  ① 确认门：风险分级 + permission_mode → 必要时 tool_confirm_request│
  │  ② client_tool_use_start（含 timeoutMs、workspaceRoots 快照）     │
  │     run → waiting_client_message（落库，断线可恢复）                │
  │  ③ 等待：client_tool_progress 续期保活（超时 activity 化）           │
  │  ④ client_tool_use_end → 归一化/截断/落库 → 回灌模型下一轮           │
  └───────────────▲────────────────────────┬───────────────────────┘
                  │ WS（复用现有 client tool 协议）   ▼
  ┌────────────────────────────────────────────────────────────────┐
  │ 客户端宿主（VSCode 扩展，Node）LocalExecutor                       │
  │  能力检查（capabilities 声明过该工具）                              │
  │  沙箱校验（path jail：绝对路径解析 + EvalSymlinks + roots 前缀）     │
  │  执行（fs / child_process，本地 timeoutMs 强杀）                   │
  │  输出归一化（截断、二进制检测）→ 回填                                │
  └────────────────────────────────────────────────────────────────┘
```

与现有机制的顺承关系：

- 工具注册走 `tblLlmTool`（`toolType=client`，`service/tool/tool.go:17-23`），挂在专用 callerKey（建议 `local-exec` 或直接 `vscode-ext`）下，模型经两段式 `get_tool` / `execute_tool` 使用（`service/react/business_tool.go:75、:195`）；
- `executeClientTool` 的等待/超时/取消/断连状态机（`service/react/client_tool.go`）原样复用；
- 历史回放天然同形（start/end 事件已入事件流，等待态 UI 已有）。

## 5. 工具集定义

命名与现有 meta tool（`todo_write` 等）和 workspace 工具（`ws_*`）同风格，`frontendHint` 与工具名一致供客户端匹配：

| 工具 | 入参要点 | 风险级 | 确认策略（服务端闸门） |
|---|---|---|---|
| `fs_read` | `path`、`offset?`、`limit?`（行）、`maxBytes?`；二进制/超限只回 metadata + 前 N 行 | read | auto；命中敏感文件模式（`.env*`、`*id_rsa*`、`*credential*`、`.git/config` 等）升级为 confirm |
| `fs_list` | `dir`、`glob?`、`depth?` | read | auto |
| `fs_write` | `path`、`content`（全量写入，受 WS 单消息 8MB 上限约束） | write | confirm_risky |
| `fs_edit` | `path`、`oldText`、`newText`、`replaceAll?`；oldText 不唯一即报错（对齐 Edit 工具语义，防盲写整文件，比 fs_write 省 token 且更安全） | write | confirm_risky |
| `shell_exec` | `command`、`cwd?`（必须落在 roots 内）、`timeoutMs?`（默认 120s，上限 600s） | destructive | **confirm（始终弹）**；命中风险正则（`rm -rf`、`sudo`、`curl … \| sh`、`git push --force` 等）在 UI 中红字标注 |

工具级风险正则复用 `ToolConfig.RiskPatterns`（`service/tool/executor.go:49-56`），`ReadOnly` 声明给 `fs_read`/`fs_list`（可进只读执行域，`client_tool.go:97` 的硬拦截自动放行/拦截）。

设计取舍：不给 `fs_delete`（删除用 `shell_exec rm` 走最高确认级，不为最危险的操作单设低摩擦入口）；不做 `fs_search`（P0 用 `shell_exec rg` 覆盖，够用且零新增面）。

## 6. 协议变更（三处增量，均向后兼容）

对外 WS 协议是稳定契约，三处均为**可选字段/新增消息类型**，旧客户端不发即不生效，行为不变：

1. **能力协商**：`run` 消息新增可选 `capabilities: { localTools: ["fs_read",...], workspaceRoots: ["/abs/path",...] }`。服务端在装配该 run 的 `activeTools` 时，只把「DB 已注册 **且** 当前连接声明支持」的本地工具暴露给 `get_tool`——否则模型会调用一个客户端根本没有的工具，白白等一个超时。`workspaceRoots` 同时进模型上下文（agent 需要知道 cwd 在哪）。roots 在声明时由客户端做一次 `realpath` 归一。
2. **执行进度与保活**：新增上行消息 `client_tool_progress`（`web/sdk/protocol/types.ts:20-31` 的枚举加一项）与同名下行事件（`service/react/internal/core/events.go` 加一项）：payload `{ toolUseId, text?, bytes? }`。双重作用：shell 长命令（跑测试、`npm install`）期间（a）作为活动信号把等待超时从固定 `interaction_timeout_sec` 续期为 activity-based，硬上限取 `tool_meta` 的 `timeoutMs`（客户端本地强杀为准，服务端只兜底）；（b）实时转发给 UI 流式渲染输出。进度事件**不持久化**，回放以 end 事件的最终内容为准，避免事件流膨胀。
3. **client 工具纳入确认门**：`executeLoadedBusinessTool` 的 client 分支（`service/react/business_tool.go:195`）在进入 `executeClientTool` 前先过 `confirmServerToolIfNeeded`（`service/react/tool_confirm.go:120`）同款流程——复用 `tool_confirm_request` / `tool_confirm_answer` 通道、`resolveEffectiveToolPermission`（工具级与 agent 级取更严者，`tool_confirm.go:59`）与 `RiskPatterns` 判定，超时按拒绝回灌。当前实现明确只拦 http/mcp（`tool_confirm.go` 注释），这是本方案唯一的存量行为变更点。

## 7. 安全设计（四层）

| 层 | 机制 | 状态 |
|---|---|---|
| 1. 传输与路由 | toolUseId 精确认领（并行委派不串包）、单连接单 run、同会话单活跃 run、`waiting_client_message` 落库可恢复 | 已有 |
| 2. 服务端闸门 | 确认门三态（§6-3）、`RiskPatterns` 分级、只读执行域硬拦截、渠道 profile（QQ/定时禁用 client 工具）、run 建立∧capabilities 校验 | 确认门扩展是新增，其余已有 |
| 3. 客户端沙箱 | 见下 | 新增（LocalExecutor 内置） |
| 4. 审计 | 工具入参（命令全文/路径）与结果已随 assistant/user 消息持久化，会话史即审计底账；P1 补按用户/渠道的用量统计 | 已有底账 |

客户端沙箱细则（LocalExecutor 内置，**不信任服务端会替它把关**）：

- **path jail**：所有 `fs_*` 的 path 先 `path.resolve` 成绝对路径，再 `fs.realpath` 解析符号链接（写入新文件时解析其父目录），结果必须落在某个 workspaceRoot 前缀内，否则拒绝并回填明确错误（告诉模型合法 roots 是什么）。防 `..` 归一化逃逸与 symlink 逃逸。
- **shell 明示不圈禁**：shell 命令本质任意，path jail 对它无效。`shell_exec` 的边界 = 服务端 always-confirm + 客户端 UI 完整展示命令原文 + cwd 默认圈在第一个 root。这依赖 §2 的信任模型：用户在场确认即操作系统级授权，与本地工作台（Claude Code 等）同信任级。
- **输出限制**：stdout/stderr 合并截断（默认 256KB，头 + 尾保留、中间标注省略字节数）；NUL 字节检测按二进制拒绝回显；`fs_read` 默认单次 ≤2000 行 / 256KB，超出要求模型带 offset 分页。
- **超时**：客户端按 start 事件下发的 `timeoutMs` 本地 `kill`（进程组），服务端 activity-based 超时只兜底。
- **敏感文件**：`fs_read` 命中敏感模式（§5）默认确认，客户端可配置「直接拒绝清单」。

## 11. 风险与开放问题

| 风险 / 问题 | 说明 | 对策 |
|---|---|---|
| 免鉴权信任头被放大 | `X-User-Name` 信任头下，拿到 URL 即可冒充用户；能力从「改图表」升级为「跑 shell」后，冒充的后果从 UI 变成用户本机任意执行 | **M2 上线前完成 caller apikey 校验**（api_key 模块已有体系，VSCode 方案 §12 同项；作为硬前置而不是后续优化） |
| 提示注入诱导 shell | 模型可能被页面/文件内容注入，诱导执行恶意命令；客户端本机是最高价值面 | shell always-confirm 且 UI 展示命令原文；风险正则红字；文件内容进上下文前不做转义（成本过高），防线放在确认门 |
| 长命令与超时语义 | 固定 `interaction_timeout_sec` 会误杀长任务；纯静默长任务（无输出）无 progress 可续 | activity 续期 + `timeoutMs` 硬上限（默认 120s）；静默任务客户端可发空 progress 心跳 |
| 大文件 | WS 单消息 8MB 上限（`service/react/ws.go`）；超限内容截断丢信息 | `fs_read` 分页；P0 明确拒绝超限写并提示模型改用分段；P4 走附件通道 |
| 断连时的副作用 | 写文件/shell 跑一半断连，现有语义已回填「不得盲目重试」（`client_tool.go:256`），但客户端本地可能已产生半成品 | 继承现有语义；`fs_edit` 的 oldText 精确匹配天然幂等友好；VSCode 插件重启后凭会话恢复（VSCode 方案 §6） |
| Windows / 多平台 | shell 语义（`/bin/sh` vs PowerShell）、路径分隔符、realpath 行为差异 | LocalExecutor 平台分支；P0 明确支持范围（macOS/Linux 优先），Windows 列开放问题 |
| 多 root 与 cwd 歧义 | 用户多个 workspaceFolder 时模型可能写错地方 | roots 全量下发给模型；工具入参不允许相对 root 之外的路径；cwd 必须显式且在 roots 内 |
| 与 playground 同会话互斥 | 基座同会话单活跃 run，插件与网页同时操作会冲突 | 沿用 VSCode 方案 §12 对策（端侧提示占用），不新增机制 |
