## 一、现状能力盘点

当前多智能体编排采用"模型自主决策 + 服务端护栏"路线，已完成：

| 能力 | 入口 | 说明 |
|---|---|---|
| 阻塞委派 | `delegate_agent`（缺省） | 父循环停在工具执行内，子 run 终态后取最后一条 assistant 消息回填 tool_result（`subAgentFinalResponse`，delegate.go:516） |
| 后台委派 | `delegate_agent` + `background=true` | 立即返回启动回执，子 run 在独立 goroutine 跑到终态（delegate.go:221），完成通知经命令箱回灌（delegate.go:276） |
| 同轮多委派并行 | 同一次回复多个 delegate_agent 调用 | goroutine + 信号量限流，受 `subagent.max_parallel` 控制（默认 1=串行，tool_dispatch.go:136）；后台委派不受此限制 |
| 通知回灌 | 命令箱（Q1） | 父 run 在模型步边界与纯文本收尾判定前吸收完成通知（engine.go:119、engine.go:208），claim-once 不重复注入 |
| 父→子通道 | `send_message`（A2） | 向已委派子 run 注入 guide 消息，不阻塞 |
| 护栏 | — | `max_depth`（默认 2）、`max_run_seconds` 看门狗、token 递归归账、取消级联（父取消/断连带走后台子 run，delegate.go:214） |

模式选择完全由模型的 `background` 参数决定（delegate.go:143），无服务端强制。

## 二、目标场景与现状判定

目标场景：**主智能体把任务分发给 A、B、C 三个子智能体，继续主干任务并持续了解子智能体进展，执行到某一步需要某个子智能体的结果时"主动下来等结果"。**

| # | 场景片段 | 现状 | 结论 |
|---|---|---|---|
| 1 | 分发给 A/B/C 后继续主干 | 同轮 3 个 `background=true` 委派，当轮拿到启动回执继续干活 | ✅ 成立 |
| 2 | 持续看子智能体状态 | 无巡查/轮询工具，机制是步边界**被动收取已完成通知**；看不到进度，只能看到终态 | ⚠️ 效果近似，机制不同 |
| 3 | 需要结果时主动下来等 | **无 join/wait 原语**。子任务已完成的等效成立（结果早已进上下文）；子任务还在跑时模型无法等待 | ❌ 缺失，且伴随结果丢失风险 |

场景 3 的风险细节（当前最实质的洞）：

- 父 run 无活可干提前收尾 → 之后子 run 完成，`deliverBackgroundNotification` 校验父 run 活跃失败
  （`errBackgroundParentInactive`，delegate.go:325），**不落账不入箱**；
- 结果只留在子 run 持久化记录里（前端可见卡片），但子 run 消息被排除在父历史之外、通知账本按 run 隔离，
  **不会进入任何后续 LLM 上下文**——下一个 run 的模型对子任务产出一无所知；
- 命令箱"绝不为通知复活 run"是有意取舍，但在这个场景下产生静默丢失。

另：`get_async_task` 只覆盖第三方业务异步任务（async_task_query.go），不提供子 run 状态查询。

## 三、补齐点

### P1：wait_agent 等待原语（join）——核心缺口

**问题**：后台委派后主模型在某个 step 确实需要某个子 run 的结果，但它还在跑，模型没有任何手段等待。

**方案草案**：新增内部 Meta Tool `wait_agent`：

- 入参：`run_ids`（列表，来自 delegate_agent 启动回执里的 runId）+ `timeout`（可选，缺省跟随看门狗口径）；
- 实现：与阻塞委派同构——父循环阻塞在工具执行内，轮询 `GetReactRunByRunID` 直至目标 run 终态或超时；
- 返回：**各 run 的状态快照**（runId / status / finalResponse），而不是整体报错——部分超时、部分成功是常态，
  语义应为"报告现状，让父模型自行决定下一步"；
- 复用现成基础设施：取消级联（父取消打断等待）、并行 HITL 路由（父循环阻塞在工具内时 clientHub 照常工作）、
  `subAgentFinalResponse` 取最终回复回填 tool_result；
- 开放问题：子 run 处于 `waiting_*`（HITL 等用户输入）时 wait 如何处理——不算完成；返回快照还是继续等，需要定；
  倾向返回快照（状态=waiting），由父模型决定是 `send_message` 催办还是放弃。

**验收场景（e2e）**：后台委派 1 个耗时子任务 → 主干再走 2~3 步 → `wait_agent` 收割结果并转述；
以及反向用例：父 run 预算耗尽/取消时正在 wait 的行为（应随父级联收敛，不留悬挂 goroutine）。

### P2：delegate_agent 工具描述引导更新（配合 P1）

当前描述只说"background 适合耗时长、无需阻塞当前对话的独立子任务"。P1 落地后应补一句引导，
让模型知道两种形态如何配合，例如：

> background=true 适合稍后再用 wait_agent 收割结果的子任务；若下一步推理立即需要结论，仍用阻塞委派。

纯引导、零机制，但没有 P1 之前不要加（不能引导模型进入无路可走的等待）。

### P3（可选）：收尾前活跃后台子 run 提示

纯文本 finish 判定前（engine.go:208 吸收点附近），若存在**仍在运行**的后台子 run，注入一次性提示：
"你还有 N 个后台子任务未完成"，让模型显式选择 `wait_agent` 等待或放弃（放弃则最终答复中说明去向）。
目的是堵"静默丢失"的口子。注意与预算耗尽收尾路径的冲突：预算耗尽时不应再注入提示续命。

### P4（独立方向，按产品形态决定）：detach 存活语义

用户关页面/父 run 结束后，后台子任务继续跑完、结果下个 run 可查（长任务工单方向才需要）。
delegate.go:214-216 已预留注释（成本可控优先，父取消级联取消后台子 run）。
落地涉及：通知投递目标从 run 级账本改为 session 级账本 + 下个 run 装配时回放，
与"绝不为通知复活 run"原则需要重新权衡。当前不建议动，等产品方向明确。

### P5（观测先行）：委派质量报表

`metrics.ReactDelegationsTotal` 已按 agent_key × status（success/error/no_response/depth_limited/cancelled/background）埋点，
补一个管理面板维度的成功率/耗时报表。用真实流量的数据决定后续编排增强的优先级——
大概率结论是"改工具描述引导就够了"，而不是"需要编排引擎"。

## 四、非目标（有意不加，防止过度设计）

- **服务端复杂度分类器/入口规划器**：增加延迟与新的错误来源，分类错误代价是整条链路跑偏；
  拆任务决策留给模型，服务端只做护栏。
- **兄弟智能体点对点消息总线**：兄弟间经父模型中转，每条跨代理信息可审计、可归因；
  点对点一旦放开调试难度指数上升，收益场景罕见。
- **运行时动态创建 agent 定义**：agent 是带工具策略的注册资源（tblLlmAgent），是治理对象；
  模型凭空造 agent 会绕开治理。若需"清单外的专家"，走受控临时模板方向单独设计。

## 五、优先级建议

P1（wait_agent）是唯一真正缺的原语，做它；P2 随 P1 一起做；P3 视 P1 上线后的丢失案例频率决定；
P4 等产品方向；P5 随时可做、成本最低。其余复杂度都应由具体失败案例来买单。
