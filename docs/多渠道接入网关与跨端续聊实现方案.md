# 多渠道接入网关与跨端续聊实现方案

> 状态：**M1 后端已实施**（2026-10-19，见 §10 勾稽与 §11 实施记录）；飞书机器人权限申请与真机联调待办。
> 起因：为基座引入 IM 多渠道接入能力——多端收发消息、run 结果跨端投递、同一会话跨端续聊（例：QQ 发起任务、飞书收到结果、在飞书里回复继续该会话）。
> 参考对象：TencentCloud/octop-gateway（Python，MIT）的架构抽象——统一消息模型、每渠道自管传输、官方 SDK 优先；**仅参考设计，不引依赖**。
> 撰写日期：2026-10-19。行号基于当日 main 分支（f03b2b0）核实。

---

## 1. 一页结论

| 问题 | 结论 |
|---|---|
| gateway 放哪 | **进程内包 `service/gateway/`**，不单独建仓库；依赖方向单向 `react → gateway`，gateway 不 import 任何 react 内部包，为将来抽取留门 |
| 有没有现成 Go 库 | 统一网关库基本不存在（matterbridge 是桥接应用非库）；各平台官方/事实标准 Go SDK 齐全，**自写薄抽象 + 嵌官方 SDK** 是正确路线（octop-gateway 同款策略：13 个依赖里 10 个是平台 SDK） |
| react 核心要改多少 | **三处小改**：requestSource 分支、ControlContext 约定、（零改）终态投递挂在 IM 适配器内；Run 入口本就是传输无关的服务层函数 |
| 前端要改多少 | 两处：playground 支持 `?session=` 参数加载（链接续聊）；管理面板新增「渠道」tab |
| 最难的部分 | 不是架构（接缝全部现成），是**飞书侧工程细节**：机器人权限审批、消息长度上限、卡片回调鉴权重放 |
| 地基数据模型 | 身份绑定表（platform identity → userName）。M1 可用渠道级默认 userName 跳过，M2 必建 |

## 2. 能力层次模型（本方案覆盖一、二，不做三）

| 层次 | 能力 | 状态 |
|---|---|---|
| 一 | 各端各自收发消息（QQ 会话、飞书会话独立） | M1 随 gateway 落地 |
| 二 | 跨端投递（任一渠道发起，结果推飞书等其他渠道）+ 消息带会话引用 + 同一会话续聊 | M1（同渠道闭环）→ M2（跨渠道） |
| 三 | 多端同会话（所有端实时看同一会话流式、任意端对话） | **明确不做**（HITL 路由/排队可见性/事件扇出一致性每条都是新问题；IM 刚需是异步投递不是实时同步；Octop 也没做——会话按渠道隔离，跨端靠投递） |

## 4. 总体架构

### 4.1 一条消息的一生

```
飞书消息 → gateway(飞书渠道) → 归一化 + 身份解析(userName) → 会话路由
   ├─ 新对话            → 平台会话映射未命中/新建 → 新建 react 会话
   └─ 回复已投递消息    → 查消息绑定表命中 → 原 sessionID 续跑（五元组粘滞）
                            │
              react.RunWithClientReaderContext(ginCtx, runCtx, payload, sessionID, imWriter, imReader)
                            │
              run 执行（Steering/排队/HITL 现有机制全照旧）
               ├─ ask_question → imWriter 推飞书卡片 → 用户回复 → imReader 按 toolUseId 匹配为 tool_use_answer
               └─ done/error   → imWriter 折叠终态 → channel.PushText 推飞书
                               → 写消息绑定（飞书 messageID ↔ sessionID/runID）
```

### 4.2 从 octop-gateway 借鉴的设计（只抄抽象，不抄代码）

1. **统一消息模型 + 会话路由键**：octop session_key 形如 `<agent>:<channel_kind>:<platform_session>:<dm|group>`；本方案对应物 = `channel + chatID → react sessionID` 映射表（§7 tblLlmChannelSession）。
2. **ChannelManager 模式**：每渠道实例 owns its transport（WS/Stream/长轮询/回调），收消息只做"归一化 → 路由 → 调 handler"。
3. **平台能力声明与降级**：每渠道声明 markdown/图/群聊/长度上限，回复按能力渲染（M1 飞书全支持，先做长度截断）。
4. **官方 SDK 优先**：有官方 Go SDK 绝不自研协议；无官方的第一版不做（个人微信等灰产场景明确排除）。
5. **流式折叠**：octop 对 IM 渠道的 response_mode 适配；本方案投递端只收整段终态，流式属于 WS 端（将来"编辑消息伪流式"是纯增量）。

## 5. 后端改动明细

### 5.1 新增 `service/gateway/` 包（主体工作量）

目录建议：

```
service/gateway/
  channel.go        # Channel 接口 + Manager（每渠道实例生命周期）
  message.go        # 归一化 InboundMessage / Addr / 平台能力声明
  route.go          # inbound 路由：消息绑定命中 → 续聊；否则平台会话映射 → 建/复用会话
  adapter.go        # imEventWriter / imClientMessageReader（IM 适配器，方案心脏）
  hitl.go           # toolUseID 等待注册表（map[toolUseID]chan，clientHub 的简化版）
  delivery.go       # 终态投递 + 消息绑定写入；跨端投递地址解析（M2）
  feishu/channel.go # 飞书渠道：larksuite/oapi-sdk-go/v3 WS 事件接收 + PushText
```

**Channel 接口**：

```go
type Channel interface {
    Kind() string                                                  // "feishu"
    Start(ctx context.Context, handler MessageHandler) error       // 自管传输
    Stop(ctx context.Context) error
    PushText(ctx context.Context, addr Addr, text string) (msgID string, err error)
}
```

**IM 适配器**（调用形态照抄 `workflow/runner.go:85,174` 的既有先例）：

- `imWriter`（实现 EventWriter）：丢弃增量事件；收到 `done`/`error` 终态 → 折叠整段 → `channel.PushText` → 写消息绑定表。排队晋升续跑的终态走同一 writer，天然覆盖。
- `imReader`（实现 ClientMessageReader）：HITL（ask_question / 危险操作确认）时推飞书交互卡片（选项→按钮），阻塞等该 chat 回复，按 toolUseId 匹配。超时口径复用 run `waiting_client_message` 的既有配置。

**续聊路由**（inbound 一个 if 分支）：

1. 消息带 `ParentMsgID` → 查 `tblLlmChannelMessage` 命中 → 用绑定 sessionID + **粘滞五元组**调 Run；
2. 未命中 → 查 `tblLlmChannelSession`（chatID → sessionID）复用；
3. 都未命中 → 新建会话（appKey/routeValues 来自渠道配置快照，userName 来自身份解析）。

飞书回复天然带 parent/root message id；「继续」卡片按钮的 callback data 携带 sessionID 作为辅助入口（显式意图）。

### 5.2 react 运行时核心：三处小改

| 位置 | 改动 |
|---|---|
| `runtime.go:754` resolveReactUserName | 加 `requestSource == "gateway"` 分支：从 ControlContext 取 gateway 解析好的 userName（DingTalk 分支为模板） |
| `components/params/react.go` ControlContext | 约定 gateway 元信息字段：`gatewayMeta{channel, chatId, userName}`，沿用"运行控制不入模"语义 |
| 终态投递 | **不改核心**——投递挂在 imWriter 的 done 分支内，不污染 runSingle 收敛路径 |

### 5.3 数据表（3 张起步 + M2 身份表）

```sql
-- 渠道配置：kind、凭证、启停、默认 appKey/routeValues、M1 可含默认 userName
CREATE TABLE tblLlmChannelConfig (...);

-- 平台会话映射：channel+chatID → react sessionID、最近活跃时间
--   续聊/复用的路由依据；创建时把渠道配置快照（appKey/routeValues/userName）存入，保证五元组粘滞
CREATE TABLE tblLlmChannelSession (...);

-- 消息绑定（续聊的钥匙）：channel+chatID+messageID → sessionID、runID
CREATE TABLE tblLlmChannelMessage (...);

-- M2：身份绑定（跨端寻址地基）：platform identity → userName
CREATE TABLE tblLlmUserIdentity (...);
```

M1 简化：单机器人场景在 ChannelConfig 配默认 userName，跳过身份表，全链可打穿。

### 5.4 配置与路由

- `conf` 新增 `llm.gateway` 段：enabled、渠道列表、HITL 超时（复用现有口径）、投递过滤开关（参照 notify_only_on_risk）。
- webhook 类渠道（企微等，二期后）挂 gin router：`/react-base-service/gateway/callback/*`；飞书 WS 长连接模式 M1 不需要公网回调。

### 5.5 SDK 选型与平台准入（官方优先；2026-10 核实）

| 平台 | Go 库 | 期 | 个人开发者准入 |
|---|---|---|---|
| 飞书 | `larksuite/oapi-sdk-go/v3`（官方；自带 WS 事件接收 + Channel 模块消息归一化 + 流式回复，抽象已半成） | M1 | ✅ 免费创建个人组织 → 企业自建应用（无需企业认证，自己审批发布，限本租户内使用） |
| Telegram | `gopkg.in/telebot.v3`（长轮询/webhook） | M2（第二渠道） | ✅ 零门槛：@BotFather `/newbot` 秒拿 token，无审核无组织概念；国内网络需配代理（渠道实现加代理配置项） |
| 钉钉 | `open-dingtalk/dingtalk-stream-sdk-go`（官方 Stream，WS 免公网） | M2/M3 | ✅ 免费创建组织 → 企业内部应用（不上架免审核，限组织内）；Stream 模式本地调试友好 |
| QQ | `tencent-connect/botgo`（官方） | **降级：M3+/按需** | ⚠️ 个人入驻可开发，但仅**沙箱环境**（指定沙箱群收事件）；**正式环境需企业/个体户资质**（营业执照+对公账号，个人主体不能升级转企业）——正式可用性存在硬门槛，故降低优先级 |
| 企业微信 | 无官方 Go SDK，HTTP 回调 + API 自封 | 按需 | 组织维度接入，未核实 |

**优先级结论**：M2 的第二渠道用 **Telegram 或钉钉**（都是长连接/Stream、无公网回调，`Channel` 接口实现与飞书同构，个人身份畅通），先把跨端投递 e2e（发起渠道 → 飞书接收）打穿；QQ 渠道若做，仅以沙箱环境做渠道抽象的验证性接入，不作为可用性承诺。

## 7. 设计决策记录（已定）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 进程内包，不单独建仓库 | 唯一消费方，抽象层无第二用户时抽库是过早抽象；octop 抽库的版本矩阵代价有实证（manager.py 大量前向兼容检查）。留门：单向依赖 + 窄接口，出现第二消费方时 subtree split |
| D2 | 发起端负责对话过程，投递端只收终态 | 流式只在发起端/WS 端；IM 刚需是异步投递非实时同步 |
| D3 | 五元组粘滞 | 续聊时呈现会话创建时的原始元组（渠道配置快照存映射表），校验逻辑零改动；跨端身份经绑定表解析到同一 userName |
| D4 | HITL 只回当前对话端 | ask_question 推回该 run 所在的 chat，不扇出其它端；先答先得的扇出语义是层次三的问题，不做 |
| D5 | 投递挂 imWriter，不进 react 核心 | gateway 侧闭环；workflow/notify.go 的 markdown 组装与"失败不重试"决策在跨端投递时复用 |
| D6 | 续聊 = 同一会话；分叉续聊作为可选 | 同一会话适合"我一个人的任务"；fork（API 现成）适合"飞书里另一个人接着讨论"。两者底层成本几乎一致，做成渠道/消息级选项 |
| D7 | 官方 SDK 优先；无官方 SDK 的渠道不做 | 与 octop-gateway 同策略；个人微信等灰产接入明确排除 |

## 8. 风险与注意事项

1. **飞书侧工程细节**（M1 主要吃时间处）：机器人权限审批周期、消息长度上限（长结果需截断+附产物链接）、卡片回调鉴权与重放、租户/群维度的事件过滤。
2. **HITL 超时**：IM 场景用户可能很久不回；沿用 run `waiting_client_message` 超时口径，超时收敛文案要适配 IM 语气。
3. **排队晋升的投递**：续跑终态经同一 imWriter 覆盖已验证；注意排队项的 payload 快照不含附件的既有约束照旧。
4. **消息绑定表膨胀**：按 sessionID 保留最近 N 条绑定 + TTL 清理（会话删除时级联清绑定，参照 session_delete 硬删级联的既有模式）。
5. **凭证安全**：飞书 app secret 进 ChannelConfig 表，管理面板回显打码（参照诊断信息导出的打码先例）。

## 9. 验收路径

- `GATEWAY_E2E=1 go test ./service/gateway/ -run TestFeishuRoundtripE2E`：飞书发消息 → 新会话 run → 终态推回 + 绑定写入。

与方案的两处偏差（均为简化）：

1. **react 运行时核心零改动**（原计划三处小改）：身份注入走 `react.NewHeadlessGinContext(userName)`（cron 的既有通道），`resolveReactUserName` 现有分支直接命中；requestSource=gateway 只作为 ControlContext 的观测标注。
2. **飞书 HITL 用文本而非交互卡片**：ask_question 推「题面 + 序号选项」文本，回复序号/文本/「跳过」作答；确认类回复「允许」。交互卡片（按钮回调）留 M3 打磨——协议层（toolUseId 组装）已就绪，只换推送渲染。

真机联调修复的两个坑（2026-10-19，均已修）：

1. **SDK 事件分发器必须显式传入**：`larkws.NewClient` 默认不创建 eventHandler，channel 模块的 `ensureMessageHandler` 遇 nil 静默跳过 OnMessage 注册，消息帧在 ws 层 `client_message.go` 因 `eventHandler == nil` 被无声丢弃（仅 Debug 级日志可见）。表象是"长连接正常、发消息无反应"，极易误判为飞书侧事件订阅/发布问题。修复：`larkws.WithEventHandler(larkevent.NewEventDispatcher("", ""))`（长连接模式无需 token/encryptKey）。
2. **MySQL 严格模式拒绝零值时间**：`ChannelSession` 建行时 `last_active_at` 传 Go 零值触发 Error 1292（`Incorrect datetime value: '0000-00-00'`）。修复：建行即写 `time.Now()`。
3. 附带：存量库缺 `tblLlmApp.default_model_hash` 列（特性晚于建库，`IF NOT EXISTS` 不补列）已 ALTER 补齐并给 demo-app 配了默认模型——网关 run 不带 modelKey，依赖 app 级默认模型解析。
