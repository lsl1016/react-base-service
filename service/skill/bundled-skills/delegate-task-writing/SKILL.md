# 委派任务写作规范

把子任务委派给子代理（delegate_agent）时，子代理看不到当前对话历史——它唯一的信息来源就是 task 参数。task 写不清，子代理就会做错方向或反复追问。每次委派前，按下面的五要素清单改写 task。

## task 五要素（缺一不可）

1. **目标**：要完成什么，产出物是什么形态（结论 / 数据 / 文件 / 代码）。
2. **全部已知信息**：相关 ID、时间范围、报错原文、已排除的路径、关键数值。宁可多写，不要让子代理重查你已经知道的事实。
3. **边界与约束**：不要做什么、不要修改什么、时间或步数预期。
4. **期望返回（expect）**：明确要带回什么，例如"根因结论 + 三条关键证据"，而不是"帮我看看"。
5. **失败时做什么**：查不到/失败时返回什么（部分结果、缺口清单），而不是空手而归。

## 委派方式选择

- **阻塞委派（默认）**：下一步推理立即需要结论时使用。
- **后台委派（background=true）**：耗时长、当前对话可以继续推进时使用；完成后以系统通知自动回灌。

## 反例与正例

反例：「帮我查一下那个任务为什么失败。」

正例：「查任务 taskId=173821 失败的根因。已知：该任务是 UDA 加速任务，今天 14:32 提交，报错 'shuffle stage timeout'，重试一次仍失败。已经排除：数据倾斜（各分区行数均衡）。期望返回：根因结论 + 日志中的关键证据行 + 建议的修复动作。查不到明确根因时，返回已核实的范围与最可能的两个假设及验证方法。」

## 多个子任务时

需要多个子代理配合时分别委派（同轮多次调用），不要把多个目标塞进一次调用；每次委派的 task 保持自包含，子代理之间看不到彼此。
