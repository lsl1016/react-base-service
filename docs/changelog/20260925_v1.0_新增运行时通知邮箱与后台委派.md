# 新增运行时通知邮箱与后台委派（Q1/A1）

## 1. 背景与目标

Steering（S1/S2）解决了"用户意图"进入运行中会话的问题，但机器事件没有回灌通道：`delegate_agent` 只能同步阻塞——父 run 挂在工具执行里等待子 run 结论，长任务期间用户干等；子 run 结束后也只有 DB 行，没有任何机制通知父 run。方案（`docs/plan/20260925_Session与Steering机制借鉴方案.md` §3/§4）将其列为 Q1（运行时通知邮箱）与 A1（后台委派）两个 P1 阶段。

本次目标：

- Q1：每 run 一个运行时命令箱（runtime command box），后台任务完成通知在模型步边界被吸收进当前轮（对齐 ZCode runtime-command-active-loop 轮内吸收器），账本镜像复用 `tblLlmReactPendingInput`（kind=notification）。
- A1：`delegate_agent` 新增 `background` 参数（async_launched 等价物），后台子 run 完成后经命令箱回灌运行中的父 run；父 run 已终态则不回灌（不复活 run）。

## 2. 代码改动

### 文件：`service/react/command_box.go`（新增，Q1 核心）

1. **`runtimeCommandBox`**：mutex + FIFO 切片的单 run 命令箱；`PushNotification`（生产者，完成监视 goroutine）/ `drainNotifications`（消费者，引擎循环）/ `pushFrontNotifications`（消费失败放回队首，下一边界重试）。Go 侧引擎只在模型步边界轮询吸收，无需 ZCode 的 notify channel 与优先级调度。
2. **`runtimeNotification`**：命令箱条目（PendingInputID/SubRunID/AgentKey/AgentPath/Status/Summary/usage）。
3. **纯函数层**：`backgroundNotificationStatus`（子 run 终态→success/cancelled/timeout/error）、`shouldDeliverBackgroundNotification`（仅父 run running 才投递）、`truncateNotificationSummary`（摘要截断 12000 rune，ZCode 120k 的 1/10）、`renderTaskNotificationEnvelope`（`<task-notification>` XML 信封：task-id/agent/agent-path/status/summary/usage）、`mergeTaskNotificationContent`（说明前缀 + 信封 `\n\n` 合并，对齐 ZCode 批合并）、`renderBackgroundDelegateLaunchedText`（async_launched 文案纪律）。
4. **`drainRuntimeNotifications`（引擎吸收）**：同一事务内逐条条件更新 claim-once（admitted→guided）+ 合并通知落库为一条 `react_notice` 类型 user 消息；成功后追加上下文（事务提交之后，失败重试不重复注入）、重置重复调用检测器（吸收即重置，对齐 ZCode）、发 `notice_drained` 事件；事务失败通知放回箱首（账本行未动）。
5. **`persistNoticeMessageTx`**：合并通知按 modelMessage 信封落库（role=user、message_type=react_notice），历史回放与上下文重建走通用解析路径，保持"落库顺序=送模型顺序"不变量。

### 文件：`service/react/delegate.go`（A1 核心）

1. **`delegateAgentInput` 新增 `background` 字段**；`delegateAgentToolDefinition` 描述更新并暴露 background 参数（boolean）。
2. **`executeDelegateAgent` 分流**：agent 解析通过后 `background=true` 走 `launchBackgroundDelegate`，否则保持同步路径。
3. **`launchBackgroundDelegate`**：组装与同步路径完全一致的隔离子 run（独立 run 行/历史清空/工具过滤/模型继承/取消注册/RunsActive 计量），立即返回启动回执；子 run 在监视 goroutine 中执行到终态。gin ctx 使用 `newHeadlessGinContext` headless 快照（后台子 run 可能比 WS 连接活得久，原 gin ctx 会被 gin 池回收）并捕获父请求 Cookie（HTTP 业务工具调用态一致）。
4. **`deliverBackgroundNotification`**：读子 run 终态产物（最终回复/递归 usage）→ 在 run 行锁事务内校验父 run 活跃（`GetReactRunByRunIDForUpdateWithDB`）并落账本行（kind=notification、status=admitted）→ 提交后入命令箱。父 run 已终态返回哨兵 `errBackgroundParentInactive`：不落账不入箱，仅记日志（结果留在子 run 记录）。行锁把投递与父 run 终态收敛（先改 state 再结算）串行化，杜绝"父 run 恰好收尾"窗口产生无人消费的残留行。
5. **`finalizeSubAgentRunError`/`accumulateDelegatedTokens` 增加 ctx 参数**：后台监视 goroutine 传 headless ctx。

### 文件：`service/react/engine.go`

1. **循环顶部吸收点**：`step > 0` 时每轮迭代顶部 `drainRuntimeNotifications`（对齐 ZCode 吸收器位置），合并通知拼进当前轮请求，不新开 turn。
2. **finish 边界兜底**：纯文本 finish 判定前最后吸收一次（吸收后 continue，让模型在最终答复中转达后台结果）；通知不受软着陆约束（区别于 guide）。
3. **finish 结算**：`settleRunPendingGuides` 更名为 `settleRunPendingInputs`（guide 与通知统一结算入口）。

### 文件：`service/react/steering.go`

- `settleRunPendingInputs` 重构：通知（kind=notification）绝不降级排队，run 终态一律先经 `SettleNotificationsByRunIDWithDB` 结算 discarded（仅日志，不发 steer 事件）；guide 部分维持 queue 开启降级排队 / queue 关闭 discarded 的 S2 语义。

### 文件：`service/react/runtime_state.go` / `service/react/runtime.go`

- `reactEngineState` 新增 `commands *runtimeCommandBox`，`newReactEngineState` 统一初始化；`runSingle` 三处错误分支结算调用更名 `settleRunPendingInputs`。

### 文件：`models/llm/react_pending_input.go`

- `SettlePendingInputsByRunIDWithDB` 增加 `kind=user_input` 过滤（通知单独结算）；新增 `SettleNotificationsByRunIDWithDB`；`FallbackPendingInputsToQueueWithDB` 增加 `kind=user_input` 过滤——**通知绝不能变成排队用户输入被自动续跑**。

### 文件：`models/llm/react_run.go` / `models/llm/react_message.go`

- 新增 `GetReactRunByRunIDForUpdateWithDB`（run 行锁读取，通知投递围栏）；新增消息类型常量 `ReactMessageTypeNotice = "react_notice"`。

### 文件：`components/params/react.go`

- 新增 `ReactNoticeDrainedPayload`（messageId/count）。

### 文件：`service/react/command_box_test.go`（新增）

- 纯函数测试 8 组：命令箱 FIFO 与 pushFront 顺序、信封字段完整性、摘要截断、合并消息、终态→通知状态映射、投递围栏状态判定、async_launched 文案纪律、工具 schema 暴露 background。

## 3. 影响范围

- 接口：WS 下行事件新增 `notice_drained`；`delegate_agent` 工具 schema 新增 background 参数（对模型可见）；消息表新增 `react_notice` 类型（前端需按系统卡片渲染，不渲染为用户气泡）。
- 模块：`service/react`（命令箱/引擎吸收点/delegate 后台路径）、`models/llm`（账本结算隔离、run 行锁查询、消息类型）。
- 配置：无新增配置项（通知邮箱与后台委派随 delegate_agent 能力与 steering 账本表直接生效）。
- 数据库：不新增数据表（kind=notification 复用 `tblLlmReactPendingInput` 既有列，DDL 已预留）；不新增列。
- 兼容性：同步委派路径行为不变；`tblLlmReactMessage` 新类型对旧前端表现为未知类型消息（历史回放接口原样返回）。

## 4. 测试验证

- `go build ./...`：通过。
- `go test ./service/react/ ./service/tool/`：通过（新增 8 组纯函数测试 + 既有 Steering/闭合/预算测试全绿）。
- `bash scripts/check-docs.sh`：通过（28 篇 0 问题）。
- 实测（服务 go run main.go 监听 :8180，docker mysql/redis/sandbox，实测客户端保留于 `cmd/livetest/delegate-background`）：
  - **absorb 场景**（后台委派 + 完成通知吸收）：`delegate_agent(background=true)` 返回"后台委派已启动：agent=echo-agent, runId=run_ba1f…"→ 子 run（main/echo-agent lane）独立完成 → 服务端日志"后台委派完成通知已投递命令箱 … status=success, pendingInputId=pend_13"→ 主 run step=2 循环顶部吸收，日志"后台完成通知已注入下一模型轮 count=1"→ WS 事件 `notice_drained {"messageId":"msg_8763…","count":1}` → 最终答复转达"后台任务已回灌完成通知：echo-agent 返回的内容就是「任务完成」"→ done。DB 核对：账本行 id=13 kind=notification status=**guided**（claim-once 命中）、content 为 `<task-notification>` 信封（status=success/summary「任务完成」/usage 8171+206 tokens）；`tblLlmReactMessage` 新增 react_notice 消息（seq=6、step_index=2）。
  - **父 run 先收敛场景**（自然发生）：主 run 在子 run 完成前 done → 服务端日志"父 run 已终态，后台完成通知不回灌(结果见子 run 记录) … status=error"，该 session 无任何 notification 账本行（不落账不入箱路径）。
  - **cancel 场景**（取消级联）：启动回执到达后立即 cancel → 主 run `cancelled` 事件 → 后台子 run 级联取消（DB：parent run state=cancelled、child run state=cancelled）→ 服务端日志"父 run 已终态，后台完成通知不回灌 … status=cancelled"，无账本行。
  - 结算路径说明：run 终态未消费通知的 discarded 结算（`SettleNotificationsByRunIDWithDB`）与 guide 结算共用同一入口与 WHERE 纪律，实测以 absorb/cancel 两场景覆盖投递围栏，结算分支经代码走查与既有 session_resumed 机制兜底。

## 5. 风险与兼容性

- **前端适配**：`notice_drained` 事件与 `react_notice` 消息类型需要前端渲染支持（系统卡片）；未适配前通知在实时流中不可见，但历史回放接口原样返回该消息，不丢数据。
- **通知不会打断 HITL**：吸收只发生在模型步边界，父 run 等待人工输入期间通知在箱内等待，等待结束后下一边界吸收；若父 run 在等待中被取消，通知随 run 结算 discarded。
- **后台子 run 的 HITL 降级**：父 run 结束后 WS 读通道关闭（runMsgCh 关闭 → hub 泵退出），后台子 run 此后若需要人工输入会以断连错误收敛——建议后台委派任务避免依赖 HITL；断连同时级联取消后台子 run（有意分歧：成本可控优先，ZCode detach 存活语义未采用，如需后续加开关）。
- **回滚方式**：模型可继续只用同步委派（不传 background）；命令箱/吸收点代码路径在无后台委派时零触发；结算函数对 kind 的过滤不影响既有 guide 行为。
